# KGS v6.2 Native 算子交付规范

本文是向 KernelGen Server（KGS）提供 v6.2 native 算子评测资产时的标准交付规范，
用于明确必须提供什么、什么情况下才需要提供，以及哪些内容不应提供。

这里的 v6.2 是交付格式版本，不是软件发布版本。本文只说明交付方需要准备和验证的
算子资产。

## 1. 规范用词与最小交付

- **格式必须**：缺失或格式错误时，独立验证器会报错。
- **标准交付必须**：Schema 可能允许省略，但正式正确性与性能优化交付必须具备。
- **条件必须**：启用对应能力时必须提供。
- **可选**：不提供也不影响基础执行。

标准性能优化算子的最小目录为：

```text
<operator>/
├── definition.json
├── oracle.py
├── correctness.jsonl
├── timing.jsonl
└── assets/                 # optional
    ├── helper.py
    ├── libvendor_op.so
    └── config.json
```

| 交付物 | 要求 | 内容 |
| --- | --- | --- |
| `definition.json` | 格式必须 | 公开 Python ABI、逻辑输出、mutation 和 alias。 |
| `oracle.py` | 格式必须 | 包含 reference、设备声明，以及需要时的输入构造、fallback 和 validator。 |
| `correctness.jsonl`、`timing.jsonl` | 标准交付必须 | 分别提供正确性和性能 workload。 |
| `assets/` | 可选 | 保存 oracle 私有的 Python、共享库或配置。 |

`REFERENCE_DEVICE`、phase reference、`gen_inputs`、`valid` 和所有 `torch_*` hook 都是
`oracle.py` 的内部契约，不是独立交付物；是否需要提供以及解析顺序统一见第 4 节。

格式允许每个算子只存在一个 phase，但只有
一类 workload 不构成完整性能优化交付：

- 没有 correctness workload，就没有 candidate 数值、mutation 和 alias 结论；
- 没有 timing workload，就没有性能用例；
- v6.2 timing workload 不做正确性校验，不能代替 correctness workload。

确实只需要 correctness 的特殊交付必须明确标注用途。

## 2. 交付方职责

提供方负责提交稳定公开 ABI、权威 correctness/timing 语义、确定可重放的 workload、
必要的输入构造与容差，以及来源 revision 和验证证据。

算子提供方不需要编写 `manifest.json`、选择 Catalog 名称、维护 operator/count 列表，
也不需要提供优化后的 kernel、外部 latency 或 Server 配置。

算子目录名必须与 `Definition.name` 一致。同一算子的 Definition、oracle、workload
和 assets 放在同一目录；多个算子可以直接放在一个交付包中。若 oracle 依赖
FlagGems 等外部源码，交付方只需记录仓库、来源分支和完整 commit，并在运行验证时通过 `--framework-root` 指向该精确 commit 的 clean checkout；KGS 维护者负责把这些信息写入 Catalog manifest。

## 3. `definition.json`：纯公共 ABI

### 3.1 完整示例

```json
{
  "api_version": "v6.2",
  "name": "addmm_",
  "description": "In-place matrix multiply-add.",
  "parameters": [
    {"name": "self", "kind": "positional_or_keyword", "required": true, "type_hint": "Tensor"},
    {"name": "mat1", "kind": "positional_or_keyword", "required": true, "type_hint": "Tensor"},
    {"name": "mat2", "kind": "positional_or_keyword", "required": true, "type_hint": "Tensor"},
    {"name": "beta", "kind": "keyword_only", "required": false, "default": 1, "type_hint": "Number"},
    {"name": "alpha", "kind": "keyword_only", "required": false, "default": 1, "type_hint": "Number"}
  ],
  "outputs": ["out"],
  "effects": {
    "mutates": ["self"],
    "returns_alias_of": {"out": "self"}
  }
}
```

Definition 只能包含公共 ABI。禁止放入 `reference`、`reference_device`、pytest 路径、
workload、dispatcher key、外部 latency 或实现源码。checked-in Definition 应显式写
`api_version`、参数 `kind` 和 `effects`，方便直接评审完整契约。

### 3.2 参数契约

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| `name` | 协议必须 | 合法且不重复的 Python 参数名。 |
| `kind` | 建议显式 | `positional_only`、`positional_or_keyword`、`var_positional` 或 `keyword_only`；缺省为 `positional_or_keyword`。 |
| `required` | 协议必须 | 是否没有默认值。 |
| `default` | 条件必须 | `required=false` 时必须提供；`required=true` 时禁止提供。 |
| `type_hint` | 可选 | 只给 Agent 和人阅读，不参与类型校验。 |

`var_positional` 表示真实 `*args`，必须 `required=true` 且没有 default。v6.2 不接受
未解析的 `**kwargs`。参数顺序必须能构造合法的 Python signature。

ABI 校验只检查参数名、顺序、kind、required/default 状态和默认值，不检查 Python
annotation，也不根据 `type_hint` 强制类型。因此 Tensor list、变长 tuple 等不需要
扩充类型 DSL；`*tensors` 使用 `var_positional`，实际值由 workload/`gen_inputs`
保证。后续被测实现仍必须保持完全一致的调用签名。

Torch dtype、device、layout 或 memory format 默认值在 Definition 中使用归一化 JSON
字符串；实际 Python 函数可以保留对应 Torch 对象默认值。

### 3.3 输出、mutation 与 alias

`outputs` 协议必须存在：

- 无返回值算子使用 `[]`，函数必须返回 `None` 或空 tuple/list；
- 一个逻辑输出时，整个 Python 返回对象归到该名称；
- 多个逻辑输出时，函数必须返回等长 tuple/list。

`effects.mutates` 列出允许修改的参数；未列出的输入会分别检查为未修改。
`effects.returns_alias_of` 将逻辑输出映射到必须共享 storage 的输入，它检查真实 alias，
不是数值相等。原地算子通常同时声明 mutation 和 return alias。

当前 schema 只表达静态 effects。无法稳定写成一个公共契约时，应调整算子边界或记录
为暂不支持，不能用不准确的 effects 换取测试通过。

## 4. `oracle.py`：唯一受信运行资产

### 4.1 `REFERENCE_DEVICE`

oracle 顶层必须恰好声明一次字符串常量：

```python
REFERENCE_DEVICE = "target"
```

- `"target"`：reference 在目标设备执行；标准性能算子必须使用它；
- `"cpu"`：只适合 correctness-only reference。CPU reference 不能拥有 timing
  workload，因为它无法作为同环境、同计时器的 baseline。

该字段只出现在 `oracle.py`，不能同时写入 Definition。

### 4.2 Primary reference

oracle 支持：

```python
def run(...): ...
def correctness_run(...): ...
def timing_run(...): ...
```

解析规则固定为：

```text
correctness reference = correctness_run ?? run
timing reference      = timing_run ?? run
```

- 两个 phase 语义相同时只提供一个 `run`；
- correctness 需要高精度、确定性或特殊 mutation，而 timing 必须复现原 API 时，
  分别提供两个 phase override；
- 只覆盖一个 phase 的特殊交付，可以只提供对应入口；
- 同时拥有两个 phase 且没有共享 `run` 时，两个 override 都必须提供。

所有存在的 reference 入口都必须与 Definition 签名完全一致，包括 positional-only、
keyword-only、`*args` 和默认值。禁止拆成 `correctness_reference.py`、
`timing_reference.py` 或 `torch_reference.py`。

split reference 示例：

```python
import torch

REFERENCE_DEVICE = "target"


def correctness_run(self, mat1, mat2, *, beta=1, alpha=1):
    result = torch.addmm(
        self.detach().to(torch.float64),
        mat1.detach().to(torch.float64),
        mat2.detach().to(torch.float64),
        beta=beta,
        alpha=alpha,
    )
    return self.copy_(result.to(self.dtype))


def timing_run(self, mat1, mat2, *, beta=1, alpha=1):
    return self.addmm_(mat1, mat2, beta=beta, alpha=alpha)
```

交付物只定义可执行 reference，不提供外部 reference latency 或 speedup metadata。

### 4.3 `gen_inputs`

基础 recipe 无法表达 column-major、非连续 view、共享 storage、相互依赖的 Tensor、
Tensor list、变长 tuple、Generator 或框架对象时，可以提供：

```python
def gen_inputs(ctx, device):
    ...
```

签名必须精确为 `(ctx, device)`：

```python
ctx == {
    "name": "<workload-name>",
    "inputs": { ... },
    "seed": 42,
}
```

`device` 是当前执行使用的 `torch.device`。hook 可以返回 `None`
表示完全使用基础 recipe，也可以返回参数名到实际值的 mapping，只覆盖它负责生成的
参数。mapping 不能含 Definition 之外的参数；所有 required 参数最终都必须物化。

`ctx` 不包含独立 phase 字段；需要区分来源 case 时，应使用稳定 workload name 或
`ctx["inputs"]` 中的显式 context，不能依赖调用顺序猜测 phase。

hook 必须在相同 context、seed 与 device 下保持确定性，不能依赖跨调用全局状态。

例如只构造 column-major `mat2`：

```python
def gen_inputs(ctx, device):
    spec = ctx["inputs"].get("mat2")
    if not isinstance(spec, dict) or spec.get("type") != "custom":
        return None
    if spec.get("generator_params", {}).get("kind") != "column_major":
        raise ValueError("unsupported custom mat2 recipe")
    k, n = spec["shape"]
    dtype = getattr(torch, spec["dtype"])
    return {
        "mat2": torch.randn((n, k), dtype=dtype, device=device).t()
    }
```

普通 contiguous random Tensor、scalar 和 JSON literal 不需要 `gen_inputs`，应直接写
workload，避免无意义的自定义 Python。

### 4.4 `valid`

默认 correctness 会递归比较 PyTree 结构、leaf 类型、Tensor shape/dtype 和数值，
同时检查 mutation 与 alias。随机或统计类算子无法逐值比较时，可以提供：

```python
def valid(ref_outputs, sol_outputs, inputs, ctx):
    ...
```

签名必须精确为上述四个参数。传入值均已移动到 CPU：

- `ref_outputs`、`sol_outputs`：将函数返回值包装成 list 后得到的 PyTree；
- `inputs`：按 Definition 参数名索引的 candidate 输入 mapping；
- `ctx`：当前 workload context。

返回值可以是 bool，也可以是：

```python
{
    "passed": True,
    "message": "",
    "metrics": {"matched_ratio": 1.0},
}
```

声明 `valid` 后，它负责 correctness 返回值和已声明 mutation 的值判断；基础校验仍先检查
PyTree 结构、leaf 类型、Tensor shape/dtype、未声明 mutation 与 return alias。

只有来源 correctness 明确不遵循这些返回结构规则时，才允许同时声明：

```python
VALID_OWNS_RETURN_CONTRACT = True
```

此时 `valid` 必须完整检查返回值结构、leaf、shape/dtype 和数值。该开关不移交
未声明 mutation 或 alias 检查，并且没有 `valid` 时禁止设置为 `True`。

### 4.5 Torch fallback

目标芯片缺少给定 API，或 primary 的部分 dtype/参数组合不受支持时，可以提供纯
Torch fallback：

```python
def torch_run(...): ...
```

`torch_run` 是 correctness/timing 共用的整轮 fallback，签名必须与 Definition 一致。
fallback 按整套 workload 选择：

1. smoke 全部 primary correctness/timing workload；
2. 任意 primary workload 失败时，从头 smoke 全部 `torch_run` workload；
3. fallback 全部成功后，整轮统一使用 fallback；
4. 两套 reference 都失败时，验证失败。

不能按 workload 混用 primary 与 fallback。

fallback 需要不同复杂输入或 validator 时，分别提供：

```python
def torch_gen_inputs(ctx, device): ...
def torch_valid(ref_outputs, sol_outputs, inputs, ctx): ...
TORCH_VALID_OWNS_RETURN_CONTRACT = False
```

进入 fallback 后不会自动复用 primary 的 `gen_inputs` 和 `valid`。普通 recipe 不需要
`torch_gen_inputs`；自定义输入则必须显式提供 fallback 版本。只有设置
`TORCH_VALID_OWNS_RETURN_CONTRACT=True` 时才强制要求 `torch_valid`。

不需要提供逐芯片 capability 列表。目标环境运行验证会实际 smoke 全部 reference
workload，以确认 API 与 dtype 能力。

### 4.6 算子私有运行资产

oracle 依赖额外 Python 文件、厂商 `.so`、权重/查表数据或配置时，将它们全部放在当前
算子的 `assets/` 子目录：

```text
<operator>/
├── definition.json
├── oracle.py
├── correctness.jsonl
├── timing.jsonl
└── assets/
    ├── helper.py
    ├── libmy_op.so
    └── config.json
```

这些文件随 oracle 一起加载。规则如下：

- oracle 的额外运行依赖只能放在 `assets/`，非运行的数据集归档约定见 5.1；
- `assets/` 可以有子目录和二进制普通文件，但整个算子目录禁止符号链接；
- oracle 导入时会临时暴露算子目录和 `assets/`，因此
  helper 应在模块顶层导入；不同算子不得互相导入私有资产；
- 使用 `ctypes`/扩展加载 `.so` 时从 `Path(__file__).resolve().parent / "assets"`
  解析，禁止写目标机绝对路径或依赖当前工作目录；
- 二进制资产必须记录构建源码/revision、目标架构、Python/Torch/厂商 ABI、校验和和
  许可证。目标机仍须自行具备系统级驱动与运行时，不应把整套运行时放进交付包。

例如：

```python
from pathlib import Path
import ctypes

_ASSETS = Path(__file__).resolve().parent / "assets"
_LIB = ctypes.CDLL(str(_ASSETS / "libmy_op.so"))
```

`assets/` 只解决 oracle 的可复现依赖，不放宽安全边界；只接收可信来源的 Python 和
二进制文件。

## 5. Workload JSONL

### 5.1 文件与身份

每个非空行是一个独立 Workload：

```json
{
  "name": "addmm-fp16-m128-k64-n256-correctness",
  "inputs": {
    "self": {"type": "random", "shape": [128, 256], "dtype": "float16"},
    "mat1": {"type": "random", "shape": [128, 64], "dtype": "float16"},
    "mat2": {"type": "random", "shape": [64, 256], "dtype": "float16"},
    "beta": {"type": "scalar", "value": 1},
    "alpha": {"type": "scalar", "value": 1}
  },
  "seed": 42
}
```

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| `name` | 格式必须 | 非空、稳定，并在交付包中唯一。 |
| `inputs` | 格式必须 | 参数 recipe 和供 hook 使用的 JSON context。 |
| `seed` | 可选 | 默认 `0`，建议显式固定；范围为 `0..2^63-1`。 |
| `tolerance` | 可选 | 只覆盖当前 correctness workload 的比较策略。 |

`Workload.name` 会出现在验证结果中，因此必须稳定且可读。

数据集维护者如需保留采样前的完整集合，可以使用 `correctness_full.jsonl` 和
`timing_full.jsonl`；它们不是标准交付要求，也不会参与验证或评测。

### 5.2 基础 recipe

| recipe | 必要字段 | 行为 |
| --- | --- | --- |
| `random` | `shape` list、`dtype` string | 生成随机 Tensor；`shape=[]` 表示 0-D Tensor。 |
| `scalar` | `value` | 复制 JSON scalar/container 值。 |
| `literal` | `value` | 与 scalar 相同，用于强调它不是随机输入。 |
| `custom` | 自定义 JSON | 基础 runner 不物化，必须由输入 hook 处理。 |

不匹配上述 recipe 的普通 JSON 值会作为 literal/context 保留。若 key 是 Definition
参数名，它可以直接作为参数值；若不是参数名，只会通过 `ctx["inputs"]` 提供给 hook。
为便于评审，直接参数值仍建议显式使用 `scalar` 或 `literal`。

`random` 可选 `device`：

- 缺省或 `"cpu"`：先在 CPU 生成 base，再分别克隆到 reference/candidate 设备；
- `"target"`：在目标设备直接生成，用于复现来源 benchmark 的 device
  generator 路径。

`device` 不能写物理卡号。普通输入优先使用 CPU base；只有来源测试明确依赖
target-side generation 时才用 `target`。可选参数可以从 `inputs` 省略，required
参数必须最终物化。

需要保留来源 benchmark 的随机输入约束时，`random` 还支持下列可选字段：

- `distribution`：`normal`（默认）、`uniform` 或 `integer`；`uniform` 可给出
  `low/high`（默认 `0/1`），`integer` 必须给出整数 `low/high`，上界不包含；
- `source_dtype`：随机生成和变换阶段使用的 dtype，最终再转换为 `dtype`；
- `transforms`：按顺序执行的声明式变换。当前支持 `cast`、`multiply`、`divide`、
  `rdivide`、`add`、`subtract`、`rsubtract`、`transpose`、`symmetrize_sum`、`triu`、
  `tril`、`softmax` 和 `multiply_random`。

`multiply_random` 使用嵌套的 `input` random recipe；`before=true` 表示先生成该随机值，
用于保留原输入函数的 RNG 调用顺序。这些字段适合三角矩阵、对称矩阵、类别标签和概率
分布等可声明约束；仍无法表达的相互依赖、layout 或对象输入才放入 `gen_inputs`。

### 5.3 复杂输入与 `*tensors`

recipe 不递归解释 list 内部的 Tensor recipe。Tensor list、变长 tuple 或共享 storage
必须由 hook 一次构造。例如 Definition 声明：

```json
{
  "name": "tensors",
  "kind": "var_positional",
  "required": true,
  "type_hint": "Tensor[]"
}
```

Workload 只保存 JSON context：

```json
{
  "name": "broadcast-three-fp16",
  "inputs": {
    "tensor_specs": [
      {"shape": [2, 1], "dtype": "float16"},
      {"shape": [1, 3], "dtype": "float16"},
      {"shape": [2, 3], "dtype": "float16"}
    ]
  },
  "seed": 42
}
```

hook 返回真实参数：

```python
def gen_inputs(ctx, device):
    tensors = tuple(
        torch.randn(
            spec["shape"],
            dtype=getattr(torch, spec["dtype"]),
            device=device,
        )
        for spec in ctx["inputs"]["tensor_specs"]
    )
    return {"tensors": tensors}
```

运行器会把该 list/tuple 展开成 positional arguments；非 list/tuple 的
`var_positional` 值会被拒绝。

### 5.4 文件型输入和期望输出

v6.2 继承 v6.1 的文件型 Workload，内置两个顶层可选字段：

- `input_path`：从一个 safetensors 文件按参数名读取输入 Tensor；
- `output_path`：从一个 safetensors 文件按 `Definition.outputs` 名称读取 correctness
  golden Tensor，不执行该 workload 的 correctness reference。

这两个字段直接属于 Workload，不需要在 `oracle.py` 中编写 `torch.load`、`gen_inputs`
或 `valid` 来模拟。普通 scalar/literal 参数仍由 `inputs` recipe 提供；从文件读取的参数
使用 `type: "safetensor"` 标记：

```json
{
  "name": "addmm_-real-fp16-4096",
  "input_path": "/data/dumps/addmm_/fp16-4096-inputs.safetensors",
  "output_path": "/data/dumps/addmm_/fp16-4096-golden.safetensors",
  "inputs": {
    "self": {"type": "safetensor", "shape": [4096, 4096], "dtype": "float16"},
    "mat1": {"type": "safetensor", "shape": [4096, 4096], "dtype": "float16"},
    "mat2": {"type": "safetensor", "shape": [4096, 4096], "dtype": "float16"},
    "beta": {"type": "scalar", "value": 1.0},
    "alpha": {"type": "scalar", "value": 1.0}
  },
  "seed": 0
}
```

输入文件的 Tensor key 必须与 Definition 参数名一致；golden 文件的 key 必须与
`Definition.outputs` 一致。单输出通常为 `out`，多输出按 Definition 中声明的名称保存：

```python
from safetensors.torch import save_file

save_file(
    {"self": self_tensor, "mat1": mat1_tensor, "mat2": mat2_tensor},
    "/data/dumps/addmm_/fp16-4096-inputs.safetensors",
)
save_file(
    {"out": golden_output},
    "/data/dumps/addmm_/fp16-4096-golden.safetensors",
)
```

文件路径必须是目标运行环境可读的绝对路径。`shape`/`dtype` 是交付说明，以文件内实际
Tensor 为准；运行时会先在 CPU 打开文件，再把输入 Tensor 移到本次分配的设备。

`output_path` 只允许出现在 correctness workload。v6.2 的 timing workload 即使使用
`input_path`，reference 和 candidate 也仍由 KGS 在同一目标环境现场计时；不从
safetensors metadata 或其他外部文件读取 reference latency。对于原地算子，只有所有
mutation 都通过 `returns_alias_of` 暴露在输出中时，golden output 才能完整表达其结果；
否则不能使用 `output_path`，必须运行 correctness reference。

若 safetensors 随算子交付，可以放在该算子的 `assets/` 中；部署到最终环境后，
Workload 中仍填写它在运行环境内的绝对路径。`.so`、配置文件以及不能用 safetensors
表达的复杂对象继续按第 4.6 节由 `oracle.py` 从 `assets/` 使用。

### 5.5 容差

```json
{
  "tolerance": {
    "rtol": 0.001,
    "atol": 0.0001,
    "atol_scale": 2.0,
    "required_matched_ratio": 0.999,
    "equal_nan": true
  }
}
```

- `rtol`、`atol` 缺省时使用内置 dtype 默认值；
- `atol_scale` 缺省为 `1.0`；
- `required_matched_ratio` 缺省为 `1.0`；
- `equal_nan` 缺省为 `false`；
- 整数和 bool 默认要求精确相等。

容差必须忠实复现来源 correctness 规则，不能用来掩盖 reference/candidate 语义差异。

### 5.6 correctness 与 timing case

correctness workload 应覆盖支持的 dtype、shape、布局、默认值、关键参数组合、返回
PyTree、mutation、alias、空 Tensor 和标量 Tensor等边界，并覆盖 timing 中所有会
改变语义的参数维度。

timing workload 应忠实来自权威 benchmark。v6.2 timing phase 只要求
reference/candidate 可执行并产生有效 latency，不比较数值、mutation 或 alias；任何
只出现在 timing 的语义维度都没有 correctness 背书。

native workload 没有 `skip` 字段。不要为每台机器复制一套几乎相同的 workload：

- 主体交付保存统一来源 case；
- 厂商 API 缺失或 dtype 不支持时，在验证结果中记录；
- 只有 benchmark 语义本身不同，才建立独立交付集合。

## 6. 明确不需要或禁止提供的内容

| 内容 | 结论 | 原因 |
| --- | --- | --- |
| 外部 reference latency/speedup | 不需要 | 交付内容只定义可执行 reference，不接受外部测量值作为真值。 |
| `implementation_reference` | 不进入 oracle/schema | 原始实现路径只能作为非执行 provenance。 |
| Definition 中的 `reference_device` | 禁止 | 唯一真值是 oracle 的 `REFERENCE_DEVICE`。 |
| 三个拆分 reference `.py` | 禁止 | correctness/timing/torch 统一在 `oracle.py`。 |
| 同语义的两个 phase 函数副本 | 不需要 | 只提供共享 `run`。 |
| 每个算子的 `gen_inputs` | 不需要 | 普通 recipe 已足够。 |
| 强制类型 DSL | 不需要 | `type_hint` 非权威，复杂类型由输入构造保证。 |
| 逐机器重复 workload | 通常不需要 | 能力差异记录在验证结果中，不复制主体数据。 |
| pytest path/marker in Definition | 禁止 | native Definition 是纯 ABI。 |
| 已优化 kernel | 不需要 | 交付目标是可验证的 ABI、oracle 和 workload。 |
| Workload `skip`、expected exception、条件 effects | 当前不支持 | 不能自创字段或改变 reference 语义绕过。 |

稳定、可独立调用的 backward API 可以像普通算子一样定义。如果 backward-only 测试
只能依赖 forward 产生的内部 autograd graph，且没有稳定公共 callable ABI，则当前
不应强行抽取为 v6.2 Definition。

## 7. 本地验证与交付证据

### 7.1 静态验证

独立验证器只使用 Python 标准库，不依赖 KGS、Pydantic、Torch 或 Triton。交付包可以
包含一个或多个算子目录：

```bash
python3 validate_v62_native_catalog.py \
  <delivery-root> \
  --delivery \
  --mode standard \
  --output validation-static.json
```

`standard` 模式检查 Definition、oracle 静态 ABI、两个 phase、recipe、workload name
和私有 assets。退出码 `0` 表示通过，`1` 表示失败。

### 7.2 目标环境运行验证

在实际交付环境中运行全部 oracle workload：

```bash
python3 validate_v62_native_catalog.py \
  <delivery-root> \
  --delivery \
  --mode standard \
  --runtime \
  --target-device <torch-device，例如 cuda:0> \
  --runtime-timeout 300 \
  --output validation-runtime.json
```

运行验证会导入 `oracle.py` 和 `assets/`，校验所有 hook ABI，物化并调用全部 workload，
执行自定义 validator smoke，并在 target 调用后同步设备。若 oracle 依赖外部源码，增加
`--framework-root <checkout>`。目标环境只需具备 oracle 自身依赖，不需要安装 KGS。

### 7.3 来源与证据

交付时同时提供：

- 来源仓库、完整 commit 和 correctness/benchmark 文件；
- 抽取工具与 commit，或人工转换说明；
- 原始参数化到 workload 的数量与映射；
- reference、容差、mutation/alias、布局和 seed 的来源；
- 私有 assets 的来源、构建 revision、ABI、校验和与许可证；
- 没有纳入的 case、skip 或 backward-only 测试及原因；
- 目标芯片、容器、Python、Torch 和厂商运行时版本；
- 静态及运行验证生成的 JSON 报告。

来源同时包含 correctness test 和 benchmark 时，应分别产生两个 JSONL，不能从一个
列表推断二者相同。

## 8. 提交前检查表

### Definition

- [ ] 参数顺序、name、kind、required/default 与真实 API 完全一致。
- [ ] `*args` 使用 `var_positional`，没有用 `**kwargs` 掩盖 ABI。
- [ ] outputs、mutates 和 returns_alias_of 覆盖真实契约。
- [ ] `type_hint` 只作为说明，没有承担运行时类型逻辑。
- [ ] Definition 不含 reference、workload、设备或测试路径。

### Oracle

- [ ] `REFERENCE_DEVICE` 恰好一次；有 timing workload 时为 `target`。
- [ ] 每个存在 workload 的 phase 都能解析到 ABI 一致的 primary entrypoint。
- [ ] 同语义 phase 只使用共享 `run`。
- [ ] `gen_inputs` 只在基础 recipe 不足时存在，且确定、无未知参数。
- [ ] `valid`/return-contract 开关完整复现来源断言。
- [ ] `torch_run` 是整轮 fallback；必要时提供独立 torch hooks。
- [ ] 没有外部 latency、机器路径或 `implementation_reference` 混入运行源码。
- [ ] oracle 私有文件只在当前算子的 `assets/`，没有符号链接或机器绝对路径。
- [ ] `.so` 等二进制记录了来源、构建 ABI、校验和与许可证。

### Workload 与验收

- [ ] correctness/timing 分别来自各自权威来源，名称全局唯一且稳定。
- [ ] correctness 覆盖 timing 中所有会影响语义的参数维度。
- [ ] seed、布局、target-side generation 和容差均有来源依据。
- [ ] 文件型 Tensor 使用顶层 `input_path`/`output_path` 和 `type: "safetensor"`，key
      与参数名/输出名一致，目标环境中的绝对路径可读。
- [ ] `output_path` 只用于 correctness；timing 没有外部 reference latency。
- [ ] 没有自创 skip、expected-exception 或厂商条件字段。
- [ ] 独立验证器 `--mode standard` 和目标环境 `--runtime` 均通过并保存 JSON。
- [ ] 来源 revision、转换说明、运行环境和未纳入 case 均已记录。
