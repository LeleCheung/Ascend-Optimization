# v6.2 Profiling 合并关键决策

本文记录将 `fix/profiling-enhanced-main-integration` 的功能迁移到 KernelGen
Server v6.2 时已经确认的设计决策。它是合并期间的权威决策记录；尚未确认的内容不应
在实现中提前假设。

## 基线与来源

- 目标基线：`origin/main` 的 v6.2 架构，合并分析基线为 `aac60cb`（tag
  `v6.2.0`）。
- 原待迁移分支：`fix/profiling-enhanced-main-integration`，PR #16 的分析基线为
  `ba86a93`。
- 新增待迁移版本：[PR #17](https://gitee.com/BaaiAC/kernelgen_server/pulls/17)，
  head 为 `6f767e1`，它直接基于 `ba86a93`，新增动态环境 metadata 探测并撤销
  PR #16 的设备型号规范化。后续 `/status` 设计以该版本为代码参考。
- “当前 v6.2”表示已经存在于目标基线的行为。
- “待迁移分支”表示只存在于旧 profiling 分支的行为。
- “本次决定”表示两边都没有完全实现、由本次合并新确定的方案。

总原则是以 v6.2 Schema、Catalog 和 evaluator 生命周期为唯一语义基线。旧分支提供
profiling 功能和厂商实现，但不恢复 v5 的公开请求、输入生成或 Catalog 执行接口。

## 已确认决策

### 1. Profiling 请求继续使用 v6.2 binding

来源：当前 v6.2，最初由 `79fbff4 feat: add v6 evaluation adapters` 引入。

状态：当前 v6.2 已实现；合并时保持。

决定：公开请求继续使用 `EvaluatorBinding + case_id + candidate`。Server 根据 binding
解析可信 Catalog、Definition、Workload、oracle 和 evaluator 类型，再由 evaluator
adapter 构造 `ProfileCommand`。

原因：客户端不应重新上传可能与 Catalog 不一致的 Definition 和 Workload；Native 与
FlagGems 也需要不同的命令构造方式，但应共享同一个公开请求和结果模型。

### 2. ProfileTarget 只作为 Native runner 内部快照

来源：`ProfileTarget` 早于 v6.2；当前 v6.2 将其保留为 Native adapter 写入
`target.json` 的内部模型。待迁移分支仍把它作为公开 `ProfileRequest` 的主体并直接传给
`profiler.profile()`。

状态：当前 v6.2 已实现；合并时保持。

决定：不恢复公开 `ProfileTarget`。它只在 Native adapter 与隔离 profiling runner
之间传递一次已绑定的 Definition、timing Workload、candidate、backend 和 oracle
路径。厂商 profiler 和 FlagGems adapter 不解释该模型。

原因：这样可以固定可信 Catalog case，支持 Server 本地的 `oracle.py`、`assets/` 和
文件型 Workload，同时避免厂商 profiler 与 v6.2 Schema 耦合。

### 3. 厂商 profiler 只接受 ProfileCommand

来源：`profile_command(ProfileCommand)` 来自当前 v6.2 的 `79fbff4`；
`profile(ProfileTarget)` 是待迁移分支沿用的旧接口。

状态：已实现；10 个 backend 均只通过 `ProfileCommand` 进入公共生命周期。

决定：统一只保留 `profile_command()`。迁移各厂商 profiler 时保留其工具调用、进程
清理、报告解析和 artifact 逻辑，但入口改为包裹 adapter 已构造的 `argv/cwd/env`。

原因：厂商 profiler 只需要理解厂商工具，不应生成 Native 输入或理解 FlagGems
pytest。这样两个 evaluator 可以执行不同内层命令，同时复用同一个 profiler。

### 4. Profiling level 正式只公布两级

来源：待迁移分支的
`d8167c4 refactor(profiling): standardize two-level protocol`。

状态：已实现并通过 Schema 回归测试。

决定：正式 Schema、OpenAPI、`/status`、序列化结果和普通用户文档只公布
`metrics`、`instruction`。旧客户端提交的 `source` 仍在输入解析边界接受，并立即单向
规范化为 `instruction`；后续内部状态和输出不再传播该旧值。

原因：源码映射、编译器 IR 和指令列表都属于深度代码证据，继续维护独立的第三个公开
level 会让不同厂商产生含义不一致的结果。

### 5. 执行前严格检查 profiler level

来源：待迁移分支的 `d8167c4`。

状态：已实现并通过执行顺序回归测试。

决定：`ProfileService` 在构造和执行命令前检查请求 level 是否在
`profiler.levels()` 中。不支持时返回结构化 `unsupported`，不执行命令，也不自动降级。

原因：缺失 instruction 工具或证据时，退化成 metrics 会把不完整结果伪装成请求成功。

### 6. 保留 normalize_options

来源：待迁移分支的 `d8167c4`。

状态：已实现并通过 effective options 传播测试。

决定：执行顺序固定为：请求 options → `profiler.normalize_options()` → evaluator
adapter 使用 effective options 构造 `ProfileCommand` → profiler 执行。结果记录实际
生效的 options，并附带调整 warning。没有特殊约束的 profiler 原样返回 options。

原因：厂商约束必须在 adapter 生成 warmup、iterations 和 timeout 参数之前生效，避免
命令实际值与结果记录不一致。每个厂商允许的具体调整仍需逐项确认。

### 7. 保留 hardware 结果

来源：当前 v6.2 的 `ProfileResult` 已有可选 `hardware` 字段；待迁移分支进一步让
`BackendProfileResult` 填充并由 `ProfileService` 传播该字段。

状态：已实现；backend 结果优先，缺省使用 Server 启动时的环境快照。

决定：保留并迁移完整传播链。无法获取时返回空字典，不影响 profiling 状态。

原因：设备型号、架构等信息有助于复现实验，但不参与 correctness、latency 或 speedup
结论。

### 8. 删除 candidate 调用次数检查

来源：当前 v6.2 的 `79fbff4`，最初用于验证 FlagGems `--profile-only` 是否执行了
`warmup + iterations` 次 candidate；待迁移分支没有该机制。

状态：已实现；旧计数字段、文件和检查均已删除。

决定：删除 `ProfileCommand.expected_call_count_path`、`expected_call_count`、FlagGems
计数文件、NCU/Ascend 检查和相关测试。

原因：该证据只能证明 Python candidate 入口的调用次数，不能证明目标 GPU kernel 被
profiler 采集，也不能证明没有 framework fallback。进程退出状态和必要 profiler
report 是否生成继续作为基础成功条件。

### 9. NCU 使用 CUDA profiler API 控制采集边界

来源：`cudaProfilerStart/Stop + --profile-from-start off` 来自当前 v6.2；待迁移分支
使用 NVTX range 过滤。

状态：当前 v6.2 已实现；迁移 NCU 增强功能时保持。

决定：以 `cudaProfilerStart/Stop` 为唯一权威采集边界，暂不使用 NVTX 过滤。顺序为：
输入生成和 warmup → device synchronize → profiler start → 正式 candidate 调用 →
device synchronize → profiler stop。

原因：KGS Native 只有一个明确的正式采集窗口，CUDA profiler API 已能排除输入生成和
warmup；不额外引入 range 名称、嵌套和线程作用域失败点。

### 10. NCU 正式 iterations 规范化为 1

来源：待迁移分支的 NCU `normalize_options()` 行为。

状态：已实现并通过 options 规范化测试。

决定：仅对 NCU 将大于 1 的正式 iterations 规范化为 1，warmup 保持请求值，结果记录
`iterations=1` 并产生 warning。NCU 自己的 kernel replay 不算 candidate 的额外调用。

原因：NCU 可能为了收集性能计数器内部重放 kernel；再让应用重复大量正式迭代会显著
增加开销，并使报告包含不必要的重复 invocation。

### 11. 暂不继续拆分 Native evaluator adapter

来源：Native evaluator adapter 来自当前 v6.2；“继续压薄”是本次评估提出的新建议。

状态：已确认不执行额外拆分。

决定：当前不为减少类代码行数而移动 fingerprint、manifest 或 profile command 构造
逻辑。它继续负责 `inspect/preflight/evaluate/build_profile_command`，但不得复制
correctness、timing 或 Workload 执行语义。

原因：这些逻辑仍属于 Native evaluator 到公共生命周期的真实适配职责；现在拆出多个
helper 只会移动复杂度，并增加 profiling 迁移期间的改动面。

### 12. operator_adapter.py 改名为 workload_runtime.py

来源：本次决定；实现提交为
`0961bee refactor: rename native workload runtime module`。

状态：已实现并通过 host 测试。

决定：模块和对应测试改名，Engine、profiling runner 和设计文档同步更新。
`loader.py` 中表示已加载 oracle hooks 的 `OperatorAdapter/load_operator_adapter` 暂不
改名。

原因：该模块实际负责 Workload 输入物化、Tensor 搬运和 Python ABI 调用绑定，不是
evaluator adapter。新名称减少与 Native/FlagGems evaluator adapter 的概念混淆。

### 13. 旧 Catalog 必须迁移为 v6.2

来源：本次合并总原则。待迁移分支仍包含 active v5 Catalog；当前 v6.2 明确不执行
v5 Catalog。

状态：已按第 28 项完成两套 Catalog 的转换、静态校验和 NVIDIA 全量 oracle 运行验证。

决定：需要保留的旧 Catalog 全部转换为 v6.2 Schema 和目录契约后才能进入 active
`data/`。未经转换的内容不得恢复为可运行 Catalog；仅用于溯源时放入 `data/.old/`。

原因：恢复 v5 运行路径会形成第二套 Definition、Workload 和 oracle 语义，并破坏
v6.2 Server 的单一协议边界。

### 14. Candidate 源码由 evaluator adapter 稳定物化

来源：当前 v6.2 由 evaluator adapter 构造 `ProfileCommand`，但 Native runner 仍由
loader 临时物化 candidate；FlagGems adapter 已创建稳定的 `target/candidate/`。
待迁移分支的 `eed723f feat: enhance Iluvatar IXKN profiling` 新增
`--implementation-source-dir`，NCU profiler 也会自行将源码写入 artifact 目录。

状态：已实现并通过稳定源码目录与 ABI 回归测试。

决定：保持 v6.2 的职责边界，由 evaluator adapter 将 candidate 源码物化到 profiling
artifact 下的稳定目录，并在内部 `ProfileCommand` 中记录 `source_roots`。Native runner
按 adapter 构造的命令从该目录加载 candidate；FlagGems 复用其已有 candidate 目录。
需要源码映射的 vendor profiler 只读取 `source_roots`，不得解析 `Implementation` 或
重新写入源码。`source_roots` 不进入公开 profiling 请求。

原因：candidate 的文件布局和执行命令属于 evaluator 的职责；profiler 只应配置厂商
采集工具。稳定路径同时满足 NCU 等工具的源码导入需求，并避免 adapter、runner 和
profiler 三处重复物化源码。

### 15. Native runner 按 backend 固化采集边界

来源：当前 v6.2 的 Native runner 已固定使用 CUDA
`cudaProfilerStart/Stop`；待迁移分支分别在 `96097fb`、`5986391`、`3d09a01`、
`b9576e9`、`eed723f` 和 `baa97e6` 中加入 Cambricon、MetaX、Enflame、T-Head、
Iluvatar 和 Kunlunxin 的 runner 控制逻辑，但由各 vendor profiler 通过不同命令参数
选择。仅处理 Native、暂不扩展 FlagGems/pytest 是本次决定。

状态：已实现；Native runner 已覆盖 10 个 backend 的固定控制方式。

决定：不引入动态 `CaptureSpec`，也不让 vendor profiler 向内层命令追加
`--profiler-control`、`--profile-window` 等 runner 专用参数。Native profiling runner
根据 `ProfileTarget.expected_backend` 选择代码中固定的采集控制方式，在 warmup 和同步
之后开始采集，在正式 iterations 和同步之后停止采集。需要运行时 API 的 backend 调用
对应厂商 Start/Stop；需要时间窗口的 backend 输出固定格式的时间戳；明确使用全进程
采集的 backend 使用显式 no-op 控制项。NCU 继续使用已确认的 CUDA Start/Stop，不恢复
NVTX 过滤。

本轮迁移不为 FlagGems 的 pytest `--profile-only` 路径增加多厂商采集控制，也不以该
路径作为 Native profiler 迁移的验收范围；其现有行为保持不变，后续单独设计和验证。
`ProfileCommand` 因此不增加 capture 协商字段。

原因：当前一个 backend 只注册一套默认 profiler，Native runner 也已经持有可信 backend，
再增加 profiler、service 与 evaluator adapter 之间的动态协商只会重复传递固定信息。
同时明确排除 pytest 路径，避免为尚未设计的第二种执行器提前扩大公共内部接口。

### 16. 保留 Native runner 完成标记

来源：待迁移分支的 `eed723f feat: enhance Iluvatar IXKN profiling` 引入
`runner-completed`，用于识别 Iluvatar 外层工具返回成功但内层 runner 未正常结束的
情况。当前 v6.2 没有该机制。

状态：已实现并通过完成标记成功、缺失和多阶段复用测试。

决定：在内部 `ProfileCommand` 增加可选 `completion_marker_path`。Native evaluator
adapter 为 profiling runner 设置稳定的完成标记路径；每次执行内层命令前删除旧标记，
runner 只有在正式 iterations、设备同步和采集停止全部完成后才写入标记。vendor
profiler 只有在外层进程成功、必要报告有效且完成标记存在时才能返回 `completed`。本轮不
要求 FlagGems/pytest 生成该标记。

该标记只证明 runner 正常执行到末尾，不记录或校验 candidate 调用次数；第 8 项决定
删除的 `expected_call_count_path` 和 `expected_call_count` 仍不恢复。

原因：部分 vendor 工具不会可靠传播其子进程退出状态，并可能留下形式上存在但不完整的
报告。完成标记提供最小的内层进程完成性证据，不试图把 Python 入口调用次数误当作目标
kernel 已被采集的证据。

### 17. 统一清理超时的 profiler 进程树

来源：待迁移分支的 `43192d8 fix: bound and clean up ncu profiling` 为 NCU 引入
独立进程组、分级终止和子进程回收；后续 Ascend、MThreads、Cambricon、MetaX、
Iluvatar、Kunlunxin 和 Enflame 等 profiler 使用了相同思路。当前 v6.2 的
`/profile` 在线程池中直接调用 `ProfileService`，不经过 Eval 的隔离 worker，因此
Eval 的进程组清理不覆盖 profiling。

状态：已实现；Eval、Profile、Debug 复用公共进程树终止模块并通过回归测试。

决定：保留进程树清理能力，但不迁移各 vendor 文件内重复的 subprocess helper。提取
公共的上层进程树终止策略：检查进程树、发送 `SIGTERM`、等待有限 grace period、仍未
退出时发送 `SIGKILL`，最后等待并回收并返回清理结果。`multiprocessing.Process` 和
`subprocess.Popen` 通过底层 handle 分别适配 `is_alive/join/exitcode` 与
`poll/wait/communicate/returncode` 的接口差异；Eval、Profile 和 Debug 共同调用同一
终止策略，不再分别维护信号顺序和超时规则。

各业务仍负责自己的进程启动、正常等待和输出收集：Eval/Preflight 创建 Python 隔离
worker，Profile/Debug 启动外部命令，公共 profiling 执行工具负责 `Popen` 的 deadline
和 stdout/stderr。所有需要进程树清理的子进程都必须用 `start_new_session=True` 或等价
方式建立明确的独立进程组。只有清理完成后才能返回结果并释放 device slot。

进程清理必须始终使用本次明确启动的子进程 PID/进程组 ID，不得使用宽泛进程名、环境
变量、shell glob 或 Server 自身进程组作为终止目标。非 POSIX 平台使用能力等价的直接
子进程终止退化路径。

原因：`subprocess.run(timeout=...)` 不能可靠清理 profiler 拉起的 runner、编译器和
厂商子进程；残留进程可能继续占用设备，使 Server 已释放的 slot 与真实设备状态不一致。
公共实现还能统一超时语义并减少不同 vendor 清理行为的偏差。

### 18. 整个 profiling 请求共享单一 deadline

来源：待迁移分支的 Cambricon、MetaX、Enflame 和 Iluvatar 等多阶段 profiler 使用
`time.monotonic() + timeout_sec` 形成绝对 deadline，并把剩余时间传给采集、导出和
解析子命令。当前 v6.2 通常为每个 subprocess 分别提供完整 `timeout_sec`。

状态：已实现并通过多阶段与 postprocess 超时回归测试。

决定：`ProfileService` 在一次请求开始时计算唯一的 monotonic deadline，并将其沿内部
链路传给 vendor profiler 和公共进程执行工具。每个外部命令只获得
`deadline - time.monotonic()` 的剩余时间；deadline 到期后终止当前进程树，不再启动
后续采集、导出、反汇编或源码映射阶段。adapter 构造完命令后、每个新阶段开始前都必须
检查剩余预算。

请求未在 deadline 内生成所请求 level 的完整证据时不能返回 `completed` 或静默降级。
到期前已经生成且通过安全检查的日志和 artifact 可以保留。第 17 项规定的 `SIGTERM`、
grace period、`SIGKILL` 和回收过程允许在 deadline 之后占用有限的清理时间。

原因：instruction profiling 往往包含采集、报告导出、kernel 枚举、反汇编和结构化等
多个子命令。若每个阶段重新获得完整 timeout，一次请求的实际耗时可能是配置值的数倍；
请求级 deadline 才能让 `timeout_sec` 表示可预测的总体执行预算。

### 19. RNG 一致性保留 v6.2 实现，只迁移测试

来源：待迁移分支的 `616775a feat(catalog): migrate KernelSwift v5 support` 引入
`_fork_reference_rng()`，在 reference 执行后恢复 Torch CPU/CUDA RNG。当前 v6.2
已经在 reference/candidate 输入生成前和正式调用前分别执行
`_seed_globals(workload.seed)`。

状态：已实现；Python、NumPy 和 Torch RNG 重放回归测试已补齐。

决定：不迁移 `_fork_reference_rng()`。继续以 v6.2 的 `_seed_globals()` 为唯一 RNG
重放机制，使 reference 和 candidate 的输入生成及正式执行分别从相同 workload seed
开始。将待迁移分支中 reference 与 candidate 都调用 `torch.rand_like()` 的测试改写为
v6.2 Definition、Workload 和 oracle 契约后保留；可在同一测试范围覆盖 Python
`random` 和 NumPy RNG。cuDNN deterministic 设置另行决定。

原因：v6.2 现有逻辑同时重置 Python、NumPy 和 Torch RNG，并适用于输入生成与算子
执行；旧 `_fork_reference_rng()` 只保存 Torch CPU/CUDA 状态。叠加两种机制会增加
状态恢复复杂度，却不提供额外的 v6.2 语义保证。

### 20. correctness 中临时启用 cuDNN deterministic

来源：待迁移分支的 `616775a feat(catalog): migrate KernelSwift v5 support` 新增
`_deterministic_correctness()`；当前 v6.2 没有对应设置。

状态：已实现并通过作用域恢复回归测试。

决定：保留该能力，但只在 CUDA/cuDNN 可用时包裹 correctness reference 和 candidate
调用。作用域内设置 `torch.backends.cudnn.deterministic=True`、
`torch.backends.cudnn.benchmark=False`，并在 `finally` 中恢复进入前的值。不得影响
timing、preflight 或 profiling，也不启用更强的
`torch.use_deterministic_algorithms(True)`。其他 backend 不类推设置未经验证的厂商
全局开关。

原因：workload seed 只能重放随机数序列，不能约束 cuDNN 的算法选择和部分非确定性
执行。把设置限制在 correctness 作用域可提高 reference/candidate 比较的可复现性，同时
避免改变正式 latency 或让缺少确定性实现的算子被强制拒绝。

### 21. 每个 workload/trial 后释放无引用设备内存

来源：待迁移分支的 `616775a feat(catalog): migrate KernelSwift v5 support` 新增
`_release_device_memory()`，在 correctness workload 和 timing trial 后执行
`gc.collect()` 与 `device.empty_cache()`。当前 v6.2 主要依赖整个隔离 worker 退出时
统一释放资源。

状态：已实现并通过 correctness、timing、preflight 生命周期回归测试。

决定：保留该能力并适配 v6.2：每个 correctness workload、每个 timing trial 和每个
preflight workload smoke test 无论成功或失败，都在设备同步且该阶段的输入、输出局部
变量离开作用域后执行 `gc.collect()` 和 `device.empty_cache()`。timing 和 preflight 的
单次执行应封装为独立 helper，避免外层局部变量仍引用 Tensor 时提前清理。清理不得进入
warmup、正式计时或 profiler 采集窗口，也不得卸载 candidate、oracle 模块或已编译
kernel。

原因：一个 v6.2 请求可能包含大量、尺寸差异显著的 workloads。只在整个 worker 退出时
清理，Python 循环引用和 allocator 空闲块可能在请求内持续积累，导致后续 workload
OOM。把清理放在测量窗口之外可以降低峰值和碎片化风险，不改变记录的 latency。

### 22. 显式 source root 不得绕过 v6.2 ABI 校验

来源：待迁移分支的 `eed723f feat: enhance Iluvatar IXKN profiling` 为源码映射增加
`load_implementation(..., source_root=...)`，但其旧 loader 不接收 Definition，也不执行
v6.2 `_bind_public_symbol()` ABI 校验。当前 v6.2 loader 强制接收 Implementation 和
Definition，但只支持内部临时源码目录。

状态：已实现并覆盖普通、keyword-only、var-positional、冲突符号、文件缺失和内容变化。

决定：为 v6.2 loader 增加显式 `source_root` 能力时，仍必须传入 Definition 并执行现有
entrypoint、签名、parameter kind 和冲突公开符号校验。evaluator adapter 使用独立函数
将 candidate 物化到稳定目录；runner 从该目录加载时验证磁盘文件与
`Implementation.sources` 一致，不重新覆盖文件。未指定 `source_root` 的普通 Eval
继续使用现有临时目录。加载完成后继续清理临时 `sys.path` 项。

需要覆盖显式 source root 的正常加载、keyword-only/var-positional ABI、冲突公开符号、
文件缺失和内容不一致测试。

原因：稳定源码路径是 profiler 源码映射所需的文件能力，不应改变 candidate 的 v6.2
调用契约。原样迁移旧 loader 会让 profiling 和 evaluate 对同一 candidate 使用不同的
ABI 校验强度。

### 25. 多阶段执行复用一个不可变 ProfileCommand

状态：已实现并通过不可变命令、多阶段和完成标记回归测试。

决定：不把 `ProfileCommand` 改成命令列表。evaluator adapter 只构造一个不可变的
`ProfileCommand`；vendor profiler 可以按工具需要，用不同的外层厂商参数将同一个命令
执行一次或多次，并在内部动态决定后续阶段。每次执行前清除旧完成标记，并独立检查剩余

原因：后续阶段数量和 kernel 名称通常只能由第一阶段动态发现，无法预先编码为公开命令

### 29. 按宿主机全局资源作用域串行化 vendor profiling

来源：待迁移分支的 `5029be3 fix(profiling): serialize Moore Threads MCU globally`
和 `b9576e9 feat(profiling): enhance PPU ACU evidence levels`。MThreads MCU profiler
和 T-Head PCM 计数器都是宿主机全局资源，不随请求选择的 device 独立。

状态：已实现并通过公共锁回归测试；MThreads 和 T-Head 真机验证均已完成，T-Head
采集结束后的 `amperfd` 已确认恢复为 Collecting。

决定：不为每个 device 创建独立锁，也不让所有 backend 无条件加锁。只有使用宿主机全局
资源的 vendor profiler，在执行 `ProfileCommand` 前进入自己的资源保护 context；同一
宿主机上的所有 device 和 KGS 进程竞争同一把锁。保护层同时包含进程内线程锁和固定的
跨进程文件锁，锁路径不接受请求参数覆盖；退出、失败和异常都必须在 `finally` 中释放。

MThreads 在持有全局 MCU 锁期间完成采集。T-Head 获得全局 PCM 锁后暂停 `amperfd`
collector，采集结束后先恢复并确认 collector 状态，再释放锁。获取锁、等待厂商工具
cooldown、暂停、采集、恢复和状态确认都服从同一个 request-wide monotonic deadline，
不得在获得锁后重新得到一份完整 timeout。无法确认 `amperfd` 恢复时最终请求必须失败，
但仍保留已有 artifact、日志和恢复诊断；普通 device-local profiler 不进入该保护层。

原因：按 device 加锁无法阻止多张卡同时争用同一个 MCU/PCM，通用全局锁又会无谓串行化
互不相关的 profiler。将保护逻辑限制在了解资源语义的 vendor backend，既覆盖线程和多
进程并发，也不会把硬件私有生命周期泄漏到公开 Schema、`ProfileCommand` 或通用 runner。

### 30. 保留 Iluvatar IXKN 纯汇编 instruction fallback，但优先修复源码映射

来源：待迁移分支的 `eed723f feat: enhance Iluvatar IXKN profiling` 建立 instruction
采集，`ebac936 fix(profiling): add Iluvatar assembly instruction fallback` 在 IXKN 无法
导出源码映射时增加纯汇编解析。IXKN 的汇编来自设备二进制，而源码映射还依赖编译器保留
指令地址到源文件行号的 line-info，并要求 profiler 能解析和访问对应源码路径。

状态：已实现并通过 parser/证据边界测试；Iluvatar 真机已取得带源码映射的完整
instruction 证据，未触发纯汇编 fallback。

决定：对外仍只提供 `metrics` 和 `instruction`，不恢复 `source` level。instruction
主路径必须为本次隔离执行显式启用 line-info、使用隔离编译 cache、传入 evaluator adapter
物化的 candidate source roots，并优先生成带源码文件和行号的结构化 instruction listing。
不得为了快速得到结果而主动选择纯汇编，也不得用纯汇编掩盖可修复的环境、路径或工具配置
问题。

只有主路径已经执行且 IXKN 明确未产生可用源码映射时，才调用纯汇编导出作为最后兜底。
fallback 仍须产生非空的结构化 `instructions.json`，保留原始汇编和主路径失败诊断，设置
`mapped_instruction_count=0`、`dynamic_timeline=false` 并返回显式 warning；不得声明
`source_mapping` capability。连汇编也无法解析时 instruction 请求失败，不能降级为
metrics 成功。主路径和 fallback 共享同一 `ProfileCommand` 与 request-wide deadline，
不通过无依据的重复采集延长请求。

原因：源码映射比纯汇编更有利于把热点指令定位回 candidate，应作为正常验收目标；但部分
厂商工具链能够保留设备二进制却无法提供 line-info，直接丢弃仍有效的汇编证据也没有必要。
将 fallback 明确标为低保真结果，可以兼顾可诊断性和最大可用证据，同时推动真机环境优先
修复主路径。

### 31. 保留昆仑芯编译线程约束并接入公共进程树终止策略

来源：待迁移分支的 `baa97e6 feat: enhance Kunlunxin XProfiler integration`、

状态：已实现并接入公共进程生命周期；昆仑芯已在单卡、单 slot 环境完成低并发

决定：仅当 Server `backend=kunlunxin` 时，在导入设备运行时之前通过 `setdefault`

原因：昆仑芯编译链及其依赖库在多请求环境中可能创建大量线程，厂商 profiler 还可能留下
后代进程；两者叠加会耗尽容器 PID 并让已释放的 device slot 仍被占用。backend 专属默认

增加已在第 27 项确认保留的 line-info 兼容补丁。当前 v6.2 提供 `ProfileCommand`；Native
runner 需要迁入第 15 项固定的 `topsProfilerStart/Stop` 采集边界。

状态：已实现并通过 topsprof/源码映射证据测试；燧原按本轮验证范围明确排除，待后续
获得授权环境后补充真机验证。

决定：metrics 使用 topsprof 包裹一个不可变 `ProfileCommand`，固定使用
`--profile-from-start off --capture-range topsProfilerApi`。只有 topsprof 正常退出、
Native command 的 completion marker 存在、VPD 和 summary CSV 非空，并解析出至少一条
GCU activity 时才能完成；非 Native command 不要求 Native 私有 marker，仍必须满足进程
和报告证据条件。

GCU trace 是可选增强：导出失败可以 warning，只有实际解析出非空 timeline 时才声明
`execution_timeline`。topsprof 1.9 不提供硬件 PMU，因此只声明实际得到的
`kernel_profile` 和可选 timeline，不声明 `performance_counters`。

instruction 使用本次请求的隔离 Triton/module cache，通过
`clang-offload-bundler` 解出 GCU device object，再用 `llvm-objdump -S -l -C -d`
生成静态 GCU instruction listing。执行前缺少 bundler 或 objdump 时返回
`unsupported`；执行后缺少 fatbin、device object 或非空 instruction listing 时返回
`failed`。源码匹配只读取 `ProfileCommand.source_roots`，profiler 不接收、重建或物化
`ProfileTarget`。

沿用第 27 项确认的 Enflame line-info 进程内兼容补丁，只在 instruction 的 Native 子进程
中按需启用，不修改厂商安装。与其他只要求纯 ISA 的 backend 不同，Enflame 此处保持已经
确认的严格语义：instruction 还必须至少有一条指令映射回提交源码；完全没有源码映射时
失败，不降级为 metrics。

`compiler_ir`、`source_mapping`、`execution_timeline` 等 capability 只在对应 artifact
实际产生时上报。保留 topsprof 日志、VPD、CSV、标准化 metrics、GCU fatbin/device
object、编译器 IR、ISA dump、`instructions.json` 和 source map。采集、报告导出和反汇编
共享 request-wide deadline；topsprof instrumented timing 仅作诊断，不替代 Eval
latency。

原因：topsprof runtime activity 与静态 GCU code evidence 分别构成两个 level 的基础；
动态 capability 上报避免把未成功导出的 timeline 或 IR 伪装成有效证据。Enflame 专用
line-info 补丁的目标就是在已知工具链错配环境中恢复源码映射，因此这里继续执行此前确认
的严格交付边界。

### 41. `/status` 上报动态观测值，产品别名只用于展示

来源：当前 v6.2 已有 `target`、`software`，并在隔离子进程中探测设备，避免主 Server
持有厂商运行时 context。PR #16 的 `41f1538` 增强海光、昆仑芯设备型号探测，
`9795a35` 与 `391fee1` 增加已知型号规范化，`34f0190` 区分 Triton Python 语言版本和
实际编译器发行包版本。PR #17 的 `6f767e1` 在此基础上改为通过各厂商 runtime API 或
只读 CLI 动态探测设备、架构、runtime 和 driver，删除精确型号兜底、设备型号规范化和
根据型号推断架构的逻辑，同时增加 metadata 完整性与来源记录。待迁移分支还在
`/status` 中上报 `server_version`；本次明确确认迁入该字段。

状态：已实现并通过 host metadata 测试；本轮八个平台的真机请求均保存了实际环境
快照，寒武纪和燧原随各自 profiler 真机验证一并后补。

决定：保留当前 `/status.target` 和 `/status.software` 结构，不增加第二套硬件 Schema，
也不因这些向后兼容的状态字段调整 `api_version`。设备和环境信息只在 Server 启动时通过
同一个隔离子进程探测一次，保留当前 v6.2 的 60 秒冷启动预算，不让主进程导入厂商
运行时。

采用 PR #17 的动态探测原则：优先读取 runtime properties 和厂商 CLI/API 的真实输出；
不再使用精确产品型号兜底，不根据设备名推断 architecture，厂商返回 `Not Found`、
`N/A` 或等价不可用值时保持字段为空。`target.device` 和
`target.devices[].name` 始终保留实际观测到的设备标识，不再由 alias 覆盖，也不生成
`raw_name`/规范名称双轨语义。海光、昆仑芯和其他 backend 的具体探测命令仍由各自
`Device` 实现负责。

为方便人阅读，`target` 增加可选的 `display_name`。展示映射独立命名为
`DEVICE_DISPLAY_NAMES`，当前确认的映射只有 Enflame `ZIXIAOC200` 到 `S60`：

```json
{
  "target": {
    "device": "ZIXIAOC200",
    "display_name": "S60"
  }
}
```

`display_name` 不属于设备身份，只允许用于 `/status` 展示、日志和报告。环境解析、
TargetContext、backend/profiler 选择、能力判断、缓存键、任务调度和知识复用全部继续读取
实际的 `backend`、`device` 与 `architecture`，禁止读取 `display_name`。映射未命中时
省略该字段，不影响任何执行行为；后续新增展示名必须使用明确的 backend 与观测设备名
精确匹配，不能恢复模糊 canonical alias。

采用 PR #17 的 `metadata` 结构，记录 `complete`、`missing`、`sources` 和可选的
`probe_errors`，使缺失值与探测来源可审计。显式部署配置只允许覆盖 architecture、
runtime version 和 driver version，并在 `sources` 中记录配置来源；设备身份和
`display_name` 不通过这些环境配置互相替换。

`software.language_version` 来自隔离进程实际导入的 `triton.__version__`；
`software.compiler/compiler_version` 来自实际拥有 `triton` 模块的 Python distribution，
例如 `triton-ascend`、`triton-mlu` 或 `flagtree`。两类版本独立探测，某一项未知时留空，
不得用另一项回填并再次混淆语言接口版本与厂商编译器包版本。

`/status` 增加 `server_version`，值来自当前 Server 的软件发布版本常量或等价包元数据，
用于确认实际部署的软件构建。客户端仍只根据 `api_version` 判断协议兼容性；不得用
`server_version` 替代 API 协商，也不得把两者版本号绑定递增。

环境 metadata 探测失败不把健康 device slot 标记为 broken；slot 健康仍由强探针决定。
如果最终缺少 `target.device`，KernelGen 继续按现有规则拒绝建立 TargetContext，而不是
使用本机或请求中的硬件名称兜底。

原因：设备原始观测值是环境识别、生成和知识复用的可靠约束；`S60` 等产品名有助于人类
理解，但不应改变程序所见的设备身份。动态探测、来源记录和展示字段分层后，既能审计真实
运行环境，也能提供友好名称，并避免软件升级或别名变化影响协议兼容与执行逻辑。
