# KernelGen Server Schema v6.2 设计

## 结论

v6.2 在 v6.1 的 per-operator 包格式上增加多 reference code 和正式评测前的统一
Torch fallback。三个逻辑角色都由同一个 `oracle.py` 提供，不增加三份源码字段或文件：

| 逻辑角色 | `oracle.py` 入口 | 用途 |
| --- | --- | --- |
| `correctness_reference` | `correctness_run(...)`，否则 `run(...)` | 正确性 oracle |
| `timing_reference` | `timing_run(...)`，否则 `run(...)` | KGS 计时的性能 baseline |
| `torch_reference` | `torch_run(...)` | primary 不可用时同时承担前两项 |

`implementation_reference` 不进入 Schema。它只是原始 Triton、CUDA、AscendC 等实现的
provenance，不是可执行 oracle。

核心约束：

- KGS 是唯一计时权威，不读取外部 reference latency；
- 一个 evaluate 请求只选择一种 reference source，不能逐 workload 混用；
- fallback 在 candidate 执行和正式 correctness/timing 之前完成；
- candidate 错误、数值错误、effects 错误不能触发 fallback；
- `TIMEOUT`、worker 退出和设备强探针失败不能触发 fallback。

## Per-operator catalog

```text
kernelgen_server/data/<catalog>/
  manifest.json
  ops/
    <op_name>/
      definition.json
      oracle.py
      correctness.jsonl       # 可选
      timing.jsonl            # 可选
```

`manifest.json`：

```json
{
  "api_version": "v6.2",
  "evaluator": "native",
  "layout": "per-operator"
}
```

`definition.json` 只保存公共 ABI，不保存 reference source 或 `reference_device`。目录名
必须等于 `Definition.name`。`correctness_reference.py`、`timing_reference.py` 和
`torch_reference.py` 在 v6.2 中不合法，避免同一算子的依赖、设备和 hook 分散成多个
真值来源。

## `oracle.py` 合同

```python
REFERENCE_DEVICE = "target"

def run(...): ...             # correctness/timing 共享 primary
def correctness_run(...): ... # 可选 phase override
def timing_run(...): ...      # 可选 phase override
def torch_run(...): ...       # 可选
```

`run()` 是两个阶段的共享 primary。correctness 优先选择 `correctness_run()`，不存在时
使用 `run()`；timing 优先选择 `timing_run()`，不存在时使用 `run()`。因此两种语义一致
时只定义一个 `run()`；只有某阶段需要 upcast、特殊公式或不同计时策略时才增加对应
override。存在 correctness workload 时，`run()`/`correctness_run()` 至少存在一个；
存在 timing workload 时，`run()`/`timing_run()` 至少存在一个。`torch_run()` 可选，
但一旦 fallback 被选择，它同时用于正式 correctness 和 timing baseline。

所有存在的入口都按 `Definition.parameters` 做结构 ABI 校验：参数名、顺序、kind、
required/default 状态和默认值必须一致。`type_hint` 仍只供 Agent 阅读，不做运行时类型
强校验。

`REFERENCE_DEVICE` 只能在 `oracle.py` 顶层出现一次，值只能为 `"target"` 或 `"cpu"`。
Catalog loader 使用 AST 读取字面量，不执行源码来发现设备。

Primary 可以提供：

- `gen_inputs(ctx, device)`；
- `valid(ref_outputs, sol_outputs, inputs, ctx)`。

`gen_inputs` 从 `ctx["inputs"]` 读取 workload recipe，并返回按 Definition 参数名索引的
实际输入。v6.2 的 `valid` 收到的 `inputs` 同样是按参数名索引的映射；存在该 hook 时，
它替代 correctness 返回值的逐值比较，以复现随机或部分输出算子的 pytest 断言。KGS
仍在调用它之前强制 PyTree 结构、leaf 类型、Tensor shape/dtype、mutation 与 alias。
v6.0 继续给 `valid` 传 ABI 顺序的参数值列表，并保留先逐值比较、再调用 hook 的行为。

Fallback 如需不同的输入或校验逻辑，使用 `torch_gen_inputs(...)` 和 `torch_valid(...)`；
未提供时使用普通 JSON recipe 和默认数值比较。`oracle.py` 必须 import-safe：目标 API
应在 primary 函数内解析或调用。若模块顶层 import 本身失败，同文件中的 `torch_run()`
也无法被安全加载，KGS 会返回 `RUNTIME_ERROR`。

## 文件型 Workload

v6.2 继承 v6.1 的 safetensors Workload：顶层 `input_path` 从目标环境中的绝对路径
按参数名加载输入 Tensor，对应 `inputs` recipe 使用 `type: "safetensor"`；correctness
可通过顶层 `output_path` 按 `Definition.outputs` 名称加载 golden Tensor，并跳过该
workload 的 correctness reference。普通 scalar/literal 参数仍从 `inputs` 读取。

`output_path` 不用于 timing。即使 timing 通过 `input_path` 重放真实输入，primary 和
candidate 也必须由 KGS 在同一目标环境、同一计时链路现场测量；v6.2 不读取
safetensors metadata 或其他外部来源中的 reference latency。原地算子只有在全部
mutation 都通过 `returns_alias_of` 暴露在 golden outputs 中时才能使用
`output_path`，否则仍须执行 correctness reference。

## 正式评测前的统一选择

KGS 对 primary 执行：

1. 导入 `oracle.py`，校验所需入口、hooks 和 ABI；
2. 按 seed 重新物化全部 correctness workload；有 `output_path` 时验证并加载 golden，
   否则非计时执行 primary correctness reference；
3. 非计时执行全部 timing workload；
4. 每次执行后同步目标设备。

全部成功后整轮选择 `primary`。任一 workload 因 API、dtype、layout 或 shape 不支持而
失败时，KGS 从第一个 workload 开始对 `torch_run()` 重做完整 readiness；全部成功才整
轮选择 `torch_fallback`。smoke 输出不会复用到正式评测，mutation/alias 输入也会重新
生成。

```text
primary 全 workload readiness
        ├─成功 → 正式 evaluate 全部使用 primary
        └─失败 → torch_run 全 workload readiness
                         ├─成功 → 正式 evaluate 全部使用 torch_fallback
                         └─失败 → RUNTIME_ERROR
```

这一步不能只做静态 capability 查询。API 可能存在，但仅部分 dtype、layout 或 shape
返回 `NOT IMPLEMENTED`；因此静态检查用于尽早发现缺失符号，动态 smoke 才是最终依据。

Candidate 在 source selection 之后加载和执行。Candidate 加载失败、运行异常、数值或
effects 不一致只影响本次评测结果，不重新选择 reference。进程级超时、worker 退出和
设备探针仍由现有隔离层处理。

v6.2 与 framework benchmark 统一阶段语义：correctness workload 才执行数值、mutation
和 alias 校验；timing workload 只要求 reference/candidate 可执行并产生合法 latency，
不比较输出或 effects。因此 timing 的 `PASSED` 只表示计时完成，不为该 shape 的数值
正确性背书。需要被严格验证的 shape 必须同时进入 correctness workload。

`/preflight` 保持 candidate-only：它只对 timing candidate 做 ABI 检查和逐 case smoke，
不执行 reference、不做 source readiness、不计时。

## Autograd-only correctness 边界

v6.2 不扩展 gradient contract。API 本身就是公开 backward 算子时，例如具有稳定调用
签名的 `linear_backward`，仍按普通 Definition 抽取：上游梯度和 saved state 是普通
输入，计算得到的梯度是普通输出。

另一类测试调用 forward API 后再执行 `.backward()` 或 `torch.autograd.grad()`，其断言
目标是输入或参数梯度，而不是 forward 返回值。v6.2 不能描述哪些输入需要
`requires_grad`、如何构造 loss/`grad_outputs`、选择哪些梯度以及各梯度的 tolerance，
因此本阶段不把这类断言转换成普通 correctness workload，也不在 `valid()`、
`gen_inputs()` 或 oracle 中模拟 backward，更不能为它臆造公开 backward ABI。

具体处理规则：

- 一个参数组合同时包含 forward 输出断言和梯度断言时，只抽取可忠实表达的 forward
  部分，并在抽取/验收记录中注明梯度断言未覆盖；
- 只检查梯度的 pytest case 不生成 correctness workload，记录为
  `unrepresentable: autograd contract`；
- 内部 `torch.autograd.Function.backward(ctx, ...)` 依赖保存的 `ctx`，不视为稳定公开
  backward API；只有 FlagGems 明确导出并注册的独立 callable 才可作为单独算子抽取。

2026-08-26 对 FlagGems `677c09efacc5beac30dc8e53becd069f04b6b5d1` 的范围检查中，
沐曦归档的 47 个算子只有 `rnn_relu` 和 `weight_norm` 的 accuracy pytest 包含 autograd
断言。其中 `weight_norm` 另有公开的 `weight_norm_interface_backward`，真正没有独立
backward API 的只有 `rnn_relu`（1/47）。整个 accuracy suite 的 723 个测试文件中有
31 个出现 `.backward()` 或 `torch.autograd.grad()`；该 4.3% 仍包含已有公开 backward
算子的测试，是需求占比的上界。基于当前占比和 Engine 复杂度，gradient contract
推迟到后续 API 版本按实际需求重新设计，不进入 v6.2。

## 响应、fingerprint 与兼容

`EvaluateResponse` 新增：

```python
reference_source: Literal["primary", "torch_fallback"] = "primary"
```

Native `benchmark_fingerprint` 覆盖纯 ABI Definition、注入后的 `oracle.py`、全部 workload
和 source-selection 策略版本。oracle 或策略变化后，旧 inspect/profile 快照失效。

- Server 默认暴露 `api_version=v6.2`；
- Server 仍解析 v6.0 request/catalog，并沿用单一 `run()`、可选 `correctness()`；
- v6.0 不支持 fallback，响应的 `reference_source` 为 `primary`；
- v6.1 是 catalog 设计编号，不是发布过的 wire API；
- KernelGen 与 KGS 软件发布版本按各自 SemVer 维护，不由 `api_version` 强制决定。

## addmm_ 试点

`flaggems-native/ops/addmm_` 中：

- `timing_run()` 调用目标设备 `self.addmm_`，并在单次调用范围内复现 FlagGems
  benchmark 关闭 TF32 的 Torch baseline 策略；调用结束后恢复原设置；
- `correctness_run()` 先以 float64 计算，后端不支持时退到 float32，再写回原 dtype；
- 不伪造 `torch_run()`，因为该 primary 本身就是可运行的 Torch API；
- 36 个 correctness workload 来自 accuracy pytest 的 full shape、scalar 和实际 timing
  dtype；
- 15 个 timing workload 的 ID、顺序、dtype、shape 和 layout 参数来自目标环境执行
  `pytest benchmark/test_addmm_.py --level core --list-cases` 的原始报告；
- 当前 core case 的 `b_column_major` 全为 false，因此不生成 `gen_inputs()`。

## 验收边界

Host 测试覆盖 v6.0 兼容、per-operator 资产约束、三个命名入口 ABI、整轮 fallback、
candidate 不触发 fallback、fallback 失败和 fingerprint。设备 E2E 还必须覆盖
reference-as-solution、preflight、普通 `RUNTIME_ERROR`、并发/资源释放，并确认评测后
scheduler slot 回到 idle。
