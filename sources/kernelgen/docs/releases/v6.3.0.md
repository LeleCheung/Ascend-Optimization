## 使用与迁移

- CLI 继续复用 Workflow，新增 Catalog、抽取优化和生命周期入口；详见 [CLI 设计](../design/kg_cli.md)。`kg status --detail` 取代 `status --json`，详细进度采用 Schema v2，各调用只暴露自身进度字段。已有 JSON 消费方须按 [进度 Schema](../design/runtime/stage_progress.md) 迁移，不保留旧格式保证。
- 组合 Workflow 改用 build 和 `WorkflowResult`，调用方从 `result.status/reports` 迁移到 `result.state/output.reports`，见 [执行与恢复设计](../design/runtime/stage_orchestration.md)。普通成功步骤复用 receipt，未完成 Optimize 保留优化 workspace 恢复；ledger 仍是评测事实来源。
- Catalog 抽取和优化可独立组合；支持 Flaggems PR 来源和 SSH + Docker case collection，见 [PR 抽取](../design/workflows/flaggems_pr_extract.md)、[Catalog 优化](../design/workflows/catalog_optimize.md)。远端 KGS 部署不再要求本地有 KGS checkout，生命周期入口经过 CLI API；远端仍为 loopback + SSH stdio。
- 新实验使用锁定的 KGS v6.3.3，旧 campaign/Server 实例不自动升级。协议仍仅由 `/status.api_version` 判断，功能由 capabilities 判断；不自动更换 Torch、Triton 或厂商运行时。

## 初次发布的验证边界（旧 commit fef3e2ef）

KGS 发布前功能基线 `c309cb351d2a473e79dcad80a90df4363d5b9fb7` 与 [之前昇腾下游 E2E](../validation/workflow_build_ascend_20260913.md) 一致；KGS 发布收尾仅涉及元数据、文档和版本测试。该历史 E2E 不是本次 KG 最终 tag 的全流程实测：使用准备好的 relu Catalog，跳过抽取和 Catalog Review，真实执行 CLI 后台提交、Bundle 上传、readiness、两轮 SimpleOpt、最终复测、代码 Review、status 和已完成任务 resume。

本次发布单独执行 host 回归，不新增 GPU/昇腾 E2E，不宣称所有新 Catalog、来源抽取或 KernelGen 多 Coder 在最终 tag 上重新验收。安装和最小启动见 [ONBOARDING](../ONBOARDING.md)。

发布相关版本、CLI、Server 和安装脚本测试为 78 passed。完整 host suite 为 1466 passed、22 failed、3 skipped；未修改的 dev 基线 `69e33b206bcc8adc77f52662a095e202e91f2fff` 在相同解释器和配套 KGS 下复跑，失败项、断言和计数完全一致，发布候选没有新增失败。两次均隔离导入路径，并在现有 NVIDIA 容器中隐藏 GPU，未安装依赖。

已知失败分布：`tests/test_coder_workflow_state.py` 14 项、`tests/test_kernelgen_selection.py` 6 项、`tests/test_ledger_best_source.py` 2 项。主要涉及最终复测返回 NEEDS_RETEST 与旧 PASSED/最佳候选断言不一致，另有损坏 ledger 未抛出预期异常的断言；本发布不将这些失败统一认定为无害测试问题，也不绕过最终复测检查。它们保留为主线待修复项，完整 suite 并未全绿。配套 KGS host suite 为 524 passed、5 skipped。
