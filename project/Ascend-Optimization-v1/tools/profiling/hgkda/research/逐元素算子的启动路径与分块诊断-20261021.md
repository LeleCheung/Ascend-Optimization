# SELU的启动路径与分块诊断

`selu_` 在当前完整调用评测中明显落后于PyTorch。HG-KDA首轮采集后，Coder自主测试了编译缓存、实际launcher和分块。探针显示：**小输入需要精简启动路径，大输入需要减少细碎program；仅加libentry装饰器没有解决启动成本。** 原始第二轮已完成但未提速，独立修复仍待验证；下面分别列出正式结果和诊断探针。

## 算子和正式起点

SELU对正数乘scale，对非正数计算 `scale * alpha * (exp(x) - 1)`，并原地写回。当前固定FlagGems本机36项合同通过、0.119× PyTorch；HG首轮通过36项、0.130×。输入非连续时的访问、原地别名、特殊值和dtype都属于正确性范围。

本批使用物理卡7、FlagTree `c286cba6`、Triton 3.5.1、CANN 9.0.0。计分是完整调用walltime，不能与旧阶段的设备kernel成绩混比。

## 真机与模拟器

首轮规范化solution SHA为 `80b0428b3ef5d5b697a0ef7d13dc17b1bb0a3c76900265ebc8ff1b70d521ad18`，原始源码SHA为 `cec7c0259644289a130f84587b6ec1a605979ddb10a4acf4fd710b7c79fe44b0`。4项metrics和1项instruction成功。

1024个fp16元素的instruction请求 `9761bae4c8be446c8b0d33c507d67e80` 保存210条模拟器指令，其中190条映射到源码。可见加载/存储、类型转换、VEXP、BAR、SET_FLAG/WAIT_FLAG等；模拟器的流水和指令时间存在重叠，不相加为真机总耗时。首轮该case的正式完整调用约74.99 μs，独立instruction请求的真机设备任务平均约1.738 μs，说明优化不能只盯设备端表达式。

首轮大矩阵的设备任务约600 μs，Scalar活跃约0.59—0.66。这个线索促使Coder进一步测试分块，并不直接等于“Scalar独占了这些比例的总时间”。

## 接口和编译资源经验

1. `libentry` 用法是 `libentry()(jit_function)` 或 `@libentry()`；直接把函数传给 `libentry(function)` 会报参数错误。这是调用方式错误，不是后端编译失败。
2. 本机LibEntry缓存compiled kernel后仍调用 `kernel[grid](*all_args)`，包括参数分类、key和device查询。不能仅凭“有缓存”假定启动开销已经消失。
3. 当前FlagTree的底层launcher参数与照搬的另一版Triton示例不同。最初直接调用报12/11个参数不匹配；按实际安装版本核对后探针可调用。这个入口具有版本约束；候选须传入本次实际输入和当前stream，只缓存编译产物及配置，不能缓存输入Tensor或计算结果。
4. 当前SELU表达式使用FP32中间量。分块16384及32768的探针出现UB overflow；其中16384要求2097408 bits，实际可用1572864 bits。8192可编译并已取得上述探针成绩。这个资源边界属于此实现/配置，不能推广成910B所有kernel的统一分块上限。

## 第二轮正式结果与缓存查找疑点

第二轮已通过36/36，成绩0.129648×，没有改善首轮0.130370×。源码SHA为 `13a6a1583c9cbf1f202f112e468f7d820366d0d22984fedd159287c402383034`，ledger登记来源为 `analyzer`、父轮次1。这一次存在真实的“profiling分析→修改→完整评测”，但修改没有产生有效性能收益；两次独立复验会按原队列保留正式最佳轮次。

第二轮按分析建议仍保留BLOCK_SIZE=1024，加入 `_fast_launch`。静态核对当前FlagTree的 `JITFunction.run` 发现，正常调用在binder前先补 `debug` 并执行 `_flagprism.apply_compile_options`；候选只把BLOCK_SIZE传给binder。`compute_cache_key` 的key明确包含options，因此存在候选查不到正常编译缓存、持续走stock fallback的可能。当前证据还没有测出实际命中状态，不把这个疑点直接写成已确认原因。

已独立排队 `audit-selu-launch.py`，等待主队列释放同一卡锁后检查原始第二轮的实际缓存命中、是否真正走直接launcher，以及按正常JIT选项查找后的单次计算正确性。它不修改候选，不参与性能计分；输出保存为本批 `research-observations/selu-round-0002-launch-audit.json`。若失败，保留失败状态再决定后续修改。

任何额外修复都需要新的候选和预算，不能把它替换进原始两轮。若采用私有launcher，还需记录固定版本约束和正常入口回退。

原生代码审阅还指出，两轮候选的非连续索引只处理最多4维，而当前正式用例最高2维。rank≥5非连续布局存在错误寻址风险；这不是已完成的NPU补测结论，不能把36/36扩大为任意rank都正确。最终交付若保留该实现，必须补充通用布局实现和独立检查；原始候选作为本轮实验记录保存。

原组最佳首轮的两次独立复验均36/36，为0.131483× / 0.124547×。已单列 [SELU追加候选](../../../operators/campaigns/night-20261021-v3-selu-launch-repair/README.md)，实际排队等待同一卡锁：补齐正常编译选项、连续大输入采用8192分块、非连续布局按全部rank寻址。先36项扩展语义、每项两次，再原36项合同两次复验。当前只有父源码/合同/候选SHA核验完成，NPU结果pending，不计入原组两轮成绩。

实际模块路径也已核对：本机 `triton.runtime.jit` 重定向至 `/usr/local/python3.11.15/lib/python3.11/site-packages/triton/spec/ascend/runtime/jit.py`，文件SHA为 `d4b9f4cc94c7a5beeb06d8c9404442cdfa26aabc4a474697a090639deb72d2db`。该实际run函数确实先注入debug和FlagPrism编译选项；证据保存为本批 `research-observations/selu-launch-import-identity.json`。核对时先导入torch/torch_npu，再导入Triton；独立诊断中反向导入顺序曾触发扩展加载错误，未影响现有worker。源码核验不替代实际缓存命中和NPU计算检查。

额外候选的7项离线测试覆盖补充语义身份、重复次数及完整case集合，还检查缓存命中、首次编译只调用一次、保留metadata/hook，以及launch结果未知时不重复执行原地计算。真实后端计算和性能仍待串行队列执行。

## 最终验证

全部后置任务已结束。真实启动审计确认：原候选用空options计算缓存key，而正常JIT补入`debug=false`；specialization相同但最终key不同。原候选没有命中已编译缓存，直接启动分支未执行；按正常options构造key可命中缓存并正确计算。原始证据见本批`research-observations/selu-round-0002-launch-audit.json`。

SELU追加候选修正options并调整分块、一般布局处理，36项扩展语义每项重复两次全部通过；两次正式36项也全部通过，为0.235649× / 0.242951× PyTorch，仍低于0.8×。这验证了具体调用路径问题，但本轮没有得到达标的SELU实现。

log10最终两次独立复验均36/36，为0.618991× / 0.539464×，同样未达标。以上均是完整调用walltime，候选源码、失败采集与原始分析保留。
