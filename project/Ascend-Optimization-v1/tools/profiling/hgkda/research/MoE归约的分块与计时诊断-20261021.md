# MoE 归约的分块与计时诊断

这是 `night-20261021-v3` 运行期间对三个生成组的分析，供后续知识更新使用。本文不注入正在运行的冻结 KG/HG-KDA 角色。三组正式合同复验已完成，扩展语义仍待检查。

## 算子与改动

`moe_sum_reduce` 将每个 token 的 top-k 个专家输出求和，再乘路由缩放系数：

```text
output[token, hidden] = scale * sum(input[token, expert, hidden])
```

固定 FlagGems-sglang 来自 `938612058a981487e439da514df7d1371cf31e68`。无 profiler 组保留原有 Triton kernel、FP32 累加、输入输出 stride 和缩放参数，仅修改大输入的 launch 配置：

| 输入范围 | 固定原版 | 无 profiler 第二轮 |
|---|---|---|
| token ≤ 64 | 2×512，8 warps | 保持原配置 |
| token > 64 | 1×2048，2 warps | 16×1024，8 warps |

hidden 方向的分块仍取配置值与 hidden 长度向上取2次幂的较小值，尾部保留 mask。源码核对未发现调用 PyTorch 归约替代计算；`torch.empty` 仅分配输出。

例如 token=4096、hidden=7168 时，原 grid 为 4096×4=16384 个 program，新 grid 为 256×7=1792 个 program。program 数约为原来的10.94%，每个 program 合并处理16个 token，同时修改 warps。这里的 program 数变化可以从源码计算；性能收益仍由实测确认，不能据此断定单一硬件瓶颈。

## 诊断证据能支持什么

原生 KG 无 profiler 组自行提交了3项 debug jobs：两项成功，一项因三维 mask 传入二维 store 导致 broadcast 编译失败。失败属于该诊断候选的维度错误，不能据此认定 Ascend 后端缺陷。

`probe_overhead.py` 的批量调用诊断测得：小输入原分块约85.91 μs、空操作 Triton kernel 约60.18 μs、输出分配约7.77 μs；逐次同步测得同 kernel 约137.19 μs、仅同步约19.78 μs。这些探针使用预分配输出，和正式完整 wrapper 的代码与测量方式不同。

因此，现有证据支持“小输入存在明显固定调用成本，大输入可通过分块组织获得显著收益”。批量调用计时仍含 host，不能称为设备独占时间；这些数值也不能简单相减，得出准确的 host、调度和访存占比。源码注释中的“HBM-bound”“16384为后端上限”尚无独立硬件证据支撑，不作为已验证结论。

第二轮采用连续且可整除时的无 mask 快路径，减少 stride 参数，展开 top-k 循环，并调整分块、warps 和 stages；其他布局保留通用 Triton 分支。源码 SHA 为 `96b0e8e40b23afe9a654d9e1afdb120046c97edebeccea5d998c212fa8491196`。两次独立完整复验均8/8，相对 PyTorch 为 **1.543× / 1.649×**，相对固定 FlagGems-sglang 为 **1.513× / 1.622×**。36项额外语义仍待执行。

五项 metrics 均成功，分别对应全部五个性能 case，每项10次预热、100次统计。已核对 profiling 的规范化 solution SHA 与第二轮 identity 一致；它与原始 `.py` 文件 SHA 是不同身份字段。

完整调用和设备任务来自不同采集，表用于区分量级，不作精确减法归因。小输入优先检查完整调用成本；大输入优先检查设备端搬运、归约和流水组织。512与4096 token的指标结构不同，应分别保留诊断。

原生分析已完成，提出将 `tl.static_range` 改为可流水化循环并调整 stages 的下一项实验。建议仍值得验证，但以下解释需要纠正：

| 原分析中的说法 | 对照事实与处理 |
|---|---|
| 第二、第三个性能 case 为2和8 token | 冻结合同实际为8和64 token。使用不透明case_id查完整输入，不能根据序号推测形状。 |
| 四条流水比例相加约1.115，因此89%串行，并据此预测约150 μs可隐藏 | 边际活跃比例不能确定准确的重叠时间、同步顺序或可隐藏的关键路径。先用指令时间线或循环改写实测区分。 |
| 以 MTE2 的平均忙时除总逻辑读字节，得到真实读带宽 | 逐核流水忙时与全设备逻辑工作量范围不同；总逻辑字节除设备任务时长只能作为逻辑有效吞吐，不能冒充物理HBM计数或峰值利用率。 |
| 1.79 μs的均值包含开头预热记录 | 固定KGS的 `_parse_op_summary` 按算子排除前10条，再聚合100条。原始CSV为110条，应按这套规则复算。 |

原生 KG 的 `get_profile_context` 直接返回评测结果的 `per_workload`。本批 Native 结果中 `axes` 为空，虽然冻结 `workloads.json` 保存了完整输入，但该MCP响应没有附上这份规格。这解释了为何需要补全上下文；它不证明所有形状错误都由接口单独造成。

本批第二轮先由 Coder 生成，之后才进行最终最佳版本 profiling。源码核对可见 `SingleCoderOptimizationWorkflow` 在 Coder 停止和最终复验之后调用 `ensure_best_profile`；Coder也能在优化过程中主动委派分析。开启 profiler 不意味着每次修改前必定执行分析。本组没有把该最终分析用于下一正式轮次。

`opprof_facts.py` 已在真实附件上验证。设备采集对应4096 token、top-k=8、hidden=7168、bf16，kernel为 `_moe_sum_reduce_kernel`，物理卡7；档案SHA为 `957b7b956505fc4b29578384ade826ec6b85ad039941f32c883506fe71c41432`，与上述HG第二轮规范化solution SHA绑定。

这些事实还不能把“搬运忙”直接等同于“HBM已饱和”：没有经过定义核验和峰值标定的物理HBM吞吐，也没有关键路径的精确重叠分解。bankgroup冲突也只是后续检查UB布局的线索，是否值得修改须看源码、编译结果和实测。

## 后续可复用的诊断规则

1. 先检查输入规模与实际调用路径，再决定优化 wrapper、program 几何还是 kernel 内部；保留小、大输入的分项结果。
2. 按 `token×hidden×top-k`、dtype、stride 和 scale 建立适用域。增大 token 分块时同步核对中间张量规模、尾部覆盖和编译资源。
3. 固定工作量，改变每个 program 的 token 数与 grid，测设备任务及完整调用；用 PipeUtilization 或可获得的指令证据进一步区分调度、搬运与计算限制。
4. 归约检查 FP32 累加、输出 dtype、非连续布局、非2次幂 top-k、非默认 scale 和输入未被修改。当前三组36项补测已完成，只有原生profiler版全部通过；正式8项不能替代这些一般语义检查。
5. 把最佳候选、失败探针和诊断来源分别保留。本次分块建议与候选来自 KG 无 profiler 组自主生成，本文分析发生在其后。
