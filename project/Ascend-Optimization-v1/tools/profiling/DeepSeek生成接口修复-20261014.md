# DeepSeek生成接口修复

问题发生在模型接口：CC只收到思考，耗尽输出额度后自动续写，源码JSON分成多段，控制器无法解析。旧`logaddexp2`方法批次第1轮生成失败；第2轮生成了源码，但因启动grid传入整数而评测失败。这些记录保留在`operators/logaddexp2/reports/profiling-agent-20261014-four-method/`。

## 已核实的原因

DeepSeek官方[Anthropic兼容说明](https://api-docs.deepseek.com/guides/anthropic_api)明确：支持`thinking`，但忽略`budget_tokens`。[思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode)明确：默认开启思考、默认high。

本机实测CC设置`MAX_THINKING_TOKENS=0`、`alwaysThinkingEnabled=false`和禁用adaptive后，实际请求省略了`thinking`。供应商按默认值开启思考，完整提示词仍产生69,605个思考字符、两轮调用；不能把CC参数当成供应商已关闭的证据。

## 修复与验证

`deepseek_request_bridge.py`仅在本次调用期间监听loopback，转发CC原始请求，并为`/v1/messages`显式添加`thinking: {type: disabled}`。Beta路径带`?beta=true`，判断须使用URL的path。保留模型、消息、最大输出额度、认证头和响应流；不记录认证头与请求正文。

同一完整优化提示词的请求适配实测：14.76秒，HTTP200，思考字符0，num_turns=1，成功解析4,692字节的完整源码。这里只证明生成接口可用，该探针源码尚未经过设备评测，不列为优化成果。

控制器选项为`--provider-thinking disabled`，审计文件为每轮`provider-request-<尝试号>.json`，实际源码仍由CC+DeepSeek生成；完整设备正确性、性能与两次最终复验决定交付。此模式继续保留20分钟生成超时及最多一次格式修复。

旧批次在模型生成阶段、两套KGS均空闲时停止，只结束本批控制器及其模型子进程组；原`campaign-state.json`未改写，停止记录见`interruption.json`。已完成的四算子最佳源码复现沿用原结果，新方法验证另开`20261014-four-direct`，两类结果分别记录。
