## 第三步：查看与恢复

产物位于`operators/<算子>/reports/profiling-agent-<批次>-replay/`和`profiling-agent-<批次>-method/`。汇总为`operators/四算子闭环-<批次>.md`与JSON，明确分开两种模式。每算子的日志位于reports下`workflow-<批次>-<模式>.log`。

同批次再次执行会恢复已完成步骤；已经发出但结果未知的设备请求不会自动重发。运行中不得修改知识、源码或commit/pull。宿主入口持有物理卡7锁，每次设备请求检查两套KGS空闲，不改镜像、服务或他人进程。

## 第四步：核验和交付

复现与生成各自进行完整正确性评测和两次最终复验。narrow_copy自动选择19657与device_task，包含DMA和kernel；其余使用19655与device_kernel。采用性能case几何平均，两次最终结果较慢值。

下载完整证据后可离线汇总，不连接设备或模型：

```bash
python tools/profiling/four_operator_workflow.py --batch example --report-only
```

修复后批次与之前复现一并汇总：

```bash
python tools/profiling/four_operator_workflow.py --batch 20261014-four-direct --replay-batch 20261014-four --report-only
```

汇总核验源码SHA、完整合同、计时范围、最佳选择与真机附件。数值Roofline尚未建立；诊断使用真实流水指标、语义、源码及编译约束。

新批次还检查候选是否真的修改了实现：只改注释、排版或顶层字面量配置表顺序的输出会被要求修正，历史原始结果不改写。最终表中的“建议产生有效优化”同时要求实际实现有变化和两次复验较慢值相对起点超过0.5%，避免把测速波动当成方法收益。独立`source-review.json`绑定候选SHA；已确认有语义错误的最终源码会被拒绝交付。

首批四项和logaddexp2重试已结束，见[最新进展](../../operators/四算子工作流进展-20261014.md)。矩阵乘第2轮生成了有效候选；其余三项仍保留起点。新的生成检查还拒绝调用参数里的`...`占位符，以及只新增未被原执行路径引用的函数而未修改入口的输出。该静态检查处理明确错误，不替代完整评测或一般形状的源码审查。新门禁只用于新批生成，历史响应按启动时规则核验与保留。

需要采用某个算子的重试结果时，离线汇总可显式指定来源，并要求所有条目核验完成：

```bash
python tools/profiling/four_operator_workflow.py --batch 20261014-four-direct \
  --mode method --replay-batch 20261014-four --report-only --require-complete \
  --method-batch logaddexp2=20261014-logadd-method-retry
```

`--method-batch`只选择报告来源，不发起新运行；其他算子仍使用`--batch`。缺少批次会显示missing，完整交付模式则停止生成汇总，不省略未完成算子。

按历史完整知识快照复现生成流程时，在新批次对`optimization_campaign.py`传入`--knowledge <旧campaign>/knowledge.md --knowledge-snapshot`。该选项直接使用旧全文，不重复拼接当前的算子知识；新调用仍需保存模型原响应并完整评测，模型生成可能有差异。运行中的旧批次使用启动时原代码，待队列完成后再同步这些改动。
