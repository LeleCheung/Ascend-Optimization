# 本轮复现与交接

本轮对象是 Excel 华为列低于 0.8× 的 amin、matmul_bias_activation、narrow_copy。结果入口为各算子的 `reports/master-closure-20261010/版本对比.md`；三算子总表由 `summarize-master-goal.py` 重算，缺少任意一组时不会生成。

## 1. 获取源码与证据

```bash
git clone git@github.com:LeleCheung/Ascend-Optimization.git
cd Ascend-Optimization
git lfs pull
```

固定 FlagGems master 为 `d6a8eec473517a3d68157b208eb9c057eb1d4c50`。仓库内 `third_party/FlagGems` 是历史版本；本轮使用单独 checkout。

```bash
git clone https://github.com/flagos-ai/FlagGems.git FlagGems-master
git -C FlagGems-master checkout d6a8eec473517a3d68157b208eb9c057eb1d4c50
```

环境为 Ascend 910B4-1、aarch64、CANN 9.0.0、Python 3.11.15、torch 2.9.0+cpu、torch_npu 2.9.0.post2、Triton 3.5.1、Flagtree 0.6.0；KG 6.7.0、KGS 6.5.0。本机复用 `tle_yy`，当前实验物理卡 7 在服务中显示为 `npu:0`。

## 2. narrow_copy 必须先准备评测适配

上游 benchmark 缺少 KGS 的懒加载 case API；小输入 PyTorch 使用 DMA，原计时器还会在 `kernel_name=N/A` 的 CSV 上失败。适配脚本只修改本轮独立 checkout，算子源码保持固定 master。

```bash
project=/绝对路径/Ascend-Optimization/project/Ascend-Optimization-v1
gems=/绝对路径/FlagGems-master
python3 "$project/operators/narrow_copy/scripts/adapt-master-case-api.py" \
 "$gems" --provenance /新实验目录/case-api.json
git -C "$gems" add benchmark/test_narrow_copy.py
git -C "$gems" commit -m '适配 narrow_copy benchmark case API'
python3 "$project/operators/narrow_copy/scripts/adapt-device-task-timing.py" \
 "$gems" --provenance /新实验目录/device-task-timing.json
git -C "$gems" add benchmark/test_narrow_copy.py benchmark/ascend_copy_timer.py
git -C "$gems" commit -m '修复 DMA 空名称解析'
```

完整范围为 18 个正确性用例与 15 个性能用例。`reports/device-timing-contract-20261010/` 保存了当次 benchmark、计时 helper 和 SHA；上面重建步骤使用同样的适配内容。

## 3. 启动独立 KGS

在已配置 CANN、torch_npu 与 Triton 的容器内执行公共启动脚本，指定绝对仓库路径、FlagGems checkout、空闲端口、获准使用的物理卡与独立产物目录：

```bash
bash "$project/tools/evaluation/start-fixed-master-kgs.sh" \
 /绝对路径/Ascend-Optimization "$gems" 19657 7 /新实验目录/profiles
```

服务可由 tmux 托管。本轮已有 19655～19658 服务，直接复测时复用对应服务；创建新实验应选空闲端口。amin/matmul 使用未修改 master 的服务；narrow_copy 使用已适配的 checkout。

## 4. 先复测最终源码

```bash
py=/usr/local/python3.11.15/bin/python3.11
"$py" "$project/tools/evaluation/evaluate-operator.py" \
 --operator narrow_copy \
 --source "$project/operators/narrow_copy/candidates/small-dma-hybrid-20261010.py" \
 --server http://127.0.0.1:19657 --timing-scope device_task \
 --output /新实验目录/narrow-final --label optimized --timeout 1800
```

最终源码与所选结果以版本对比 JSON 的 `source_sha256`、`result_path` 为准。上述小 DMA 候选已完成完整评测，进一步候选是否替代它由完整结果决定。amin 的最终源码为 `direct-axis-native-v5-20261010.py`，matmul 为 `profiling-kgroup-v6-20261010.py`；使用原 master 服务和 `--timing-scope device_kernel`，完整范围分别为 27、42 项。

amin 与 narrow_copy 的 baseline 是保留原内核的启动兼容版本；原版分别有超限或大输入同步问题。候选路径、修复与来源 SHA 均记录在算子 README 和 provenance 中。

## 5. 重跑 KG 两组与独立复验

按 [评测说明](README.md)运行 `run-kg-operator-910b.sh`，两组分别为 `no-profile`、`profile`，都从同一 baseline 出发，预算为两轮。使用新的 workspace 后缀。模型为 CC 接 DeepSeek `deepseek-v4-flash[1m]`，配置和令牌在本机环境中。控制器 venv 位于 `/data/hanle/ascend-optimization/runtime/kg-controller`；运行器脚本显式使用本仓库 `sources`。

任务由 tmux 托管，KG 原生后台 worker 自行完成轮次。结束后使用 `finalize-kg-arm.py` 导出并完整独立复验，narrow_copy 显式传入 `--server http://127.0.0.1:19657 --timing-scope device_task`。

## 6. profiling 与证据检查

`collect-optimized-profiles.py` 采真机 PipeUtilization，`debug-operator.py` 运行开销或编译诊断；都经 KGS 队列串行执行。`run-task-timing-diagnostic-910b.sh` 对 narrow_copy 分别记录设备任务、host enqueue、同步调用和预分配 JIT 启动耗时。

设备计时不包含 host 发射间隙；关闭 KG profiling 反馈不等于关闭设备计时器。DMA 混合实现与纯 Triton 分别标注。数值 Roofline 当前尚未建立；matmul 原始 Msopprof 文本给出的 `memory caused` 与计数缩放问题均保存在原始诊断中。

原始报告、JSON、CSV、日志与 tar.gz 保留采集字节。`archive-manifest.json` 映射原生 KG 长路径到短路径并记录 SHA；Windows 拉取时由 `.gitattributes` 保持这些附件字节。下一会话先读各算子 README、总表和本文件，再检查真实进程、KG 状态和 KGS 队列。
