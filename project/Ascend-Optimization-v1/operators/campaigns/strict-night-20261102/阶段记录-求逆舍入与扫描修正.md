累计交付仍为25/30：1015为7/10，1029为18/20。以下修复沿原PyTorch合同验证，尚未建立合格CANN参考，不增加CANN验收数。

## 求逆：把整LU误差拆成直接算术问题

按列延迟更新LU的768组离线模型存在共同配置，匹配三个冻结奇异矩阵；第一份实际Triton实现仍编译失败。KG第一轮候选为5/7、3/7、5/7，已按原预算终态。

独立诊断使用CPU `libm.fmaf`作为单次FP32舍入参考，比较当前910B编译结果。2048个初始样本中，显式`tl.fma`有1270项不同，补偿乘加为0项。

扩展到8192个普通指数范围和乘积消去样本后：

| 运算 | 融合关闭：不同数 | 融合开启：不同数 |
| --- | ---: | ---: |
| 显式`tl.fma` | 4588 | 4588 |
| 拆分乘法和加法 | 4588 | 4588 |
| 纯Triton补偿乘加 | 0 | 0 |
| `tl.div_rn` | 451 | 451 |
| 余数修正商 | 0 | 0 |
| `tl.div_rn(1,b)` | 546 | 546 |
| 余数修正倒数 | 0 | 0 |

最小例子：`(1+2^-23)*(1-2^-23)-1`。CPU单次舍入参考为`-2^-46`；显式FMA输出0；纯Triton补偿乘加输出`-2^-46`。

实际TTIR和adapter均保留`math.fma`；`tt.precise_divf`在adapter中变成`arith.divf`。两种融合开关生成的npubin SHA相同。常规`llvm-objdump`虽然识别`elf64-hiipu`，却只输出`<not available>`，未取得有效ISA反汇编，因此不声称已定位到某条底层机器指令。检查器、输入、逐样本结果和编译产物位于`numerical-probes/fp32-compensated-v2/`。

这是当前环境的有限样本证据，不是全IEEE证明。Codex据此实现通用误差补偿，没有将固定矩阵、逆矩阵或用例常量放进候选。

v5中，小矩阵按列LU使用补偿乘加和余数修正商；倒数广播为向量，绕开标量precise-div转换风险。数学循环实际使用有界动态循环，头部旧说明未更新。大矩阵保持原右看式LU，输出地址使用独立变量；全部设备计算、打包、置换和info生成仍为Triton。

`compile_inverse.py`显式指定Ascend910B4，阻止设备初始化、driver使用和CompiledKernel加载，只使用单CPU交叉编译。v3完整检查了3个编译实例，及时发现constexpr起点错误；v4因7×7编译超预算，仅保留已完成的3×3产物，未宣称所有分支通过。按PID和进程启动身份停止的只有本次CPU编译树。v5覆盖3×3、批量7×7、非连续7×7与64×64，对齐实际启动的32／8 warps选项后，4个实例全部编译成功；原件与检查器在`analysis/linalg_inv_ex/compile-dynamic-v5/`。离线编译不替代NPU数值或性能评测。

v5的真实正式结果为3/7：小矩阵4项数值不符，大矩阵3项通过。`offline_inverse_kernel.py`去掉编译装饰器，以NumPy指针和FP32算术模型执行原小矩阵函数体；4个固定正确性输入均通过CPU参考。这个模型用于检查索引与数学顺序，不是设备模拟器，也不证明NPU编译结果正确。当前安装的Triton解释器遇到缺少内部别名、布尔运算和循环边界兼容问题，失败原件保存于`cpu-structure-v1/`，不把这些尝试记成设备数值结论。

后续诊断`inverse-stages-v1`已排入原卡锁：同输入比较原稿与带中间存储的变体，保存LU、U转置前代、L转置回代，再测试向量与标量混合的补偿乘加／商。先检查插桩输出是否和原稿一致，再解释中间结果，避免将插桩改变编译行为当成原稿证据。诊断没有性能计时或CANN资格结论。

v6保留按列LU与补偿算术，将小矩阵求解改为按列AXPY更新，减少嵌套逐行点积循环。CPU逐句模型同样4/4；真实运行时5/5，正式仍为3/7，四个小矩阵用例的最大误差和匹配比例与v5相同。因此更改三角求解组织没有解决当前差异，不能把CPU模型通过写成设备通过。两个CPU模型的原输入、输出、LU和源码SHA分别保存在`cpu-literal-v5/`、`cpu-literal-v6/`。

阶段诊断v1已知终态为`diagnostic_error`：检查器把`cpu.mT`转置属性误写为`cpu.mT()`，因此只保留了第一组原稿设备输出，未保存阶段结果。修正版`inverse-stages-v2`使用独立名称、检查器SHA和请求身份补采，保留v1失败原件。该错误属于诊断工具，不能解释成候选编译或数值失败。新版同时用FP32位模式核对插桩／原稿结果，避免相同NaN被普通数值相等检查误判为插桩改变输出。

v2已完成：四组插桩结果与原稿逐位一致，LU阶段与CPU源级模型分别有2、1、60、52个元素不同。第一组3×3的上三角末列应为1.240888、-1.953177，设备阶段输出为1.952756、5.674444；其余LU元素与模型一致。偏差已在三角求解之前出现，不能继续只调整求解算法。

新增1024个标量／向量混合样本中，补偿乘加与修正商均为0项差异，但常数分子的修正倒数仍有384项差异。例如分母1.234567046时，设备为0.810000598，CPU单精度参考为0.810000539。这补充了此前全向量8192样本未覆盖的表达形式，不能把全向量检查通过外推到标量化路径。

v7由此提出两项可验证修改：下半列更新先将不活跃位置的乘法操作数置零，再直接执行补偿乘加，避免`where`同时保留旧列与临时结果；倒数的填充行分母设为1，保留非splat向量表达。源级模型4/4，离线编译覆盖3×3、批量／非连续7×7与64×64且4/4通过，仍待NPU完整评测。当前证据未定位到具体后端pass或ISA，不将缓冲复用解释写成已证实结论。结构化比较和生成脚本位于`analysis/linalg_inv_ex/stage-comparison-v2.json`与`analyze-stages-v2.py`，后续KG上下文会携带这些事实。

为缩小机制范围，另建`inverse-mask-reciprocal-v1`最小探测：分别比较旧掩码表达式、先屏蔽操作数和普通乘加的循环旧值保留，再比较标量／非splat向量分母的倒数。四个离线编译实例通过；设备执行在原卡锁内排于v7之前，不重复性能计时。若最小探测未复现完整LU的错误，仍保留完整LU阶段证据，不据此否定原问题。首版离线编译记录器因字符串路径处理错误中断，新记录器修复后4/4通过，前者未提交任何设备任务。
