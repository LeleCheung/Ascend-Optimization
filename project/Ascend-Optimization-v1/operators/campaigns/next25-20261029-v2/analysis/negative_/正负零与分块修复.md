# negative_：负号语义与分块修复

本轮已经把负零失败定位到Triton前端生成的`0-x`，并发现放大符号位翻转分块会触发UB溢出。修复候选、正式测试和补充检查分别保留；性能成绩以本轮KGS19659完整调用为准。

## 负零在哪里丢失

目标NPU PyTorch对输入`[+0, -0]`输出`[-0, +0]`。旧候选输出`[+0, +0]`，FP16、BF16、FP32均如此。旧候选虽通过30/30正式合同，增加NPU正负零检查后只有57/60。较早使用CPU IEEE结果的补测原件保留，后续已实际核对NPU参考与CPU参考在此输入上一致。

当前安装版Triton 3.5.1的两个前端文件均有以下实现：

```python
def minus(self, input):
    _0 = self.tensor(self.builder.get_null_value(...), ...)
    return self.sub(_0, input, True)
```

文件是`triton/language/semantic.py:469`和`triton/spec/ascend/language/semantic.py:514`，SHA256分别为`a1362a0e71bcd8971aec95e95837c839e4758db252f9261eb1eee348b891cbe9`、`3d2ac763cff4556951d553bd249e56615c6d196ddad05e5b68532657ea4eddd7`。

成对采集的实际`candidate/ir/_neg_flat-0.ttir:16`已经是：

```mlir
%0 = arith.subf %cst, %x_4 : tensor<1024xf32>
```

这里的常量为零。普通数的取负与零减相等，但`0-(+0)`没有产生取负应有的负零。表达式在TTIR阶段已经如此，不能将首次改写位置说成Ascend后端；本次没有修改已安装编译器。

## 替代实现及片上缓冲

替代候选将浮点数按位解释为同宽整数，翻转符号位，再按位解释回原dtype：

```python
# FP32；FP16/BF16对应uint16和0x8000
y = (x.to(tl.uint32, bitcast=True) ^ 0x80000000).to(tl.float32, bitcast=True)
```

首次将连续分块上限设为32768，正式评测28/30，两个大FP32性能输入编译失败。编译器报告需求3145728 bits（384 KiB），可用1572864 bits（192 KiB）；不能只按一个输入张量估计UB用量。

`launch-reuse-bitwise-v3`将分块上限降为8192，来源SHA为`eb2631fe205d4d2f82a3b5114a7a9beb30625108dec90349e05334bc8c159823`。该候选已通过30/30正式合同，完整调用加速比0.512×；补充语义检查和配对采集继续以各自原件为准，尚未达到0.8×性能线。
