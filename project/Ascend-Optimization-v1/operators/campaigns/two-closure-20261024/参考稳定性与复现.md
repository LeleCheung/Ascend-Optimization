# 累计积分参考：缩小反例与官方稳定执行方式

本轮已确认：**问题不是PyTorch整体不支持910B，而是当前FP16非末轴扫描在默认非确定性模式下，重复结果的差异可超过原合同容差。官方确定性模式在本轮检查中解决了重复结果不一致。**

固定Torch `2.9.0+cpu`、torch_npu `2.9.0.post2`、CANN9.0、FlagTree `c286cba6`、物理卡7。准确op-plugin源码在上一批`knowledge/CumsumKernelNpuOpApi.cpp`，调用`aclnnCumsum`。本轮未升级或修改这些组件。

## 新实测

同一FP16输入，沿dim0分别执行`cumsum`和`cumulative_trapezoid(dx=1)`，每种条件六次：

| 形状 | 默认cumsum：无交集位置数 | 默认积分：无交集位置数 | 确定性模式 |
|---|---:|---:|---|
| `(128,8)` | 0 | 0 | 两项六次逐值一致 |
| `(256,8)` | 0 | **1** | 两项六次逐值一致 |
| `(512,16)` | **12** | **16** | 两项六次逐值一致 |
| `(1024,32)` | **141** | **111** | 两项六次逐值一致 |
| `(1024,128)` | **363** | **378** | 两项六次逐值一致 |

“无交集”使用原`atol=rtol=0.015`：分别围绕六次参考结果构造允许区间；若交集为空，不存在一个固定输出能同时通过这六次参考。0个空交集不表示逐值一致，例如默认128×8仍有相对第一次超容差的结果。

最小已观察积分反例为256×8，位置`[239,4]`六次结果为`[-0.1689453125,-0.162109375,-0.15625,-0.16015625,-0.158203125,-0.1923828125]`。固定输入SHA256为`f5874ea96d99dcc5b9399c8ccea5a50015d99d1e52936425b28d65e842b3ed19`。这是本轮尝试形状中的最小反例，尚非对所有可能输入证明的全局最小规模。

隔离进程中启用`torch.use_deterministic_algorithms(True)`后，五种形状的两项运算全部重复六次逐值一致。这是官方API的实际效果，不能解读为已证明默认模式内部具体哪条指令有错。仍需结合运行路径确认是否选择不同扫描实现。

## 独立复现

保存的FP16原始输入位于`research/reference-stability/`，完整结果为`results.json`。在已持有本项目物理卡7串行锁、其他评测空闲的隔离容器进程中运行：

```bash
export ASCEND_RT_VISIBLE_DEVICES=7
python3 tools/profiling/hgkda/reproduce-cumsum-stability.py \
  --input operators/campaigns/two-closure-20261024/research/reference-stability/default-256x8-cumulative_trapezoid-input.bin \
  --shape 256 8 --repeats 12 --output /tmp/cumulative-default-new.json
```

另起进程，增加`--deterministic`、更换`--output`进行官方稳定条件对照。以512×16或1024×128固定输入检查通常能观察更多差异；非确定性结果的具体数值及数量会变化，不要求重现相同六个数。脚本只读取固定输入、重复调用、保存逐项差异，不改KGS配置或正式合同。
