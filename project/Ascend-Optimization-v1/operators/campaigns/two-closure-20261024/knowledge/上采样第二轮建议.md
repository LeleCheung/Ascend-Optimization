# 上采样首轮之后的增量路线

首轮四份源码正式24/24通过，搜索最佳约0.345×。真实debug已经区分：逐点四次GM读取约290ms；行加载后使用偏移GM加载约21ms；对齐行加载＋片上gather降到约0.6ms的大输入路径。盲目删除mask没有提升。小输入PyTorch约30微秒，标准Triton裸launch探针约57微秒，host路径也需要单独处理。全部数值为当前环境的诊断或搜索记录，最终看独立验收。

下一轮优先修改数据复用和程序组织，而非重复同样的分块扫描：

- 整数2倍上采样可沿输入行组织，一个program同时产生相邻输出行/列，复用相邻输入行和水平邻点，避免分别生成每个输出行时反复做gather及地址计算。权重来自真实align_corners=False和有效scale=2的条件；不能只凭输出尺寸2倍就忽略显式scale。边界单独钳位，保留一般比例/stride路径。
- 评估水平/垂直可分离方案及完整融合两者。分两kernel多一次中间张量，但可能用更规则读写换掉复杂gather；必须将分配、写读临时张量和全部launch计入最终成本。不要仅凭单kernel更少就拒绝比较，也不要忽略FP32中间值与最终低精度舍入。
- 针对大输入，查实际IR/指令确认tl.gather及join是否生成逐lane循环、transpose或多次UB搬运，再决定用索引shift、切片或等价组织替换。已有instruction采集因240秒预算取消，不表示没有瓶颈；先读已归档IR和真机metrics。常规编译缓存可读，不改全局后端。
- 小输入若优化host启动，遵守当前preflight准入：标准kernel[grid](...)调用、元数据缓存及本机可用libentry；不绕过准入规则。直接raw launcher仅在明确可接受且当前stream/指针/对齐/尾部全部正确时另作方案，不把旧算子允许性自动推广。

最终还需运行check-remaining-special.py的36项显式scale/布局门禁。原版ABI失败与全部候选失败继续保留。该建议为Codex对本批证据的追加诊断，供第二轮新覆盖层读取；不改写首轮已冻结角色。
