# 上采样：用连续输入块替代逐输出行重复读取

本建议由Codex根据首轮真实源码和debug数据提出，尚未在NPU验证，不能计为优化成果。当前源码每个program处理BR个输出行，分别为每行读取两个输入行；相邻输出行实际上重复读取输入。本批大输入为4×32×128×128，输出4×32×256×256，BR=16时共有2048个program。

## 优先做的不同数据流

对于有效高度和宽度均2倍、align_corners=False的连续NCHW路径，令一个program处理R个连续输入行对应的2R个输出行。加载一个包含上下halo的连续输入行块，长度为next_power_of_2(R+2)×IW；沿最后一维做连续GM读取，之后在UB中用gather选上下行和水平邻点，再插值、join并连续写输出。可试R=4、8，先证明halo/首尾/跨channel正确。相较当前为2R个输出行做4R次行读取，连续块可以减少重复GM搬运和DMA调用。

具体索引例：输出行oy=2*q+j，对应源坐标q-0.25（j=0）或q+0.25（j=1）；上下行分别为(q-1,q)或(q,q+1)，边界clamp。patch起始行q_base-1，加载负行/超尾行时mask，gather索引使用clamp后的真实源行减patch起点。行块不得越过同一N/C图像。若next_power_of_2补齐导致tile太大，应缩R；所有中间张量和编译缓冲都计入UB。也可以先只在高度使用patch复用，水平保留现有gather。

这是待验证方案，UB gather仍可能降低成标量循环，须对比真实IR/设备时间。不把GM搬运理论减少当作实测性能提升。非2倍、非单位末维stride、显式scale不等价于2倍时保留一般路径。

CPU预检已完成：`upsample-patch-cpu-model.py`按上述halo和上下行索引实现，共3种dtype×8种形状×3种R，72/72与CPU参考吻合，包括高度/宽度1、奇数尾块、多通道和批次。结果和脚本SHA见`upsample-patch-cpu-result.json`。这只验证索引和插值等价性，不证明Ascend编译或性能；新kernel仍需真实NPU全部门禁。

## 启动开销

首轮小输入裸普通Triton launch约57微秒，不能把它视为语言或硬件的不可逾越下限。固定版本FlagGems已有from flag_gems.utils import libentry，@libentry配合@triton.jit在其他已有算子使用过，优先验证当前单kernel加装饰器后的完整调用开销和数值；无需绕过标准kernel[grid](...)接口。缓存元数据仍须包含shape/stride/dtype/scale，保持当前stream。s_n/s_c/s_h等实际只依赖元数据的stride也可constexpr以便后端识别连续布局，但要记录编译次数及多布局验证，不能假定所有输入连续。

检查顺序：小输入启动开销、大输入真实设备时间、正式24项、独立48项及全部6项timing数值，最后36项显式scale/布局补验。只按相同case实际候选延迟选择新版本。
