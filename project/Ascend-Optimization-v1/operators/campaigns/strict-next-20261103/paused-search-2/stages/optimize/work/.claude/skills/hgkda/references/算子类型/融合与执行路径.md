# 融合与执行路径

用真机任务记录核对候选和参考侧各启动几个 kernel、有无 DMA 和临时张量。单个 kernel 内 Vector、MTE、Cube 并行活跃，不能据此认定启动了多个 kernel。

融合的潜在收益是减少临时张量读写和 launch；代价可能是缓冲占用增大、并行度降低和同步增加。先记录原路径，再比较融合后的路径和完整延迟。

融合GEMM在GM流量更少仍慢时，可读[矩阵乘复用方向与流水验证](../性能指标/矩阵乘复用方向与流水验证.md)，检查相邻M／N多输出块共享B／A、bias复用与编译调度。方向变换和constexpr形状的联合收益要与同模板单因素确认分别记录。

narrow_copy 的历史经验是：参考侧小连续复制走 MEMCPY_ASYNC，纯 Triton 的小输入设备任务更慢，因此采用小输入 CANN DMA、大输入 Triton。适用条件、正确 ABI 与计时覆盖都影响结论；不能把此策略推广到任意切片。

CANN aclrtMemcpyAsync 是宿主侧运行时 API。TLE Raw 的 AscendC 外部操作在 kernel 内执行，编译与调度路径不同；即使都搬数据，也需要分别评测。

## 本批QKV：布局与精度分别核验

固定FlagTree 0.6.0+ascend.gitc286cba6下，QKV旧扁平索引在实际ttadapter中产生9个逐元素读写循环与12个DiscreteMemAccess标记；显式序列×head_dim二维块使这些标记消失。同输入FP32真机MTE3指令12,587,008→4,096，写回接口流量降为1/32。证据见主批次`analysis/transform_bias_rescale_qkv/old-new-mechanism-v1.json`，绑定v2源码`f2a888fac572`。旧GM→UB计数为0却仍有标量load，不能解释成没有读取输入；静态IR信号、计数和延迟需一起核对。

FP16精度还需独立检查：v3完整21/21，但扩大补测后47/48，Q输入60000、bias60000在缩放前溢出，候选inf而NPU参考30000。证据为v3的`extra-checks-geometry-range-v4.json`，源码`7c853389fa0c`。Q与bias须在相加前转FP32，再缩放及写回。v4源码`ed2efaf75fef`已完整21/21、补测48/48通过，完整调用0.92367×；真实补测位于`proposals/transform_bias_rescale_qkv/fp32-q-accumulation-v4/assessment/extra-checks.json`。v3的失败仍保留；硬件机制采集绑定v2，未另采v4。这里是具体算子/编译器的证据，不是所有扁平索引都会退化。

## 矩阵求逆：先核对奇异输入合同

本批linalg_inv_ex原版5/7，失败恰为两个singular用例。真实诊断见`analysis/linalg_inv_ex/contract-probe-fc75b4022866.json`：输入通过复制一行构成数学奇异矩阵；参考info分别为0与[0,0]，原版为3与[7,7]。参考inverse包含约1.05e8与1.92e9的有限值，与CPU参考一致，候选则返回量级约1的值。因此info和inverse都不一致，不能只修返回字段。

原版求解阶段将零对角替换成1；改为真实对角并只更新主元上方行的`zero-pivot-solve-v1`仍5/7，失败变为非有限分布不匹配。需要区分病态/奇异输入下浮点分解舍入与普通精度错误。冻结合同继续保留，不用PyTorch求逆替代候选，不硬编码参考残差、singular标志或NaN图样；NPU侧与CPU数值相同本身也不代替执行路径trace。
