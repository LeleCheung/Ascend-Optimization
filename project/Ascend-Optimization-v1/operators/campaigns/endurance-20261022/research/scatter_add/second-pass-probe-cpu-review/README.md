# scatter_add 第二批探针的 CPU 复核

本目录是 Codex 对 CC/DeepSeek 实际提交诊断代码的独立复核，不是新的优化候选，也没有新增 NPU 运行。

原生调试任务 `a3e52d4fd1cc4bc18f1d85e003de3ba5` 上传源码 SHA 为 `995e9232562fc4b015d6422ce3b1cafef5d491ea4a9090c063fd3ce01482dd46`。`original-probe.py` 保留准确字节；原请求、NPU 输出和任务状态保留在该轮 KG 调试归档中。

## 三维误差来自探针自身

原 `model_small` 用 `st[i] = st[i + 1] * shape[i]` 推导连续 stride。对 `[5, 7, 9]` 得到 `[35, 7, 1]`，正确值应为 `[63, 9, 1]`；因此它把贡献加到了错误的位置。

`original-cpu-review.json` 使用实际上传的函数在 CPU 重复九组输入，重现了原探针全部九组大误差，说明这不是 NPU 专属问题。只将公式改为乘 `shape[i + 1]` 后，九组 CPU 复核中 FP32 累加模型全部通过原容差，见 `stride-review.json`。保存的 FP16/BF16 NPU 参考前八项也与 CPU 参考一致；这里没有重新验证全部 NPU 输出。

修正后的诊断源保存为 `stride-corrected-probe.py`，只用于说明单行修改及源码身份，没有替换活动 KG 中的代码或历史回执。后续若重跑该探针，应作为独立新任务登记。

## 设备执行错误后的耗时不计成绩

同一探针在 2048² 输入的 `dense_64_64` 发生设备执行错误，随后若干变体报告约 0.125 ms。错误后的这些数字需要在独立、健康的新进程里重新验证；不能仅凭该 JSON 宣称获得高加速比。当前完整语义门禁和正式 KGS 评测仍是选版依据。

这项经验补充了诊断方法：先用可信 CPU 实现校验探针的索引模型，再讨论硬件精度差异；发生设备错误后，后续测量须独立核对。它不证明某种累加路径已在 NPU 上闭环，也不修改任何正式合同、容差或冻结角色。
