# log10_／selu_ 缓冲与搬运优化批次

本批已完成源码优化、完整测试、真机成对采集和48项证据核验。最终log10_为 **0.875×**，selu_为 **0.898×**，均为KGS完整调用相对PyTorch的本批一次正式结果。

| 算子 | 同批父版 | 最终版 | 相对父版实际加速 | 交付说明 |
|---|---:|---:|---:|---|
| `log10_` | 0.751× | **0.875×** | **1.125×** | CC生成的地址键启动缓存；实际耗时下降11.1% |
| `selu_` | 0.898× | **0.898×** | 1.000× | 沿用上轮源码；本轮新候选未优于父版 |

最终两份源码各通过36项正式测试和42＋12＋9项补充检查。两项本批测值都超过0.8×；SELU源码未变，其上轮0.790×仍保留为历史结果。本批收益只按同case实际延迟计算，不把复测分数变化当作新增优化。简洁汇报见[精简汇报](精简汇报.md)，机制、失败与贡献见[方法与机制](方法与机制.md)，源码身份及全部候选见[最终清单](deliverables-final/manifest.json)。

固定 FlagGems `d6a8eec473517a3d68157b208eb9c057eb1d4c50`、FlagTree `0.6.0+ascend.gitc286cba6`，沿用上一轮合同字节、KGS 19659完整调用walltime、物理卡7。每份候选先通过42项布局／语义检查和12项大连续输入检查，再做一次完整正式评测。最终按同case候选实际延迟选择源码，保留失败及未入选结果。

本轮研究两个具体问题：log10 的大输入搬运是否能通过扩大有效分块改善；SELU 的 BF16／FP32 临时量是否能通过编译器现有缓冲复用选项或代码重组减少。普通循环、多tile和仅关闭多缓冲在上一轮已试过，不机械重复。

Codex负责既有证据诊断、机制候选与整合；HG-KDA冻结知识和成对事实，服务器CC／DeepSeek负责追加生成。两者贡献分别记录。

目录：`seeds/` 为上轮最终源码，`catalog/` 为冻结合同，`candidates/` 为独立机制候选，`results/` 为门禁与正式结果，`research/` 为profiling及IR。实验期间查看各状态JSON，不把未完成批次当作交付。

## 执行与复现

当前实验由910B宿主的tmux托管。`continue-buffer-kg.py`等两轮缓冲候选结束后，冻结诊断证据并运行CC；`finish-buffer-campaign.py`等CC结束后，验证独立机制候选、父源码与最终交付，再采集真机profiling并离线核验证据。等待阶段不持卡锁，设备任务通过同一把项目锁串行。

在910B宿主仓库根目录运行以下命令，可用新输出目录独立复现最终两份源码。保留物理卡7、原36项合同、42＋12＋9项检查和每份源码一次正式评测。脚本会自动取得项目卡锁；不需要在Windows安装模型或NPU工具链。

```bash
python3 project/Ascend-Optimization-v1/tools/profiling/hgkda/reproduce-paired.py \
  --batch buffer-pointwise-20261022 --tag final \
  --output /data/hanle/ascend-optimization/runs/buffer-independent-reproduction-01
```

原实验状态和工作区不覆盖。要重新生成候选，应建新批次，并按`plan.json`复制同字节合同与起点；最终源码复现不需要重新调用CC。

## 工作流修正

本批增加了dtype数值范围门禁、同字节源码复用、控制器异常恢复和通用批次参数。控制器变量名冲突在log10_语义检查后被修复，已有工作区、检查与正式请求没有重新提交。历史失败状态、恢复前状态和等待队列调整均保留。

最终采集使用同源码的原生KGS metrics、四组成对OpProf及父版／最终版实际编译IR；48项离线核验通过。模拟器请求超时及重复请求取消单独保存，本批没有成功获得模拟器热点报告，也没有数值Roofline。长路径原始profiling由`raw-evidence/`快照保留，短路径源码、逐case结果和比较JSON直接展开；快照manifest逐文件记录SHA。
