# 启动机制系统原型与独立算子检验

本批不是旧最佳源码复现，而是冻结新方法后调用 CC＋DeepSeek 生成候选。开发对象为 `selu_`，独立算子为 `sigmoid_`；均从固定 FlagGems 提交 d6a8eec 的原始实现出发，不把历史优化源码给模型。

研究问题：**在调用路径与设备任务组织都可能影响性能时，自动干预探针能否区分原因，并指导有效代码修改？**

## 冻结与对照

`plan.json`登记源码、合同、工具 SHA、模型、预算与方法版本，`method-snapshot/`保存当次方法。两组使用相同原始探针、后端接口知识、候选机会与 KGS 合同：

- `raw_evidence`：提供原始测量，模型自行分析。
- `mechanism`：在同一测量上增加调用执行图、竞争假设及预期变化。

该对照只检验诊断表达的增量。它不是纯原生 KG 的 profiling 对照；相同候选次数也不等同相同实际墙钟成本。独立算子先运行机制组，开发算子先运行原始证据组，固定交错顺序。

首次批次 `mechanism-pilot-20261026` 因 Native 候选公共别名冲突，在零项通过时停止，尚未调用模型。v2修正ABI适配和两组共享提示，原始失败保留。

## 方法边界

当前图为 `wrapper → JIT分派 → runtime提交 → device执行 → stream完成`。关系来自实际捕获的调用和stream语义；**没有重建设备内部指令依赖，也没有测出各节点独占时间**。

第一项干预在相同编译产物、输入和stream上比较完整wrapper与直接提交，重复交错测量。所有配对收益超过1.15时支持继续检查调用分派。该阈值属于事先登记的实质变化门槛，不是统计置信水平。

大输入若具备明确的一维长度和 BLOCK_SIZE 接口，再做同JIT分派入口的分块探针。该探针同时改变block与grid，以完整任务组织为对象，不把耗时差直接归为设备内部某条流水。

补充检查覆盖三种dtype、特殊值、空输入、offset、stride、动态输入指针和stream切换；另通过Native完整合同的42项正确性和9项性能。最终调用路径检查核对候选是否真正减少暖启动JIT调用，记录同输入实际延迟。

工具入口：`tools/profiling/hgkda/mechanism/run.py`；探针、策略、候选语义检查分开保存。`results/<算子>/<反馈组>/`保存模型提示、原始响应、候选、补充语义和正式评测；`seed-probe/`保存起点探针与诊断。冻结已有批次不直接重跑，应使用新目录生成新计划。

本轮目标是完成可运行的单机制研究原型与独立检验。一次候选实验用于发现有效性与实现问题，不能据此声称相对原始证据有统计显著优势。
