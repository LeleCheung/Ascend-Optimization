# cumulative_trapezoid：下一轮先过数值，不再先调分块

本批原版正式33/33、约0.354×，但独立补充16/18，全部timing数值只有2/9。因此正式PASSED不能证明长序列分支正确，也不能作为优化版交付。FP16三个性能输入都失败，BF16三个也失败；FP32大输入4096长度另有9个元素超出既定1e-4容差。完整错误在results/cumulative_trapezoid/parent/semantics.json。

原版在FP32中直接计算(a+b)*0.5，再FP32扫描，最后将输出乘dx。这不等价于参考的Slice/Add/Muls/Cumsum：低精度Add结果先舍入到输入dtype，乘dx/2也在扫描之前；扫描输入dtype又可能改变本机CANN的加法顺序。仅增加二维tile、保持原来算式，不会修复这些数值问题。当前原版metrics的Scalar活跃98.5%是性能信息，不能替代数值修复。

下一轮的第一项实质实验应是KGS debug：用冻结oracle.py的gen_inputs生成全部9项timing输入，对比候选和oracle.run，严格按各case原始atol/rtol调用torch.testing.assert_close并输出每项结果。leaf路径来自本批plan.json中cumulative_trapezoid记录，先验证其contract_sha256。该debug检查不计分、不换参考、不改容差。候选tmp/main.py位于KG工作区，不能直接依赖check-endurance.py沿source父目录找到本批plan；可直接调用已有native_timing_inputs并按上述显式leaf读取合同。最终独立验收仍由控制器运行原检查器，不能用debug结果代替。

先分离三类差异：增量生成每步舍入、FP16扫描的真实累加策略、FP32长序列结合顺序。先读本批installed-triton-scan-sort-source.json、installed-cann-cumsum-source.json和CANN扫描实现与结合顺序.md。CANN静态源码只提供候选机制，仍需实际NPU探针对比：原dtype cumsum、先FP32 cumsum再降精度、CPU逐步FP16/FP32顺序模型，以及分组模型。不要重复上一批已失败的“增量舍入后直接FP32树形扫描必然正确”假设，也不要假设更数学精确就一定匹配本机参考的舍入。

全部9项timing数值及18项补充通过后，再优化Vector扫描与连续读写。禁止调用PyTorch cumsum/cumulative_trapezoid或FlagGems原算子作为候选数学核心。若某种匹配参考的顺序累加实现慢，也要先保留正确起点，再并行处理多条独立序列、分块缓存输入和控制舍入，而非用高分错误版本替换。
