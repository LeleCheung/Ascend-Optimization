# 设备加载与启动层分开处理

本批上采样第一轮24/24通过，但大输入候选完整调用约290ms，参考约0.2ms。CC已提交专项设备探针区分四次向量指针load、连续行加载后gather与program开销；以实际debug回执为准。不要只靠扩大分块重复同一逐lane加载路径。

探针还出现约0.1ms的launch-only设备Event区间。该计时可能混入host提交间隙，不能把它直接称为纯设备启动延迟，更不能用Event数值代替KGS完整调用成绩。先优化设备寻址，再对小输入分别检查Python/JIT调用、参数封送、分配与设备任务。

仓库已有本机验证的启动层实例：`operators/交付源码-20261023/rad2deg_/main.py`、`operators/交付源码-20261023/selu_/main.py`。其中普通Triton首次编译后复用generated launcher，后续每次仍传当前指针、shape及stream，缓存仅保存安全的编译特化与启动函数；注意输入对齐、masked尾部、dtype及布局不能沿用错误假设。先考虑固定FlagGems的libentry/安全编译缓存，再按真实证据判断是否需要直接启动函数。

上采样有独立输出，缓存不得保存输出Tensor或用过期输出指针。若实现新launch路径，须检查新分配输入、换指针、奇数形状、非连续布局、当前stream，以及真实profiler注册；不能为profiler改成另一套计算kernel。最终以完整KGS和全部计时输入数值门禁验收。以上是待实测的方法参考，不预设能达到0.8×。
