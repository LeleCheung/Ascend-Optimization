# 散射加法：由固定上游能力提出的新候选

源码只读核查发现固定FlagGems中存在Ascend向量排序接口，而不只有逐lane散射：

- `third_party/FlagGems/src/flag_gems/runtime/backend/_ascend/ops/masked_scatter_backward.py` 的 `_expand_sort_kernel` 使用 `triton.language.extra.cann.extension.sort`（`al.sort`），对FP16/FP32 key进行原生vsort，再`tl.gather`恢复原位置；注释明确int key可能在HIVM校验失败，不能直接用整数排序。
- 同文件记录 scan/transpose 派生向量直接接 gather 可能触发设备错误，必要时拆成两个kernel，经临时buffer传递；不能在本批未验证前当作已解决。
- `.../_ascend/ops/argsort.py`另有带编译源码身份的局部paired-sort lowering，不能修改共享compiler全局状态；优先直接使用已支持的`al.sort`。

可验证的新假设：末轴scatter按每行`(目标index,原位置)`排序，再分段求和，最后连续写出所有目标位置，可能避免owner方案O(width²)比较及逐lane原子。对width≤2048，`目标index*width+原位置`小于2^24，可用FP32精确编码排序键；更大范围必须重新证明，不能溢出或损失整数位。通过`sorted_key % width`恢复原位置，从已加载src向量`tl.gather`，避免随机GM读取。

分段求和和输出重建可以评估：1）同key的associative_scan；2）前缀和＋二分查找每个目标的区间端点。第二种有前缀相减抵消误差，要以完整FP32/FP16/BF16输出验证，不能因为数学等价就认定数值通过。输出必须包含原inp；存在空桶时贡献为零。排序、scan、临时buffer和所有launch都计入完整调用耗时。

这只是由现有上游源码提出的新路线，未在本批NPU验证；不能宣称已经加速。应先用小输入CPU模型和一个NPU探针验证，再决定是否投入完整候选。仅适用于真实形状条件，非末轴与一般stride保留已验证路径。

CPU预检：24组（三种dtype、四种宽度17/128/1024/2048、两个seed）在原容差下全部通过；FP32最大绝对误差约7.45e-6。输入只在CPU运行，不代表NPU编译和性能成功。原始回执为scatter-sort-cpu.json，执行源码为scatter-sort-cpu-driver.py。
