# 池化：低精度窗口位置必须匹配参考舍入

## 已确认的新失败原因

CC首轮最后源码`a74bb444...`已由Codex准确保存，30/30特殊语义通过，但原合同与独立扩展共27项中只有25项通过；失败为FP16/BF16的32³输入、16³输出计时用例。它不能作为有效交付。旧`ee9b00...`快照之后CC又修改过源码，恢复器身份检查已拒绝将旧快照当作最终源码。

Codex核对准确PyTorch提交`0fabc3ba...`的`FractionalMaxPooling.h`，参考公式为：

```cpp
scalar_t alpha = static_cast<scalar_t>(inputSize - poolSize) /
                 static_cast<scalar_t>(outputSize - 1);
sequence[i] = static_cast<int>((i + sample) * alpha) -
              static_cast<int>(sample * alpha);
sequence[outputSize - 1] = inputSize - poolSize;
```

`FractionalMaxPool3d.cpp`确实以输入`scalar_t`调用它。URL、准确原件和SHA见`fractional-reference-sources.json`。因此，不能统一把区间运算提升为FP32，也不能仅凭数学上alpha为整数就忽略随机样本。低精度中间舍入会改变某些起点，选中另一个池化窗口；这不是只需加大输出容差的小误差。

`fractional-interval-cpu-model.py`在全部9个冻结输入逐值验证：保留scalar_t舍入时，值与索引全部匹配；FP32区间模型在两个大低精度输入分别有3588/7952个值不同，其余7项匹配。CPU结果见`fractional-interval-cpu-result.json`，它不替代NPU验证。
