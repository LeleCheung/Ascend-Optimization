# cumulative_trapezoid的原生组件融合备选

纯Triton实现仍应先解决全部数值门禁，再优化扫描。如果本机tl.cumsum的Scalar化和参考舍入无法在预算内同时解决，可独立评估“Triton融合生成增量＋CANN原生扫描”这一混合实现。它是对复合算子的融合优化，不是Triton扫描backend本身变快，成果须单列实现类型。不得调用torch.cumsum或torch.cumulative_trapezoid代替候选；也不能将直接调用CANN扫描写成自研Triton扫描。

Codex只读核对本机CANN9公开头文件：`include/aclnnop/aclnn_cumsum.h`、`include/aclnn/acl_meta.h`、`include/acl/acl_base.h`，原件与SHA见installed-cann-cumsum-api.json。动态库`/usr/local/Ascend/cann-9.0.0/lib64/libopapi.so`已存在，尚未进行NPU绑定验证。无需升级固定FlagTree/CANN或安装新库。

公开接口有aclnnCumsumGetWorkspaceSize(self,dim,dtype,out,&workspaceSize,&executor)、aclnnCumsum(workspace,workspaceSize,executor,stream)；另有无dtype参数的CumsumV2版本。必须按真实头文件配置准确的ctypes签名、aclDataType枚举和返回值，不能猜ABI。输入输出用aclCreateTensor描述已有Tensor的真实shape、stride和data_ptr，输出与增量可直接分配连续张量。workspace须按GetWorkspaceSize结果分配；当前stream来自本机已有raw stream查询，保持临时张量生命周期和顺序；不缓存输入/输出数据或静态stream。先用全新executor和descriptor验证，减少复杂缓存的状态错误。

增量仍由我们自己的Triton kernel生成：先将a+b舍入到输入dtype，再将其乘dx/2并舍入到输入dtype，之后调用原生扫描，不能把dx移到扫描之后。尊重非连续输入、负dim、长度1和非二次幂dx。dtype/舍入差异必须用9个冻结timing输入及18项补充检查真实核对，不依据接口名字认定已经和PyTorch路径等价。

这一路线的潜在收益是将参考的Slice/Add/Muls/Cumsum复合流程缩成融合增量kernel＋原生扫描，必须把descriptor、workspace、分配和全部launch计入完整调用walltime。它既可能快，也可能因Python FFI开销而慢，只有实测能决定。需要确认KGS原有preflight准入接受这种原生组件融合；若不接受，保留失败，不绕过准入。不改参考或容差，不修改环境或共享服务。
