# 先验证探针，再解释性能

本知识在 scatter_add 第二批角色冻结之后补入，供后续新建覆盖层使用；不追改当前角色或历史实验。实际采用须查新批次输入来源和工具请求。

## 调试任务完成与变体正确是两个条件

原生调试任务的 `SUCCEEDED` 只说明脚本正常退出。脚本若捕获异常、保存失败记录后继续，仍可能包含编译失败、设备执行失败或错误数值。逐条检查候选的误差、输出形状/dtype、输入是否保持不变，再考虑其耗时；缺少检查字段保持“未知”，不能当作零误差。

scatter 第二批的 `34d08a487da14164ace00f667bbd277f` 正常退出，但若干原子变体有大面积数值失败，不能因它们给出了毫秒数就作为有效性能对照。原子累加探针还须保证每次测试从正确初始状态开始；重复调用会修改输出时，应核对缓冲区初始化或恢复，并将正式语义必需的初始化成本计入性能。

## 先在可信 CPU 实现上检查索引模型

连续多维 stride 的递推应乘下一维大小。`[5,7,9]` 对应 `[63,9,1]`。scatter 第一项探针 `a3e52d4fd1cc4bc18f1d85e003de3ba5` 错乘本维大小，得到 `[35,7,1]`，使九组 CPU 累加模型也大面积偏离参考。只修正该行后，九组 CPU 复核的 FP32 模型全部通过原容差。

因此，模型、参考和候选出现大误差时，先核对输入生成、布局、索引和比较容差，再讨论后端精度机制。CPU 模型通过也不保证 NPU 采用相同累加顺序，需要独立真机核对。准确原源码、单行修复及回执见 `research/scatter_add/second-pass-probe-cpu-review/`。

## 设备错误后的后续测量须重新建立有效性

同一脚本发生设备执行错误后，后续看似极快的测量不自动可信。上述两个 scatter 探针分别出现过错误后约 0.125 ms 和约 0.115 ms 的大输入记录；另一个独立任务中的有效大输入仍为十几到几十毫秒。应保留原始回执，在当前串行 KGS 调试接口中新建有数值检查的任务，验证候选和测量状态；不重启共享服务、不转到其他卡盲跑。

这些额外探针用于诊断和搜索。交付仍须通过控制器独立语义门禁、全部冻结性能输入数值检查及一次完整 KGS 正式评测，并按同 case 实际候选延迟选版。
