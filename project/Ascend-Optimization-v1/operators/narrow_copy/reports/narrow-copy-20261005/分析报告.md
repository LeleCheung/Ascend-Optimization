# narrow_copy profiling 分析

## 采集范围

本报告针对正式评测中最慢的一个代表性 workload：
`benchmark/test_narrow_copy.py::test_narrow_copy_perf::core::float16::3`。候选源码、PyTorch 基线和正式评测保持不变。`msprof` 的数据用于诊断，不能替代 KGS 的 walltime 加速比。

910B 真机为 Ascend910B4，KGS 专用端口为 `19652`。本目录同时保存 metrics 和 instruction 两级原始 JSON。

## metrics 结果

候选主 kernel 为 `_narrow_copy_flat_persistent_kernel`，AI Vector Core 执行平均 **9.61 us**（两次采集为 7.34～11.88 us）。AIV 指标如下：

| 指标 | 数值 |
| --- | ---: |
| MTE2 时间占比 | 69.1% |
| MTE3 时间占比 | 70.8% |
| Vector 时间占比 | 0.1% |
| Scalar 时间占比 | 12.9% |
| Cube 利用率 | 0% |

这说明该 workload 是纯数据搬运路径，瓶颈在 MTE2/MTE3 和固定 launch、同步开销，算术单元没有形成限制。优化方向应优先减少 kernel/program 数量、同步和边界处理开销，并让连续拷贝使用最直接的搬运路径；不应引入计算或复杂索引。

## instruction 结果

instruction 级请求先完成 metrics，再运行 Ascend AI Core simulator。共发现 2 个 kernel、2 个 simulator core、350 条指令，其中 90 条映射回候选源码。目标 kernel 有 138 条列出的指令：

- `tl.store` 对应 MTE3 指令约 9.89 us；
- `tl.load` 对应 MTE2 指令约 9.11 us；
- MTE2/MTE3 的 `WAIT_FLAG`、`SET_FLAG`、`MOV_SRC_TO_DST_ALIGN` 占据主要指令路径；
- `tl.range` 的循环仍产生每 program 的除法、取模和分支控制，但其时间远小于数据搬运；
- 模拟器报告的执行时间是诊断数据，不能与正式 eval walltime 直接比较。

因此第一轮实验假设是：减少 persistent loop 的控制与同步成本，测试更少的 program、更大的连续 tile 或直接 flat copy；每个候选都必须在完整 33/33 correctness 和 15/15 timing workload 上复验。

## 下一轮 A/B 方案

1. 固定当前候选和 PyTorch baseline，保存无 profiling 的正式结果。
2. 将本报告摘要注入 Claude Code prompt，要求只改变 narrow_copy 的连续拷贝路径。
3. 运行一轮有 profiling 反馈的 KernelGen；profile 反馈只作为诊断输入。
4. 对新候选重复 correctness、walltime、metrics；比较几何平均、最差 case 和小 shape 固定开销。
5. 如果候选仍低于 PyTorch，保留诊断证据并给出“当前 Triton 路径打不过 PyTorch”的结论，不把 simulator 或 msprof timing 当作加速比。
