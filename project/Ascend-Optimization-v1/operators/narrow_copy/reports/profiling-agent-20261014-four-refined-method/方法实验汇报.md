# narrow_copy 方法生成实验

CC+DeepSeek 从固定纯 Triton 起点生成了有效的小输入 CANN DMA 候选，33/33 完整通过。最终两次相对 PyTorch 为 **1.121907×、1.118180×**，取较慢值 **1.118180×**；本批起点 **0.798135×**，最终提升 **40.10%**。

第一轮新增正确六参数 ABI 的 `aclrtMemcpyAsync`，对连续单段、`pre==1`、输出元素数不超过65536的输入走 D2D；源偏移为 `start*post*element_size`，`destMax` 和 `count` 都为输出字节数，当前输入设备 stream，不同步。库不可用回退 Triton，非零返回报错；大输入内核与分块保持父版本。第一轮初测1.125×并采纳，最终成绩以上面的两次复验为准。

第二轮把多行尾切片错误地当作整段连续，完整评测失败，未采纳。独立源码审查另提供 `[2,4]` 输入沿dim=1取start=2、length=2的反例：应复制索引 `[2,3,6,7]`，候选却复制 `[2,3,4,5]`。实际 `_DMA_MAX_ELEMS` 也仍为65536，与模型声称提高到8388608不一致。原响应和候选保留，具体反例见 `round-02/source-review.json`。

最终保留第一轮，SHA256：`2a6e306866509369b33bdfc9419010f97019e95b88c6999e661fe3c37525d070`。已核验两份实际模型源码、两次完整复验及 16 份真机附件；物理卡7、KGS19657，计时为 **device_task，包含 DMA 与 kernel**。原始状态、失败评测与独立审查分别保存，未改写失败轮的记录。

当前分析依据是逐 case 设备任务延迟、实际执行路径、源码及真机指标，数值 Roofline 尚未建立。历史最佳源码复验1.105×另行记账，本批是重新生成源码后的实际成绩。
