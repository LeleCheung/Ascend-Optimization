# 汇报口播与数字口径

## 第一部分：方法与算子例子

可以这样讲：

> 我们把老师提供的 PyTorch 与候选实现成对 profiling 流程接入了 HG-KDA，并补上了可复用的指标聚合与差异计算。脚本整理搬运量、搬运指令数、Vector／Scalar／MTE 时间、等待和冲突，并计算平均搬运粒度；另外把源码、编译 IR、实测指标和经验参考组织成结构化证据，也加了候选 kernel 的热点指令筛选和源码映射。Agent结合这些证据与算子知识提出修改，再由 KGS 的完整正确性和性能合同决定是否保留。

> 以 `matmul_bias_activation` 为例，候选与 PyTorch 在同输入下采集指标，Agent选择源码、IR、成对指标和热点工具，再选择相邻输出块复用 B 的方案。候选通过42项正式测试及18＋24项补充检查；同批15个case的实际设备延迟改善1.023倍，KGS完整调用相对PyTorch为0.884倍。它证明这条分析与验证流程能运行并复现已有有效方法，不是全新自动发现；目前该候选仍略慢于PyTorch。

不要说：

- “HG-KDA已经建立了定量Roofline”。现在有经验Roofline参考和结构化分析，物理峰值及定量 component Roofline 尚未建立。
- “指令热点就是完整硬件关键路径”。当前是按候选kernel筛选、排序指令并映射到源码；矩阵乘演示中的模拟器只留下部分证据。
- “Agent独立完成了所有诊断与优化”。KG、CC／DeepSeek、HG-KDA知识、Codex诊断／修复共同参与，具体归属按算子记录。
- 将经验阈值说成性能定律。它们用于提出需要验证的方向，不直接证明因果或最优方案。

## 第二部分：算子结果

- 会议指定10项：7项默认条件超过0.8×，1项在官方确定性条件下超过0.8×，另2项的PyTorch默认参考包含CPU回退，已经完成补充NPU分解对照。不能说“10项全部按默认原生NPU参考达标”。
- `cumulative_trapezoid` 的0.812×仅适用于隔离进程启用官方确定性算法的合同；默认参考存在同输入重复运行不自洽问题。
- `fractional_max_pool3d` 的17.683×和 `_conj_physical` 的47.170×是相对含CPU回退的PyTorch参考。另做的10.066×和2.296×使用项目自建NPU原语分解参考；不是官方原生单kernel结果，也不应替换默认验收分数。
- 性能比0.8×表示通过本项目门槛；1.0×才表示达到或超过PyTorch。不要把0.8×说成快于PyTorch。
- `selu_` 在会议10项表中为0.837×；另一个扩展批次报告0.898×。来源分开列，不跨批次平均。
- FlagGems固定提交 `d6a8eec473517a3d68157b208eb9c057eb1d4c50`；FlagTree `0.6.0+ascend.gitc286cba6`；SGLang固定提交 `938612058a981487e439da514df7d1371cf31e68`。
