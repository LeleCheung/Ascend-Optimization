# 性能分析工具演示：成对指标对比与指令热点

建议本次演示只讲这两个工具，总计约五分钟。Roofline放在方法页作为补充，不现场展开校准。

这是一套能在Windows控制端直接运行的离线演示：读取已归档的真机CSV和模拟器指令报告，重新调用现有分析工具。不会连接服务器、占用NPU或调用模型。图片由本次重新计算的结果生成，是结果展示图，不冒充终端或真机采集截图。

## 一、现场操作

在项目的 project/Ascend-Optimization-v1 目录打开终端，执行：

    python "operators/汇报材料/工具演示-20261029/演示性能分析工具.py"

脚本默认在演示目录中新建带时间戳的输出目录，不能覆盖已有目录。仅依赖Python与生成图片用的Pillow，离线分析无需torch、NPU或msprof环境。

只演示某一项可分别执行：

    python "operators/汇报材料/工具演示-20261029/演示性能分析工具.py" --part compare
    python "operators/汇报材料/工具演示-20261029/演示性能分析工具.py" --part hotspots

如果服务器采集不便、网络不稳定，直接使用已验证输出目录中的运行日志、JSON和两张图片即可。现场重新执行脚本则能展示输入、计算与结果的真实过程。

## 二、演示1：成对指标对比（约两分钟）

### 展示顺序

1. 打开输出目录下“成对输入”中的 spec.json：显示log10_、4096×4096、FP16以及源码SHA。
2. 展示两侧 OpBasicInfo.csv、Memory.csv、PipeUtilization.csv。原文件从LFS归档定向读取，先验证整个归档及19个输入文件的SHA和长度。
3. 运行现有 compare_opprof.py，展示“成对演示运行日志.txt”或“01-成对指标对比.png”。
4. 如老师追问其他流水指标，打开“成对完整结果.json”，查 differences、reference.tables、candidate.tables，不只展示三个派生数字。

### 应看到的结果

| 指标 | 候选 | PyTorch | 候选/PyTorch |
|---|---:|---:|---:|
| GM→UB搬运量（CSV字段KB） | 32768 | 32768 | 1.000× |
| AIV MTE2搬运指令数 | 2036 | 760 | 2.679× |
| 每条平均搬运（十进制kB） | 约16.48 | 约44.15 | 0.373× |

CSV里标作KB的量按原比较脚本乘1024转成字节；平均搬运粒度展示为十进制kB/条（除1000），所以旧PPT近似写16.5/44.2。若改用KiB/条（除1024），则为16.09/43.12。只是单位换算不同，不是新测量的性能波动。

### 口播

“这一步把老师提供的成对分析方法接入了当前流程。脚本自动核对输入、设备和kernel，聚合指标、计算差异。这个例子两边读取量相同，但候选用了约2.68倍搬运指令，每次搬得更小，所以Agent应该结合分块、连续访问和编译IR检查搬运组织。”

这里是历史种子的诊断数据，不是当前最终0.875×源码的采集。不会把种子证据改写成最终版本的证据。计数差异提示排查方向，不能单独证明带宽饱和。

## 三、演示2：指令热点与源码关联（约两分钟）

### 展示顺序

1. 展示原报告 a008-ascend-instructions.json，它包含92条指令，其中72条带源码映射。
2. 脚本读取同次KGS请求中的实际源码，通过已有 hgkda_adapter.py::instruction_hotspots 匹配 _rad2deg_kernel，按每核指令报告时间、cycles降序排序，保留前12条。
3. 展示“热点演示运行日志.txt”或“02-指令热点与源码.png”，再打开“热点关联源码.txt”，看第54、55行。

### 应看到的前五条

| 排名 | 指令 | 累计模拟器报告时间 | 源码位置 |
|---|---|---:|---|
| 1 | BAR | 25.61 μs | 第38行，kernel函数定义 |
| 2 | WAIT_FLAG | 17.03 μs | 第55行，tl.store |
| 3 | BAR | 15.22 μs | 第54行，乘法与类型转换 |
| 4 | BAR | 11.46 μs | 第54行，乘法与类型转换 |
| 5 | MOV_SRC_TO_DST_ALIGN | 8.57 μs | 第55行，tl.store |

以上各指令地址的记录均执行22次。时间是按指令地址聚合后的累计模拟器时间，不是单次执行延迟，不能相加成真机总耗时。

### 口播

“上一项告诉我们指标哪里不同，这一项把排查范围缩小到具体指令及源码。厂商工具和KGS已经提供指令及源码关联，我们新增的是候选kernel匹配、无关kernel过滤和每核热点排序。这里等待和搬运映射到写回行，其他同步热点还指向计算与函数入口，Agent可以据此优先检查相关依赖。”

表中是严格前五条；此前仅列BAR、WAIT_FLAG、MOV三条是代表性热点，不能称严格Top3，也不能说全部都已定位到写回。

本例来自历史诊断候选，不是当前1.117×交付源码，不以此报告证明最终版本的因果改善。

## 四、老师可能追问

- “今天重新跑了模拟器吗？”：没有，今天重跑的是已有报告的分析。原始采集由msprof op simulator执行，厂商工具提供指令观测与源码映射，KGS解析；本次离线调用项目筛选脚本。
- “最后谁判断怎么优化？”：脚本提供可核对的指标与热点，Agent结合源码、IR和分类知识提出假设，优化后仍需真机KGS完整验证。
- “跟老师的工作相比加了什么？”：复用成对采集思路，增加指标聚合/差异/搬运粒度计算、一致性校验、候选kernel热点筛选和统一证据输入。没有把厂商源码符号化或KGS解析器算成我们新写的能力。

## 五、输出文件

- 成对完整结果.json：原比较脚本的完整输出，含流水、搬运和其他已采集指标。
- 成对演示核验.json：运行命令、返回码、输入SHA、摘要与来源范围。
- 热点完整结果.json：现有函数输出的每核前12条、指令与源码映射。
- 热点输入源码.py、热点关联源码.txt：同次请求中的候选源码及带行号版本。
- 两份运行日志.txt：本次真实离线计算的命令及结果。
- 两张PNG：可直接插PPT的结果展示图。
- 运行状态.json：执行时间、演示脚本SHA、完成状态。
