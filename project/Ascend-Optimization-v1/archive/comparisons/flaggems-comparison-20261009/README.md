# FlagGems 原版与当前候选对照（2026-10-09）

> 历史联合对照：五个对象的 Excel 华为列均已超过 0.8×，本批次作为复现与方法参考保留，不计入新目标成果。各算子归档原因见 [归档索引](../../README.md)。

后续三项修复与三轮复测已完成，见 [最终修复报告](../flaggems-repaired-comparison-20261009/validated-v5/README.md)。PReLU 旧候选约 2.82× 在重复测试中出现 FP32 精度失败，新候选修复后相对 PyTorch 为 0.95×；下面表格保留本批次的单轮历史结果。BatchNorm、SmoothL1 相对本机修复版 FlagGems 的直接倍数分别为 2.19×、1.61×。

**MSE 和 `t_copy` 已确认超过当前 FlagGems 原版，分别加速 1.20× 和 1.73×。** 五个候选均通过完整评测；PReLU、BatchNorm 和 SmoothL1 的原版在本机测试合同下存在正确性问题，候选同时包含修复，不能把这三项只写成性能提升。

基线是 **910B 上的 PyTorch + torch_npu**。使用现有 KG/KGS 评测体系：KG 保存生成/适配后的候选，KGS v6.5.0 的 FlagGems adapter 执行正确性与计时。本轮固定已有候选做对照，没有重新生成候选，也没有测出独立 Profiling Agent 的增益。

## 实测结果

| 算子 | 原版相对 PyTorch 加速比 | 候选相对 PyTorch 加速比 | 候选相对原版加速比 | 正确性通过数：原版 → 候选 |
|---|---:|---:|---:|---|
| `mse_loss_backward` | 1.11× | **1.34×** | **1.20×** | 27/27 → 27/27 |
| `_prelu_kernel_backward` | — | **2.82×** | — | 3/21 → 21/21 |
| `t_copy` | 1.96× | **3.43×** | **1.73×** | 9/9 → 9/9 |
| `batch_norm_backward` | — | **5.03×** | — | 9/30 → 30/30 |
| `smooth_l1_loss_backward` | — | **3.48×** | — | 290/291 → 291/291 |

倍数越大越快，1× 表示持平。原版未完整通过正确性时，不给出有效性能胜出结论。五个候选共通过 378 项正确性、57 项计时，合计 435 项。

相对 PyTorch 的数值采用 KGS 计时用例加速比的几何均值。相对原版的数值按相同用例的 **原版实际延迟 / 候选实际延迟**逐项计算几何均值，不能简单相除前两列。MSE 在 15 项计时中赢 12 项；`t_copy` 赢全部 6 项。两项对应的 PyTorch 基线漂移几何比为 0.995 和 0.984。

## 代码区别

| 算子 | FlagGems 原版 | 当前候选的关键变化 |
|---|---|---|
| MSE backward | 元素融合，block 最大 1024 | block 最大 8192；连续输入快路径，广播/stride 回退；对齐 ATen 计算顺序；缓存编译后的 launcher |
| PReLU backward | 权重按末维索引，权重梯度与输入同形状 | 按通道维索引并归约到权重形状，适配本机 NPU 接口；融合输入梯度和部分归约，分块完成权重梯度 |
| `t_copy` | 已有 32×32 二维分块转置 | 按 dtype/形状选择 tile；一个 program 处理多个 tile；整除时省去 mask；使用 `tl.trans` 和 launcher 缓存。分块转置本身原版已有 |
| BatchNorm backward | 每通道一个 program，直接使用 `save_invstd` | 小形状融合、中形状分块循环、大形状分阶段归约；限制 tile 的 UB 占用；按本机保存方差的语义计算 `rsqrt(var+eps)` |
| SmoothL1 backward | block 1024，beta 除法和条件选择 | block 4096，编译期 beta 倒数和梯度截断；显式处理 beta=0，修复输入相等时的 NaN |

PReLU 的首个失败是权重梯度形状 `[1024,1024]` 与参考 `[1]` 不一致；BatchNorm 有 21 项数值失败，涉及保存方差与标准差倒数的接口语义；SmoothL1 唯一失败是 `beta=0` 且输入等值时产生 NaN。具体用例和错误保存在 [comparison.json](comparison.json)。

五份活动原源码均与锁定上游对应文件逐字节一致，五份候选均不同于原版。MSE、PReLU、`t_copy` 原文件已标注 `Generated by KernelGen`，这些现成实现本身也可能是 KG 产物。本轮确认的是当前候选相对它们的变化，不能把五个加速比统一归因于自研 Profiling Agent。

## 计时与测试合同

- 实际计时是 FlagGems 默认 **kernel 模式**，使用 Ascend `do_bench_npu` 测设备侧耗时。它先尝试 mspti，不可用或失败时回退到 torch_npu profiler。
- **KGS 的 `timing=walltime` 不会改变此 adapter 的 benchmark 模式。** 原执行脚本和原 `environment.json` 中的 walltime 注释有误，已在 [timing-audit.json](measurements/timing-audit.json) 更正；原请求与原结果保留。不能据本轮数字推断 Python 调用或 host launch 开销的收益。
- 请求为 warmup 1000 ms、benchmark 100 ms、num_trials=1、timeout 1500 秒；Ascend kernel 分支没有使用前两项，实际采用 `do_bench_npu` 默认 warmup=5、active=30。
- 双方使用同一 binding、测试合同和请求参数，在同型号 910B4 的不同 NPU 上顺序执行。这是单轮复测，设备号和逐项 PyTorch 延迟均已保存。
- 正确性与计时项分别为 MSE 27+15、PReLU 21+9、`t_copy` 9+6、BatchNorm 30+15、SmoothL1 291+12。
- 本机已有测试适配由双方共同使用：PReLU 通道数按第 1 维；BatchNorm 保存方差取正值；benchmark 使用 case API。实际测试、benchmark、计时源码及上游差异见 [contracts](measurements/contracts)。

PReLU 首次原版评测因 KGS loader 的公共符号冲突失败。补测仅追加具名 `run` 包装，保存原函数私有别名，并让公共符号指向同一包装；没有修改原内核。最终采用 [prelu-retry](measurements/prelu-retry) 结果，首次入口失败也保留。

`t_copy` 候选的直接 launcher 使用 Triton 内部接口，缓存键尚未包含设备编号；本轮每个评测进程绑定一张卡，常驻多卡进程复用前需补齐该缓存键。launcher 缓存的 host 收益需另做端到端计时。

## 复现

在 910B 的 Git 仓库目录执行。运行环境与历史实验目录位于仓库外层 `runtime/`，FlagGems checkout 位于外层 `FlagGems/`：

```bash
cd /data/hanle/ascend-optimization/Ascend-Optimization
../runtime/kg-controller/venv/bin/python \
  project/Ascend-Optimization-v1/tools/evaluation/compare-flaggems-910b.py \
  --root /data/hanle/ascend-optimization \
  --output /data/hanle/ascend-optimization/runtime/kg-controller/runs/flaggems-comparison-new
```

脚本默认使用现有独立 KGS `127.0.0.1:19654`；输出目录须为新目录。它依赖服务器上的历史候选运行目录及运行配置中记录的 Catalog 路径，单独克隆 Git 源码尚不足以运行此命令。这些服务器运行资料与已删除的仓库 square/softmax Catalog 无关。本轮实际执行的两个脚本也保存在 [executed-scripts](measurements/executed-scripts)。2026-10-09 本地脚本和报告已按用途归组，新的目录结构尚未同步服务器。

原始数据归档后，在 Windows 或 910B 的仓库根目录重新核验并汇总：

```bash
python project/Ascend-Optimization-v1/tools/evaluation/summarize-flaggems-comparison.py \
  project/Ascend-Optimization-v1/archive/comparisons/flaggems-comparison-20261009
```

本轮主运行为 `flaggems-comparison-20261009b`，PReLU 包装补测为 `flaggems-prelu-comparison-20261009c`，均已完成；日志见 [logs](measurements/logs)。
