# PReLU 归约精度问题

PReLU 的第一版接口修复补上了权重梯度归约，但第二轮完整测试在 BF16 大形状上失败。原因是测试中的 `use_gems` 接管了 `torch.sum`：FlagGems 第一阶段虽然用 FP32 累加，却将部分和保存为输入 dtype，第二阶段再读取这些已舍入的部分和。

低精度问题的修复保持原始逐元素乘积，使用 `sum(dtype=torch.float32)`，归约完成后才转回权重 dtype。直接改成 FP32 乘法会改变参考要求的乘积舍入，诊断中也出现不通过，因此没有采用。

固定形状 `[16,7,57,32,29]`，BF16/FP16 各 8 个 seed，诊断结果如下：

| 实现 | 原生环境 | `use_gems` 环境 |
|---|---:|---:|
| 第一版接口修复 | 16/16 | 12/16 |
| FP32 逐元素临时缓冲 | 16/16 | 16/16 |
| 保留原缓冲，仅指定 FP32 归约 | 16/16 | 16/16 |
| 现有优化候选 | 16/16 | 16/16 |

未放宽测试容差。此表用于定位精度问题；最终性能和完整 workload 正确性以三轮 KGS 评测为准。

完整测试又在超大 FP32 输入 `[16,128,64,1280]` 上发现一般树归约的舍入误差：绝对误差 0.00317，相对误差 1.76e-6，超出原容差 1.3e-6。TwoSum 误差补偿基线随后通过三轮测试，但归约开销较大。

轻量分阶段归约试验中，旧候选第二轮在 FP32 输入 `[1024,1024]` 上失败，相对误差约 7.19e-6。因此旧候选约 2.8× 的数字不作为稳定成果。最后保留补偿基线，并为候选加入融合的 TwoSum 部分归约与补偿最终归约；双方完整通过三轮，候选相对修复基线为 1.97×，相对 PyTorch 为 0.95×。性能损失来自本轮新增的稳定归约路径，完整证据见 [最终复测](../validated-v5/README.md)。所有尝试保留独立源码与批次。

原始调试请求和结果分别在 [首次诊断](prelu-bf16/)、[环境对照](prelu-context/)、[最终归约修复诊断](prelu-fp32sum/)。机器可读汇总见 [precision-summary.json](precision-summary.json)，实际 FlagGems 归约源码见 [flaggems-sum-source.py](flaggems-sum-source.py)。
