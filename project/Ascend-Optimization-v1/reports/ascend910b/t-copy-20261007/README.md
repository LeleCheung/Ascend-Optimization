# t_copy 优化报告

## 结论

`t_copy` 在 Ascend 910B 上已完成一次正式 KG 闭环：正确性 `9/9`，性能 `6/6`，全部 workload 通过，几何平均加速比为 `2.007x`。不过这个总数主要来自 `64x64` 小尺寸；`4096x4096` 大尺寸候选仍比 Aten 原生实现慢 `28%~35%`，因此当前版本可复现但不是大尺寸最终优化版。

## 候选

二维输入使用 Triton `32x32` 分块加载、`tl.trans` 转置后连续写回；零维和一维输入使用扁平复制 kernel；其他维度按原算子语义报错。候选没有调用 PyTorch 算子作为后门，也没有主机同步。

## 正式证据

- 910B workspace：`runtime/kg-controller/runs/t-copy-noprofile-63c4721c/`
- 状态：`SUCCEEDED / COMPLETED`
- 正确性：`9/9`
- 计时：`6/6`
- 总 workload：`15/15`
- 几何平均加速比：`2.007467776x`
- 最差 workload：`bfloat16, 4096x4096`，`0.653x`
- 代码审查：完成，无阻断问题

## 逐类结果

小尺寸 `64x64` 的 fp16、fp32、bf16 分别约为 `5.69x`、`6.30x`、`5.86x`；大尺寸 `4096x4096` 分别约为 `0.660x`、`0.723x`、`0.653x`。这说明当前瓶颈是大尺寸下过多的小 tile 和转置布局转换，而不是正确性或 KGS 故障。

## 后续

下一轮应保持索引使用 `tl.int64`，并测试更大的 tile 或每个 program 处理多个列块，重点改善 `4096x4096`。当前评测的候选索引计算仍是 32 位，超大张量存在潜在溢出风险；正式交付前应修正并重新评测。
