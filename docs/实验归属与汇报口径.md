## 版本归属

历史优化中，Codex参与过profiling解读、瓶颈诊断、优化建议和源码修复。因此，不能仅凭`--profile`开关，将历史成绩称为“纯原生KG无profiler／有profiler”的独立效果。

后续面向用户的简洁汇报默认列“FlagGems实测”和“当前优化版”，不默认展开“KG原生无profiler／有profiler”两列。当前优化版可以来自KG、HG-KDA、CC/DeepSeek与Codex共同完成的工作；应在来源说明中写明实际贡献，不能把Codex参与后的成绩归为HG-KDA自动工作流独立取得。

详细实验仍保留`kg-no-profile`、`kg-profile`、`HG-KDA`等模式、原始源码、分析调用和追加修复的记录。模式名表示运行配置，不自动证明模型之间没有外部建议，也不自动证明profiling指导了代码修改。

本轮`night-20261021-v3`确有单独运行、冻结输入的原始KG对照组。它们与后续Codex修复分别记账，不因统一汇报列名而抹去这项区别。最终value交付来自KG无profiler生成版加Codex布局修复；最终MoE交付来自HG-KDA生成版加Codex布局修复。原始五份扩展语义失败继续保留。

### 2026-10-22 对象更正与后续重点

会议目标按用户更正登记为`_conj_physical`。固定源码中它和`conj_physical`是不同接口：实数输入时，前者分配新张量并复制，后者直接返回输入；共轭位及布局处理也不同。此前`night-20261021-v3`测试的是`conj_physical`，14/14不能移作`_conj_physical`的通过证据。保留旧批次名称和字节，为正确目标另建合同与复测。

会议表按当前可交付性排序：有效交付 → 已有通过候选但未达标 → 原版通过且可直接优化 → 正确性或编译待修复 → 参考路径或目标接口待建立。排序描述当前证据完备程度，不表示保证实现难度或下一项运行顺序。

FlagGems-SGLang后续活跃优化对象只保留`gelu_and_mul`。其他四项退出日常待优化汇报：`moe_sum_reduce`保留为已交付成果；`per_token_quant_int8`、`rotary_embedding`保留为原版通过且已超过PyTorch的体检记录；`silu_and_mul_masked`保留为待核对组合参考口径的观察项，不根据28.947×宣称优化充分或完成公平性能验收。这里的归档指停止主动优化和日常重复汇报，暂不移动原始证据目录；用户要求全表时仍可列出全部五项。

## 数值与复测

- 后续默认一次完整评测，不再默认安排两次独立复验。更改既有工具的复验次数前，应同步调整相应验收门禁；本文件本身不修改运行脚本或历史合同。
- 已经存在的两次同源码、同合同、同计时范围的完整有效结果，在简表中取几何平均，只显示一个数；原始两次测量不删除、不覆盖。不能先对四舍五入后的展示值求平均。
- 正确性、编译失败或参考包含CPU回退时，写明状态，不用失败用例中的局部性能代表全组。
- Excel历史记录、当前固定版本实测分别列示。设备kernel计时、含DMA的设备任务计时、含host和device的完整调用walltime不混用。
- 相对FlagGems的提升由同case实际延迟比较得到，不能用两组相对PyTorch的汇总成绩相除代替。
