# Triton候选与CANN参考硬性规则

2026-11-02用户澄清原目标：**baseline使用CANN原生库或来源明确的Ascend C实现；我们优化和交付的候选必须严格使用Triton。** 此前把候选改写为Ascend C，是执行方向偏离，不是用户要求放宽实现语言。

## 角色与实现边界

|角色|允许的实现|用途|
|---|---|---|
|性能baseline|优先同语义CANN原生库；也可使用来源、版本及构建明确的Ascend C参考|成对profiling、执行路径对照和性能比较|
|优化候选|严格Triton|我们优化、评测和交付的算子实现|
|正确性参考|原冻结PyTorch语义、输入、容差及补测；同时核验CANN／Ascend C参考自身资格|检查精度、布局、别名、状态及特殊值|

1. **候选的实际设备计算和数据搬运必须由Triton kernel完成。** 包括逐元素计算、复制、填充、归约、扫描、布局转换，以及快路径、尾部和回退分支。
2. 禁止用自写Ascend C、自定义外部设备库、CANN／aclnn目标算子、`aclrtMemcpyAsync`等原生DMA复制、PyTorch目标算子或CPU计算代替候选的任何计算／搬运路径。把这些路径包在Triton或Python入口中，仍不符合严格Triton要求。
3. Python／C++只可承担张量分配、元数据和视图管理、编译缓存、参数打包、随机生成器状态管理、当前stream及Triton启动等宿主胶水；不得承担目标算子的数值计算或数据搬运。仅用C++启动Triton核，不等于改用Ascend C。
4. Triton编译器正常生成的C++启动器、IR和硬件指令属于工具链；不得通过外部设备二进制或手工替换生成代码绕过Triton实现限制。参考侧的厂商代码和候选侧的Triton代码分别保存、分别标注。
   用户同日进一步确认DMA边界：Triton的`tl.load`／`tl.store`经编译器生成硬件DMA搬运符合要求；宿主直接调用`aclrtMemcpyAsync`完成复制不符合要求。限制的是绕过Triton实现算子，不是禁止硬件使用DMA。
5. 某条路径Triton难以达标时，继续优化Triton，或如实记录正确性／性能／工具链限制；不得自动切换为Ascend C、CANN或DMA来凑过验收线。

## 实验与验收要求

- 固定FlagGems、FlagTree、CANN、输入、容差、计时范围及候选源码。性能baseline与候选不能混淆。
- CANN／Ascend C参考必须先通过同语义资格检查；单接口、转换／状态适配、组合参考分开记录。没有合格原生参考时保留参考缺口，不擅自替换目标语义。
- 候选先进行逐路径后端审查，再进入KGS完整评测、补充检查和profiling。所有实际执行分支均须满足Triton要求，不能只检查文件后缀、入口名称、`backend`标签或是否导入了Triton。
- KGS的`PASSED`只证明相应测试通过，不自动证明候选是严格Triton。现有历史控制器尚未统一实现这项后端门禁，执行者必须先完成源码及调用路径审查；不得直接续跑会生成或选中Ascend C候选的旧夜间流程。
- 只把符合以上实现边界、完整正确性与补测通过、相对合格参考加速比超过0.8×的候选计为当前目标达标。超过1×才表示快于该参考。
- KG、CC／DeepSeek、Codex和HG-KDA知识库均遵守同一限制；性能证据和历史成功经验不能覆盖这条硬约束。

## 历史成果如何处理

原始源码、请求、结果和SHA保留，另行标注适用范围，不删除或重写原始证据。

- 含Ascend C、CANN扫描或DMA等路径的历史候选只保留为混合后端历史实验或机制参考，不计入当前严格Triton交付。
- 即使保留Triton回退，只要快路径使用Ascend C／CANN／DMA，该候选也不符合要求。
- 此前“25/30项CANN对照达标”“原10项7项、新20项18项”的统计包含混合后端，**不得继续作为严格Triton达标数量引用**。原PyTorch口径的历史总数也须重新审查候选后端，不能直接沿用。
- 后续从可追溯的严格Triton源码重新选种子、优化和评测，重新建立10＋20总表。严格Triton最新达标数在完成该审查前标为“待重建”，不从旧总数简单扣减推算。

这条规则优先于本项目历史计划、知识库、角色提示词和控制器中的相冲突描述。后续只有用户明确变更要求时才能调整。
