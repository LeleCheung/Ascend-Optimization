本次整理只操作 `/data/hanle/ascend-optimization/`。宿主机 `/root`、共有容器与镜像保持原样。获准使用的物理 NPU 为 6、7，当前选择 7，服务中显示为逻辑 `npu:0`。

```text

│   ├── third_party/FlagGems/        固定 master 源码，不是 submodule
│   └── project/Ascend-Optimization-v1/
│       ├── operators/              当前三算子的候选、脚本与正式结果
```

`runtime` 是运行条件，`runs` 是实际执行产物，Git 仓库保存交付源码与正式证据。正式结果已经导入 `project`，运行目录不要求 Windows 复制。旧报告内的路径、提交号和 profiler 原始附件保持采集时内容，不批量改写。

## 固定 FlagGems

主线使用 `d6a8eec473517a3d68157b208eb9c057eb1d4c50`。源码随总仓库提供，`manifests/flaggems-master-files.json` 保存逐文件 SHA，不再需要在仓库旁手动克隆一份 FlagGems。

控制端或 910B 均可执行 `python3 project/Ascend-Optimization-v1/tools/environment/verify-flaggems-snapshot.py`，检查 6,352 份文件的字节及 Git 跟踪清单。导入新快照时，上游已跟踪但被自身 `.gitignore` 忽略的文件也必须加入总仓库；不要仅凭一次 `git add` 判断导入完整。

narrow 的评测副本只修改 case API 和 DMA CSV 空名称解析；算子代码、用例范围、计时计算保持原合同。可从仓库生成：

```bash
root=/data/hanle/ascend-optimization
repo=$root/Ascend-Optimization
project=$repo/project/Ascend-Optimization-v1
python3 "$project/tools/environment/prepare-narrow-runtime.py" \
  --repo "$repo" --output "$root/runtime/flaggems-narrow-device"
```

生成器核验完整 master 源码，并要求两个适配文件与 `operators/narrow_copy/reports/device-timing-contract-20261010/` 中的归档字节一致。输出目录已存在时拒绝覆盖。

KGS 原生接口要求评测树有 Git HEAD 且源码干净，因此生成器在这个 `runtime` 副本内建立临时 Git 快照。它不设远端、不独立更新，也不是 submodule；唯一维护和同步的主仓库仍是 `Ascend-Optimization/`。删除运行副本后可按上面的命令重新生成。

历史源码可从本仓库 Git 历史恢复，无需长期保存一个完整 `FlagGems-historical/`：

```bash
git archive 0008e8a8abf78f37ffd848fad0e84a8b0e2b3a10:third_party/FlagGems \
  | tar -x -C /新建的历史复现目录
```

该快照对应历史上游 `4772d816bc5d52d37c4718f36adf377d81261f83` 的仓库导入版本，历史修复与评测合同仍在 `project/.../archive/` 中。

## 启动与评测

在宿主机运行以下脚本，复用已配置的 `tle_yy` 容器：

```bash
bash "$project/tools/environment/start-project-services.sh" "$root" tle_yy 7
tmux list-sessions
```

19655 使用未修改的固定 master，19657 使用 narrow 的设备任务计时副本。两个服务都只看物理卡 7；评测依然必须串行提交，避免互相干扰。启动脚本遇到占用的端口或同名会话会停止，不替换他人的服务。

在容器内使用 `tools/evaluation/evaluate-operator.py` 完整复验。amin 和矩阵乘使用 19655、`device_kernel`；narrow 使用 19657、`device_task`。最终源码、27/42/33 项完整合同和命令见 [复现与交接](../project/Ascend-Optimization-v1/tools/evaluation/复现与交接-20261010.md)。

KG 运行器从自身位置定位仓库源码，默认评测端口 19655；新任务通过 `KG_RUN_ROOT` 选择新批次的 `runs/<批次>/kg-runs`。narrow 应显式指定 19657。运行器读取 CANN 官方 `set_env.sh`，不再依赖其他人的 `/data/yy/kgen/kernelgen/env.sh`。
