# 下一阶段：模拟器驱动的attention优化与Agent收益验证

日期：2026-11-12，路线口径于2026-11-16补充。状态：开发决策与执行计划，尚未执行新attention任务或接入新Harness。

## 工作中心

研究现有Agent在复杂算子优化中的诊断不足，通过模拟器提供热点区域、显式等待和空闲等证据，关联源码、实际IR及设备profiling，并以真机测试验证优化结果。方法分为两条共享证据入口、分别评估的路线：

1. **编译优化线：Triton源码 → 单算子IR → 通用编译pass。** 若改动可由Triton表达，先改Triton源码；若证据指向特定算子的生成IR异常，研究单算子IR变换；若多个算子反复出现相同的编译缺陷，再研究通用pass。
2. **能力扩展线：Triton kernel → custom op → Ascend C。** 当目标硬件操作无法通过现有Triton语义和编译pass表达时，评估已有builtin/custom op；没有可复用实现时，再研究Ascend C custom op。该路线是独立的混合实现研究分支，不属于严格Triton交付。

论文核心问题是：额外白盒证据如何改变Agent的瓶颈判断和路线选择，以及在相同资源约束下是否改善最终性能、达标率和优化成本。算子性能分析已有大量研究，工作定位应聚焦于“执行证据如何映射到可执行的修改层次，并改善Agent决策”，而不是声称首次进行算子性能分析。

## 范围调整

- 主线优先考察[CANNBench Level 4的attention相关任务](https://cannbench.com/benchmarks)。实际任务名、版本、参考、硬件支持、测试合同、许可及提交要求先核验，不预设任务已可在910B运行。
- 调研KernelBench的任务组织、测试及论文比较口径；暂不同时展开第二套大规模优化任务。
- 现有FlagGems 30项维持原始合同和26/30交付记录，剩余四项保留问题，不把继续冲刺30/30作为默认工作。FlagGems／FlagGems-SGLang原生测试与PR准备作为独立交付支线。
- 早期九项不恢复新实验；历史资料可只读追溯。
- 不以知识库扩展作为独立主目标。现有核验、去重及检索能力继续维护，后续评估外部分享的经验资料和适用条件。

## 第一项工作：任务与证据可行性预研

先确定一个能检验模拟器价值的attention任务，再开展连续优化；不先做大规模插件重构或无目标的算子批量评测。

1. **只读整理既有trace。** 优先读取log10_区域方法实验，列出每次修改使用了哪些证据（成对profiling、模拟器、IR或人工／Codex诊断）、提出了什么机制假设、CC实际修改什么、指标和完整性能如何变化。标明证据参与了决策还是经受控实验验证了因果贡献；不能仅凭先后关系把收益归因于模拟器或成对profiling。保留无收益与失败案例，不重复设备测试挑选正结果。
2. **筛选attention任务。** 固定基准仓库版本，整理实际算子名、数学语义、形状／dtype／布局、参考实现、完整验收方式、910B可运行性、模拟器采集能力与成本。优先选择具有明确数据搬运、同步或流水组织问题且能完整验证的任务。
3. **选定一个试点。** 先跑通参考与起点候选的完整测试，再对代表case采集真机profiling及模拟器CSV／trace，核对源码、kernel、硬件核、时间单位和实际IR。采集不足以支持具体诊断时如实记录缺口。

预研交付物：一份目标筛选表、一份既有trace归因表，以及一个明确版本和测试合同的attention试点。模拟器能提供何种有效证据，是选择试点的重要条件。

## 对照实验合同

- 固定模型版本、模型配置、起点源码、算子集合、参考、正确性容差和完整调用计时。
- 无HG-KDA组与有HG-KDA组使用相同基础编码／评测能力，仅改变明确声明的分析工具及其信息。
- 预先规定预算与停止条件。记录模型token、调用次数、设备测量次数、总墙钟时间和模拟器开销；共同预算上限不意味着实际消耗相同。
- 两组由相同模型流程生成和修改候选。实验期间的人工／Codex临时诊断必须记录；用于开发的方法先固化，正式对照避免只向一组注入额外建议。
- 汇报最终正确性、相对同一参考的性能、预定义阈值下的达标率及优化成本。多个独立运行用于方法评估时须预先规定，不与对同一候选反复测量挑分混淆。
- 主对照先验证工具整体价值；后续再按问题比较仅成对profiling、增加热点区域、再增加流水时间轴等信息层，分析模拟器的增量贡献。
- 若评估两条修改路线，分别固定起点、实现边界和预算；严格Triton结果与custom op／Ascend C混合实现结果分开报告。通过逐项消融或配对实验评估profiling、模拟器及路线选择的贡献，不将相关性写成因果结论。
- CANNBench原生合同与KGS合同分别保存；若通过KGS适配，不默认认为两者计时和参考完全相同。

下一步只围绕试点需要补强：

- 将时间轴区间计算从regions.py提取至timeline.py，保持公开结果兼容并复用冻结trace验证；当前汇报图使用的新模块名尚不代表代码已经拆分。
- 核验报告是否支持同步事件标识、流水方向及操作数，再考虑SET_FLAG／WAIT_FLAG配对和缓冲区复用关系。
- RAW／WAR／WAW与控制依赖归因尚未实现，不从空闲比例直接推断关键路径或因果停顿。
- 每项修改记录“模拟器证据 → 机制假设 → Triton／IR／pass修改 → 预期变化 → 实测变化 → 真机完整结果”。不要求每个案例同时修改三个层次。
- 能力扩展线另记录“无法由Triton／现有pass表达的证据 → custom op接口及Ascend C实现 → 与严格Triton路线的同合同比较 → 正确性、延迟和开发／编译成本”。
- 模拟器时间与真机时间分别解释；只有完整正确性与真机性能结果支持时才更新交付。

## 插件化形态

HG-KDA核心已独立，KG不是必需依赖；KGS通过适配层提供评测，msprof提供真机与模拟器采集。公共CLI／JSON是继续解耦的基础。

调研DeepSeek Harness的实际插件接口与版本，以薄适配层暴露现有能力，避免复制整套分析核心。其他Harness应复用同一工具合同与证据格式。新Harness插件接入属于待实现，不宣称当前已兼容。多轮编排、凭据及设备配置由显式宿主／后端管理。

方法指引、结构化经验及脚本职责继续分开。没有Agent时可独立使用分析工具；有Agent时重点评估结构化证据对诊断和优化决策的帮助。

## 贡献与实现约束

Codex负责瓶颈分析、方法与工具设计、只读审查及实验编排；CC／DeepSeek负责候选实现、启动封装、目标算子的IR／pass修改及能力扩展线中的custom op实现。不能借编译pass或控制脚本绕过既有分工。严格Triton交付线的设备计算与搬运继续使用Triton；能力扩展线允许研究custom op／Ascend C，但结果单独标注，不计入严格Triton交付。评测、门禁与必要补测保持独立证据。

阶段成果不以新增算子数衡量，而以可复现的机制分析案例、有效的有／无工具对照和可移植工具接口衡量。论文可基于KDA、KernelAgent或其他合适宿主，不绑定KernelGen。
