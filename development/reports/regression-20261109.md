# 独立 HG-KDA 的固定候选回归

## 目标与口径

2026-11-09 启动独立入口全量回归。对象为 `benchmarks/index.json` 中已经达到严格 Triton＋合格 CANN 参考验收要求的 25 项；固定候选、原输入、容差与计时参数，不启动旧 KG 优化循环，不在回归中修改候选。

每项通过独立 `hgkda gate`、`kgs upload`、`kgs evaluate` 完成新请求，随后运行原版本的 PyTorch／CANN 补充检查。正式成绩采用 KGS 完整调用 walltime；每项仅做一次正式完整评测。历史分数与本轮分数分别记录，不把两个加速比分数的比值解释为候选优化收益。

回归结束后，再处理尚未达到该验收口径的 `cumulative_trapezoid`、`uniform`、`fractional_max_pool3d`、`expm1_` 和 `linalg_inv_ex`。候选的全部设备计算与搬运继续严格使用 Triton，CANN／Ascend C 只作为参考。

## 本轮入口兼容修复

准备阶段发现部分合法元数据／存储视图调用被新静态筛查误拦。现明确允许 `broadcast_shapes`、`view_as_real`、`view_as_complex`、存储别名查询及设备属性查询；张量计算、复制、外部执行入口继续受门禁限制。完整逐路径审查仍与候选 SHA 绑定，静态白名单不代替依赖审查。

3 份候选保留了原始 CRLF。CLI 改为按原字节解码后计算身份，避免 `read_text` 自动换行转换导致哈希不匹配。原候选、评测输入和容差未修改。回归启动时 Windows 和服务器均通过 16 项自动测试；后续加入异机归档映射检查，Windows 17 项通过。覆盖元数据误拦、计算调用拒绝、CRLF 身份，以及完整 case 集合、实际后端、几何平均重算和归档位置映射。

Windows 的独立 venv 已从当前源码重新安装，17 个已安装 Python 模块与维护源码逐字节一致，16 项测试再次通过。验证开发源码和验证已安装包分别记录，避免旧安装快照掩盖入口变化；910B 使用的已安装 CLI／门禁也已核对 SHA。

10 个历史绝对路径依赖采用逐文件临时链接，全部核验归档 SHA。8 个为 CANN 参考库，2 个为已审查的宿主启动桥，后者只负责分配、参数及 Triton 启动。正常结束后移除链接；不恢复旧 project 实验工作树。

## 结果

25 项固定候选回归完成：776/776 个正式用例、2366/2366 个补充检查通过；23 项相对 CANN 超过 0.8×。服务器及 Windows 的独立原件审计均核验 25/25，未发现身份、合同、case 或计时重算错误。完整表格和原件见 [本批归档](../benchmarks/regressions/20261109/README.md)。

`negative_` 为 0.652877×，`hardswish_out` 为 0.778083×，两项正确性与补测通过，性能未过线。原有 25/30 验收索引表示拆分前结果；本轮固定候选达标 23/25，修复实验另立候选身份。

完成项原件按字节自动镜像到 Windows 控制目录，并重算 SHA；本地离线复核使用同一核验函数。汇总保留每个 case 的候选耗时、CANN 耗时和加速比。

首个性能未过线项为 `negative_`：原候选完整正确性 30/30，两侧补测各 63/63，但本轮相对 CANN 为 0.652877×，历史为 0.813792×。小输入候选耗时由约 12.5～15.1 微秒变为 16.6～18.7 微秒，大输入及 CANN 参考耗时变化较小。该事实提示优先检查启动与宿主路径，尚不能单独证明原因。保留本轮结果，不通过重复相同正式测量挑选过线分数；后续修复须使用独立的新源码身份。

## 回归后的性能修复

修复实验使用独立源码身份，继承原正式合同、输入、容差和计时设置。`negative_` 的宿主缓存版本通过正确性，但仅为 0.695×。检查编译 IR 后，将完整分块改为固定长度的无掩码读写，尾块保留掩码；FP16／BF16 分块上限 16384，FP32 为 8192。实际捕获四类 Triton 核，并通过 36 项冷／热启动、新地址、新 stream、非连续、未对齐及大输入尾块检查。

完整块版本正式评测 30/30，两侧补测各 63/63，相对 CANN 为 **0.805699×**，恢复过线。该值为一次正式请求结果，距离验收线较近；不通过重复测量挑选分数。宿主桥仅处理元数据、参数和 Triton 启动，全部设备计算保持 Triton。

`hardswish_out` 的初始 8192 分块版本超出 UB 预算；即使关闭自动多缓冲仍未通过。单一完整块循环进一步降低需求，但仍需 1703936 bits，超过本机 1572864 bits（192 KiB）。这些失败发生在编译路径检查，均未提交正式请求。后续归一化门控版本单独核验，不改变固定回归结论。

最终版本使用 `x * clamp(x/6 + 1/2, 0, 1)`，输入或输出为 FP32 时保留 FP32 计算，其余采用输入精度；FP16 输入与输出可用 8192 分块，BF16／FP32 保留 4096，避免 BF16 内部类型扩展导致缓冲溢出。保留原容差和特殊值要求，21 项实际编译路径检查、42/42 提交前检查、正式 30/30 及两侧各 42/42 补测通过，相对 CANN **0.866788×**。

因此，固定回归为 23/25，新候选修复后原 25 项全部恢复达标；加上 Uniform 新合格参考，当前原合同及语义口径为 **26/30**。累计积分独立数学合同单列 1 项。完整状态见[当前索引](../benchmarks/current.json)。

## 剩余五项的参考资格与结果

| 算子 | 本轮结果 | 原合同状态 |
| --- | --- | --- |
| `uniform` | 原 Triton 候选相对 CANN Uniform＋Clamp 为 **2.398526×**；18/18，资格 31/31，两侧补测各 31/31 | 保留输入、容差及随机语义，补齐合格组合参考 |
| `cumulative_trapezoid` | 独立数学参考合同下 **1.012343×**；33/33，资格 36/36，两侧补测各 36/36 | 原 NPU 默认合同未宣布通过，新合同单列 |
| `expm1_` | 官方默认和高精度模式均为 0/3 类型通过小值数学资格 | 未获得合格 CANN 参考，不报告相对其性能 |
| `fractional_max_pool3d` | 未找到覆盖随机窗口及索引的同语义 CANN 入口 | 现有 Triton／含 CPU 回退的 PyTorch 结果保留，原生参考缺口未解决 |
| `linalg_inv_ex` | CANN Inverse 仍缺逐矩阵 LU `info` | 不用 API 返回码冒充 `info`，原生参考缺口未解决 |

Uniform＋Clamp 使用原始 from／to 生成样本，再限制到输出类型在原半开区间内可表示的上下界，完整计时包含分配和两个原生接口。该结果补齐参考资格，不表示 Triton 候选因此产生了同幅度的新优化收益。

累计积分候选保留相邻加法与缩放的输入类型舍入，并采用 FP32 前缀累加；参考为 CANN Add＋Muls＋FP32 Cumsum＋必要的 Cast。CPU PyTorch 只用于数学资格检查，正式计时参考仍全部执行 CANN。原 NPU 默认 FP16 非末轴参考的不稳定性与失败原件保留。

Expm1 首轮 500001 为私有缓存目录未建立造成的初始化错误。修复环境后的独立进程中，官方选项及 API 均执行成功，但小值误差未合格，环境错误与数值错误分别保存。公开源码研究与局部资格结果见 [CANN 参考可用性](native-reference-availability-20261109.md)。

各阶段均在同一项目卡锁内串行运行，不重启共享容器或影响其他任务。源码、控制器快照、完整评测及编译失败证据见[本批归档](../benchmarks/regressions/20261109/README.md)。

## 异机离线核验

安装 HG-KDA 并拉取 LFS 原件后，可用 [audit.py](../tools/regression/audit.py) 的 `--original-run-directory` 和 `--verify-transfer` 参数，在 Windows 或其他 Linux 主机核对归档。它在内存中映射原路径，重算完整 case、身份、两侧补测及分数，同时核验传输清单的全部文件，不修改冻结请求或重新执行设备任务。具体命令见[回归工具说明](../tools/regression/README.md)。
