**懂。你要讲清楚的是：HG-KDA看到了什么证据，如何找到代码位置，为什么想到这个改法，以及修改后怎样验证。** 我上一轮偏重介绍“优化了什么”，中间的推导过程讲得不够。



下面按你的三个技术点，各展开一个最清楚的候选。所有代码都是用于讲解的简化表达。



先记住GQA的这几行计算即可：
```ini
S = scale * (Q @ K.T)       # Q和K匹配，得到分数
P = exp(S - row_max(S))     # 得到权重
O = (P @ V) / row_sum(P)    # 加权汇总，再归一化
```

我们的case 4中，**每8个Q头共享同一组K/V**。矩阵乘主要由Cube处理，指数、求和等主要由Vector处理，中间需要搬运数据和等待结果。

**技术点1：成对profiling——从搬运差距，找到重复加载。**



对应compact第2段中的**索引7：KV持久复用**。



**① HG-KDA先看到什么？**



对同一个输入，分别采集我们的实现和CANN：

| 修改前指标     | 我们的实现       | CANN          |
| --------- | ----------- | ------------- |
| GM→L1搬运量  | **112 MiB** | **约64.3 MiB** |
| L0C→GM搬运量 | 96 MiB      | 96 MiB        |

这给出一个具体研究方向：**为什么我们的输入侧搬运更多？优先检查是否重复加载了数据。**



**② 回到源码，找到什么？**



当时每个query块由独立program处理：
```ini
# 修改前：每个query块各执行一次
q = load(Q_for_this_tile)
k = load(K_for_shared_head)
v = load(V_for_shared_head)

out = attention(q, k, v)
```

结合GQA的头共享关系，发现同组8个Q头、每头2个query块，**16个program在重复读取同一份K/V**。



**③ 为什么能想到改法？**



K/V只取决于共享头，与当前query块无关。因此可以让一个program连续处理这些query块，把K/V载入放到循环外：
```lua
# 修改后：同组query块复用一次载入的K/V
k = load(K_for_shared_head)
v = load(V_for_shared_head)

for tile in query_tiles_of_this_group:
    q = load(Q_for_tile)
    out = attention(q, k, v)
```

**④ 怎么证明改对了？**



修改后profiling显示：

- GM→L1搬运：**112→52 MiB**；
- L0C→GM搬运保持96 MiB；
- 完整调用：**328.447→268.772 μs，下降18.17%**。

这个例子的完整逻辑就是：

> **成对profiling发现搬运差距 → 源码揭示共享数据重复加载 → 调整Triton程序组织 → 复测确认搬运减少和性能提升。**

**技术点2：模拟器热点——从一条昂贵的搬出指令，找到QK交接类型。**



对应compact第3段中的**索引11：QK交接缩窄**。



**① 热点工具看到了什么？**



模拟器采集窗口中，两处同类搬出操作的累计耗时不同：

| 搬出位置   | 窗口内累计耗时          |
| ------ | ---------------- |
| QK结果搬出 | **83.49 μs／19次** |
| PV结果搬出 | **29.22 μs／18次** |

于是，研究重点落到**QK结果搬出**。



**② 怎么定位到源码？**



这一步适合讲成：



**热点指令位置 → 对应IR操作及张量 → Triton表达式。**



实际IR显示，这里搬出的是一个 **128×256的FP32 QK结果**，对应：
```ini
qk = tl.dot(q, tl.trans(k)) * qk_scale
```

AST可以辅助识别源码表达式和结构；这次定位的关键证据还有实际TTIR／BCMLIR，不能只靠AST解释机器指令的耗时。



**③ 为什么想到修改类型？**



这块FP32结果每次搬运128 KiB。若用FP16交接，就能减到64 KiB；接收后恢复FP32，继续做softmax。



实际Triton修改很短：
```ini
# 修改前
qk = tl.dot(q, tl.trans(k)) * qk_scale

# 修改后
qk = tl.dot(q, tl.trans(k)).to(tl.float16).to(tl.float32) * qk_scale
```

**④ 怎么知道这两次转换真的减少了搬运？**



需要检查后端是否把FP32→FP16转换放进搬出路径。随后用生成代码、profiling和重放核对，结果是：

- L0C→GM总搬运：**96→64 MiB**；
- 完整调用：**205.284→196.158 μs**；
- 原四用例正确性检查通过。

这个例子可以讲成：

> **热点排序找到昂贵搬出 → IR说明搬的是什么 → Agent提出缩窄交接类型 → 修改Triton → 验证转换位置、搬运量和收益。**

**技术点3：模拟器流水空泡——从等待窗口，找到可以提前执行的独立计算。**



对应compact第5段中的**索引22：分母归约前移**。



**① timeline看到了什么？**



当时的执行顺序是：



**发送P → 等待PV返回 → 计算分母及倒数 → 输出归一化。**



模拟器显示，Vector在等待PV时，分母计算还没有开始。



**② 关联到IR，发现什么依赖关系？**



分母是：
```ini
d = row_sum(P)
inv = reciprocal(d)
```

**它只依赖已经算好的P，不需要PV结果。** 因此，等待PV的这段时间可以用来计算分母。



**③ 具体怎么改？**



下面是实际IR重排的伪代码：
```makefile
# 修改前
send_P_to_cube(P)
pv = wait_and_receive_PV()

d = row_sum(P)
inv = reciprocal(d)
out = pv * inv
```
```makefile
# 修改后
send_P_to_cube(P)

d = row_sum(P)
inv = reciprocal(d)

pv = wait_and_receive_PV()
out = pv * inv
```

改法看起来只是前移两行，但要由IR中的数据依赖、缓冲和事件关系确认它可以安全执行。



**④ 怎么验证空泡被利用了？**



修改后重放显示，sum和倒数计算进入了发送／等待区间。计算内容和逻辑搬运量保持，完整调用：



**144.437→133.321 μs，下降7.70%。**



这个例子的讲法就是：

> **timeline发现等待窗口 → IR分析发现独立计算 → 把计算移入窗口 → 重放确认重叠 → 真机确认收益。**
