Emerging accelerators rarely ship with mature compiler backends, so recent work
asks LLM agents to write native kernels directly from ISA documentation and
simulator feedback. On two such accelerators, we find that this direct workflow
returns a correct kernel on only 17 of 38 workload instances, and that most of
its inference budget is spent re-deriving machine semantics and repairing
illegal code rather than optimizing the workload. We present Contour , which consists of two parts. Contour-Explore
replaces native-code generation with search over
a mapping surface: a typed set of scheduling knobs and their legal domains,
generated automatically from the accelerator’s ISA description and the workload
graph. A compiler-owned resolver completes partial assignments into legal plans
and emits native code, so every evaluated candidate is verified against the
compiler’s default. Kernel writing becomes knob assignment, and kernel
optimization becomes design-space exploration that any policy can drive through
the same intent interface, including hill climbing,
evolutionary search, and LLM agents. Compared with KernelCraft, a
state-of-the-art agentic kernel generator, an LLM agent through Contour-Explore
returns a verified kernel on every Gemmini and PLENA instance, produces 2.86 × 2.86\times and 1.13 × 1.13\times faster kernels on the instances where both
succeed, and uses 26.3% and 83.4% fewer tokens per verified kernel.
KernelCraft returns a correct kernel on only 60% of the Gemmini
instances and 5 of the 18 PLENA instances. The agent’s kernels are also 1.17 × 1.17\times faster than those from the expert-written tiling heuristics in
Gemmini’s software library and 1.46 × 1.46\times faster than those from PLENA’s
compiler, and
AccelOpt finds 1.50 × 1.50\times faster kernels on Gemmini and 1.20 × 1.20\times faster kernels on four PLENA attention instances when it searches through
Contour-Explore instead of editing kernel programs. A generated surface is bounded by its vocabulary. The second component—Contour-Ext—lifts this bound: when
search stalls, an LLM agent reads the stalled program, hardware facts, and
search history, then extends the backend itself by implementing a new knob and
its lowering. Contour-Ext accepts the extension only if the
default path is byte-identical, every new value is numerically correct and
changes the program, and the enlarged surface yields a measured gain.
On VTA, Contour-Ext extends the AutoTVM surface of TVM, and AutoTVM’s
XGBTuner then finds 4.14 × 4.14\times faster kernels; on PLENA, the extended
surface makes the kernels found by hill climbing 1.20 × 1.20\times faster. 1. Introduction Programmable tensor accelerators often expose target-specific
instruction set architectures, explicitly managed on-chip
memories, and specialized data-movement and control mechanisms ( Chen et al., 2019 ; Moreau et al., 2019 ; Genc et al., 2022 ; Jouppi et al., 2017 ) .
Supporting such a target requires a tensor compiler backend to lower tensor
operations to these interfaces, including instruction selection, memory
placement, state configuration, and legal instruction sequencing ( Hong et al., 2025 ; Ikarashi et al., 2022 ) . However, most proposed tensor
accelerators lack reusable tensor compiler backends for generating
implementations beyond supported kernels or templates, and rapid hardware
iteration makes separately engineered backends difficult to maintain ( Jain et al., 2026 ; Huang et al., 2024 ; Hong et al., 2024 ; Ikarashi et al., 2022 ) .
When a reusable backend is unavailable, developers
often fall back on manually written low-level kernels or target-specific
compilation templates ( Jain et al., 2026 ; Nie et al., 2026 ) . Recent work has explored large language model (LLM)-based kernel generation
and optimization across GPUs and specialized tensor
accelerators ( Hong et al., 2024 ; Zhang et al., 2025a ; Ouyang et al., 2025 ) .
These systems construct and revise kernel programs, guided by compilation,
correctness tests, and performance feedback ( Nie et al., 2026 ; Hong et al., 2025 ; Zhang et al., 2025b ; Sereda et al., 2025 ; Liao et al., 2026 ) .
For example, KernelCraft generates and repairs ISA-level kernels from
machine specifications, using compilation, execution, and correctness
feedback ( Nie et al., 2026 ) , and AccelOpt starts from a correct
kernel and improves performance using beam search, profiling feedback, and
optimization memory distilled from slow–fast kernel pairs ( Zhang et al., 2025b ) . We refer to workflows in which agents generate or
revise complete kernel programs as program-level agentic generation . Figure 1. Kernel generation combines reusable machine-interface knowledge
with workload-dependent mapping decisions. Across workloads, these workflows involve two classes of information with different
reuse properties (Figure 1 ).
Workload-invariant machine knowledge defines the target interface, including
instruction semantics, the memory hierarchy, direct memory access (DMA)
protocols, configuration-state transitions, synchronization, and legality
constraints. Workload-dependent mapping decisions determine how a particular
computation uses that interface, including tiling, scheduling, layout, fusion,
dataflow, and precision. Both are required to produce an executable kernel, but
machine knowledge can be reused across workloads, whereas mapping decisions
generally vary across workload instances.
Without a reusable backend, the agent handles both within the same
per-workload loop, so each invocation spends inference and validation
feedback not only on workload-specific optimization, but also on instruction
legality, configuration-state transitions, data-movement protocols, and
synchronization. Recent advances make this coupling optional. TensorLift recovers executable
tensor-level machine semantics from RTL ( Gao et al., 2026 ) and represents them in the Tensor Accelerator
ISA Definition Language (TAIDL) ( Jain et al., 2025 ) , from which a
compiler backend can be generated automatically ( Jain et al., 2026 ) .
Workload-invariant machine knowledge can therefore be compiled once and
reused across agent invocations. Figure 2. Compiler-mediated agentic kernel generation compiles machine
semantics once while searching workload-dependent mappings per
workload, and extends the mapping surface with a validated knob when
search stalls. A generated backend takes over machine-specific code generation. Two
problems remain. First, search agents need explicit control over mapping
decisions: where a compiler resolves implicit mapping choices,
program-level workflows treat that completion as a black box and lack
a shared contract for submitting partial mapping decisions and inspecting
their resolution.
Second, the compiler defines which mapping decisions an agent can
express, and this set bounds every search policy: a mapping that no
published decision expresses cannot be reached, whereas a program-level
agent can write it directly. We address the first problem by separating
mapping search from compiler-owned completion and native code generation,
and the second by letting an agent extend the compiler when search stalls
(Figure 2 ). We present Contour , an agentic framework in which search agents
choose mapping decisions and the compiler generates the kernel. Contour consists of two parts: Contour-Explore searches a mapping
surface, and Contour-Ext extends it. Contour-Explore derives a workload-conditioned mapping surface from
formal, RTL-lifted machine semantics and publishes each mapping decision as
a typed knob with its legal values. The agent submits a mapping intent:
required or preferred knob values, with other decisions left to the
compiler. For example, it may select an algorithm, prefer a tile size, and
leave loop organization unspecified. A symbolic resolver completes a legal
mapping for the backend to lower to native code; completing an empty
intent yields a verified default kernel, Candidate-0 , which initializes
search. During search, feedback reports the realized mapping values,
correctness, and performance to guide the agent’s next mapping hypothesis.
A search agent , the component that proposes mapping intents,
can implement an LLM-based policy or a conventional search policy, such as
hill climbing, evolutionary search, or random sampling; all policies
share the same mapping surface, symbolic completion, code generation, and
candidate-validation path. Contour-Ext extends the mapping surface when search in Contour-Explore
stalls. An LLM-based extension agent analyzes the stalled kernel and
the search history, then implements a new knob and its lowering in the
compiler. Contour-Ext keeps the knob only if it passes correctness and
effectiveness checks, after which Contour-Explore republishes the surface and
search continues. The agent’s ability to write low-level code is thereby
applied to the compiler instead of to a single kernel: an accepted knob is
checked once and then remains available to later workloads and to every
search policy. Contour-Ext requires only a knob registry, a lowering, legality
checks, and an evaluator from its host compiler, so it also applies to
existing compilers such as TVM ( Chen et al., 2018a ) . This paper makes the following contributions: • We characterize how program-level agentic generation repeatedly
reconstructs workload-invariant machine semantics on accelerators without
a reusable kernel-generation backend: when we replicate KernelCraft
on PLENA, repairing programs and reasoning about machine semantics take 4.1 × 4.1\times the completion tokens spent on optimizing correct programs. • We design Contour-Explore, a workload-conditioned mapping-search
interface that publishes typed decisions derived from the hardware
specification and the workload. It supports partial intents with
required, preferred, and automatic decisions, completes them into legal
plans, and reports the realized mapping values as feedback to guide
subsequent search. • We design Contour-Ext, which extends the mapping surface when
search stalls with knobs that pass correctness and effectiveness checks.
On 16 VTA instances, Contour-Ext extends the AutoTVM surface of TVM, and
AutoTVM’s XGBTuner finds 4.14 × 4.14\times faster kernels on the extended
surface than on the original one. On 18 PLENA instances, the extended
surface makes the kernels found by hill climbing 1.20 × 1.20\times faster. • We evaluate Contour-Explore against KernelCraft, AccelOpt, and
the software shipped with each accelerator: the tiled matrix-multiply
routine in Gemmini’s official software library and the compiler of PLENA.
An LLM agent searching through
Contour-Explore returns a correct kernel on every Gemmini and PLENA
instance, whereas KernelCraft fails on 21 of the 38; where both succeed,
the agent’s kernels are faster and cost fewer tokens. The agent’s
kernels are also 1.17 × 1.17\times faster than the Gemmini library routine and 1.46 × 1.46\times faster than those of the PLENA compiler. AccelOpt also finds
faster kernels when it searches through Contour-Explore than when it edits
kernel programs. 2. Preliminaries 2.1. Emerging Accelerator Architectures We study three representative accelerator platforms: Gemmini ( Genc et al., 2022 ) , an established state-of-the-art tensor-accelerator
generator; PLENA ( Wu et al., 2026 ) , a recently introduced open-source
research accelerator for long-context agentic LLM inference; and VTA ( Moreau et al., 2019 ) , an open-source deep-learning accelerator. All
three expose
target-specific instructions and explicitly managed on-chip memories, so
mapping a tensor computation requires coordinating its computational
decomposition with data placement and movement. Gemmini. Gemmini is an open-source, full-stack DNN accelerator generator integrated with
RISC-V systems. Its central compute structure is a configurable spatial array
whose processing elements perform
multiply–accumulate operations using weight- or output-stationary dataflow.
The array reads operands from a banked, explicitly managed scratchpad and
writes partial and final results to a higher-precision accumulator. A Gemmini
mapping therefore determines how matrices are tiled, staged through the
scratchpad, accumulated, and executed under the selected dataflow. PLENA. PLENA is designed for long-context agentic LLM inference and organizes its ISA
around Matrix, Vector, Scalar, HBM, and Control instruction classes. Its Matrix
Unit uses an output-stationary flattened systolic array: operands stream along
a long reduction dimension while sub-arrays retain partial sums, which are
combined by a cross-array reduction.
PLENA separates its on-chip storage into a Vector SRAM for activations and
vector intermediates and a Matrix SRAM for weights and KV tensors. The latter
supports transposed and non-transposed reads without explicitly rearranging
the stored data, directly supporting computations such as Q ​ K 𝖳 QK^{\mathsf{T}} .
The Vector Unit complements matrix multiplication with elementwise,
reduction, and nonlinear operations needed by normalization and softmax. PLENA composes these capabilities at tile granularity. Independent HBM
prefetch paths can fill the Matrix and Vector SRAMs while other units execute,
and fine-grained scheduling can interleave matrix multiplication, vector
reduction, scalar control, and data movement within a fused attention
pipeline. The architecture also supports mixed-precision MX formats across
its storage and compute paths. Its programmable mapping surface consequently
includes matrix and vector tiling, cross-array reduction, tensor orientation,
SRAM placement and residency, prefetching and buffering, numerical precision,
fusion, and overlap across execution units. Together, these are hardware-level mapping
decisions that the compilation approaches below must ultimately realize. VTA. The Versatile Tensor Accelerator (VTA) ( Moreau et al., 2019 ) is the
open-source deep-learning accelerator of the TVM compiler
stack ( Chen et al., 2018a ) . Its GEMM core multiplies int8 tiles held in
explicitly managed on-chip buffers and accumulates in int32. Its load,
compute, and store modules run concurrently and synchronize through
dependency queues, so data movement can overlap computation. TVM generates
VTA code from a schedule, which fixes the tiling, loop order, and on-chip
buffer placement of a tensor operator; its VTA backend maps the scheduled
loops to VTA load, GEMM, ALU, and store instructions. 2.2. Machine Semantics and Generated Backends We use compiler backend to mean the target-specific component
that translates a tensor computation graph into accelerator assembly. Prior
work provides the machine semantics that a backend needs in machine-readable
form. The Tensor Accelerator ISA Definition Language (TAIDL) describes
accelerator state, instruction semantics, and legality constraints using
tensor operations ( Jain et al., 2025 ) . TensorLift generates TAIDL from
RTL: it lifts bit-accurate architectural-state updates into tensor-level
descriptions of computation, data movement, and control, and validates them
against the low-level model with SMT proofs and simulation ( Gao et al., 2026 ) . A compiler backend can then be generated
from the TAIDL specification ( Jain et al., 2026 ) ; on seven Gemmini
workloads, TensorLift with such a backend achieves a 1.014 × 1.014\times geometric-mean speedup over the official handwritten kernels ( Gao et al., 2026 ) . These systems provide reusable machine semantics and native code generation,
but do not expose workload-level mapping decisions to an external search
policy or accept partially specified mapping intents. Contour introduces
a mapping-search interface that publishes the decisions available for each
workload and accepts required, preferred, and automatic choices.
Its symbolic resolver completes partial intents into legal plans
and reports their realized mapping values as feedback. The mapping surface,
intent interface, resolver, and feedback-directed search workflow are
introduced by this work. Table 1. Tokens generated by KernelCraft on PLENA. Program-Level Agentic Generation KernelCraft studies a different response to the absence of a reusable
backend: a tool-using LLM agent directly generates and repairs a close-to-metal
kernel for each workload ( Nie et al., 2026 ) . Each task supplies a
concrete workload instance, the target ISA and hardware
documentation, and memory-layout information. A platform-specific execution
harness gives the agent access to the target compiler, simulator, correctness
oracle, and documentation retrieval. Together, these inputs and services form
the agent’s context. The required output is an ISA-level program that
explicitly realizes both the computation and its use of the target machine. Generation proceeds as a multi-turn diagnosis-and-repair loop. In each
iteration, the agent produces a candidate assembly program, compiles and
executes it, and receives syntax diagnostics, functional differences, and
execution latency. When additional machine information is needed, the agent
queries the supplied ISA and hardware documentation through grep_docs . It uses this feedback first to repair correctness and then
to optimize performance, repeating the loop until its interaction budget is
exhausted. Because the generated artifact is already close to the target ISA, the agent
is responsible for more than workload mapping. Within the same program, it
must select instructions, calculate addresses, place values in the memory
hierarchy, schedule data movement and computation, manage configuration state,
and expose parallelism. KernelCraft shows that frontier agents can sometimes
produce correct, performance-competitive kernels for unfamiliar accelerators. Program-level agents can also optimize an existing kernel. AccelOpt
organizes this process around three agents: a planner, executor, and
summarizer ( Zhang et al., 2025b ) . In its workflow, the planner
proposes optimizations using profiling
feedback and accumulated experience; the executor implements these plans as
kernel programs; and the summarizer distills reusable optimization insights
from slow–fast kernel pairs for subsequent exploration. In its Trainium
implementation, the agents receive hardware constraints and NKI programming
guidance through platform-specific prompts. 2.4. Motivation KernelCraft’s program-level generation workflow treats each workload task in isolation.
Although the target ISA, memory organization, and instruction semantics remain
unchanged across tasks, the workflow does not carry the machine-specific
knowledge recovered for one task into the next. Consequently, the target
details required for native-code generation remain part of every per-workload
interaction. When we replicate KernelCraft’s experiments on PLENA with its benchmark
workloads, including GEMM, GEMV, normalization, softmax, FFN, and attention,
and classify each model turn by tool verdict and by content,
most completion tokens go to repairing programs and to reasoning about machine semantics : instruction semantics, operand conventions, memory
layout, precision formats, legality, and timing. These two uses take 4.1 × 4.1\times the completion tokens and 4.8 × 4.8\times the reasoning tokens spent
on optimizing correct programs (Table 1 ). Every run
spends 9.7–50.9% of its completion tokens on this workload-invariant
knowledge. This observation motivates our compiler-mediated agentic design: a reusable
compiler captures target-invariant code-generation knowledge and
generates every candidate from the validated machine semantics, so that
candidates are legal by construction and the agent can spend its tokens on
workload-specific mapping decisions instead of program repair. 3. Design Contour consists of two parts (Figure 3 ). Contour-Explore connects a search agent to a reusable compiler through a
workload-specific mapping interface. The agent chooses how to map a tensor
computation; the compiler completes these choices and generates target code.
An independent evaluator checks the output and measures performance. A
controller returns these results to the agent and retains the fastest verified
candidate. The same interface supports neural and conventional search policies. Contour-Ext extends this interface when search stalls. An extension
agent implements a new knob and its lowering in the compiler, and Contour-Ext
keeps the new knob only if it passes correctness and effectiveness
checks.

Constructing the Mapping Surface The input is a tensor computation in the high-level optimizer (HLO)
intermediate representation ( OpenXLA, 0000 ) and a target described by TAIDL. A workload contract fixes the computation, input data, target,
execution boundary, and numerical acceptance policy for every candidate.
Within this contract, a 1 mapping surface lists the decisions that search
may change, such as tiling, operand residency, or execution overlap. Each
decision, or knob , has a type and a finite domain of supported values. The surface generator constructs a workload-specific mapping surface using a TAIDL
hardware description and a shared mapping layer. TAIDL specifies architectural
state, storage capacities, instruction semantics, and legality constraints.
The shared mapping layer defines the knob vocabulary and default policies,
which are compiler design choices reused across accelerators. For each
workload, the surface generator uses the hardware description and these shared policies
to derive the available knob values , and the resolver
checks their joint legality. The shared mapping layer defines each knob category with four parts:
a derivation rule that creates knob instances and candidate domains from the
workload graph and TAIDL facts, a default policy, a legality predicate for
its values, and a plan field that lowering reads. We call these four parts a knob definition . A compiler version is the compiler together
with its registered knob definitions. The surface generator publishes one
surface for each compiler version. Contour-Ext (Section 3.5 )
registers new knob definitions through the same interface, so added knobs
and built-in knobs use the same derivation, publication, and completion
steps. On PLENA, the surface generator first selects the knob categories applicable to the
operator family. The eight categories cover algorithm, matrix and vector
decomposition, placement, memory pipeline, execution pipeline, precision, and
loop structure. For each applicable knob, it tests each supported value by
requiring that value and completing the remaining decisions with the default
policies. It retains values whose completion passes the constraints and omits
knobs with only one retained value. Those fixed choices remain compiler-owned. These per-knob tests do not make the domains independently combinable. The
resolver checks joint constraints again when it completes an intent. For
example, the attention algorithm determines whether scores are materialized;
that choice changes SRAM demand and the legal block sizes. A conditional
surface therefore publishes individual domains without enumerating their
cross-product. Gemmini instead uses a finite catalog of complete mappings
that pass the workload’s shape, capacity, and scheduling checks. Both forms
expose legal choices without exposing physical instructions or addresses. 3.2. Completing Mapping Intents An intent assigns values to exposed knobs. Contour supports 2 hard assignments that must hold and 3 preferred assignments that may be relaxed.
The resolver rejects unknown knobs and values outside the published domains,
and fills automatic or omitted choices using shared default policies.
Gemmini selects a complete catalog mapping and treats all selected values
as hard assignments; PLENA also supports partial intents with preferences. For PLENA, completion first applies all hard assignments together. The
resolver fills the remaining choices with the shared default policies and
checks shape, capacity, reduction, output-coverage, and dependency constraints.
If this completion fails, it rejects the intent . It then processes preferences
in a fixed order : category order followed by knob-name order. For each
preference, it adds the requested assignment to the accepted assignments and
attempts completion again. A successful check retains the assignment ; a
failure drops it and records the requested value, realized value, and reason.
Preferences are incorporated incrementally in a fixed order, retaining each
choice only when its completion remains legal alongside previously accepted
assignments. Mapping completion produces a resolved plan : a complete legal mapping with eight
semantic sections for the computation graph, matrix and vector decomposition,
placement, memory, precision, pipeline, and loops. It also constructs an
engine-schedule directed acyclic graph (DAG) specifying operations and
dependencies, rejecting cyclic schedules. Internal resolution records identify
defaulted choices and honored or relaxed preferences. The resolved decisions
guide subsequent lowering of the tensor computation to target code. 3.3. Feedback-Directed Search Search begins by completing the empty intent. The resulting default plan, Candidate-0 , uses the shared default policies under the target and
workload constraints. It requires no model inference. The controller compiles,
executes, and verifies this plan before using it as the initial incumbent , the fastest verified candidate so far. The agent receives
the workload, surface, default decisions and performance, and remaining
evaluation budget. PLENA additionally reports a bottleneck profile containing
engine activity, HBM traffic, and SRAM occupancy. Gemmini: selecting a legal point. The agent sees the catalog’s mapping decisions, with performance hidden for
untried mappings. It submits one complete mapping per evaluation. The
controller rejects duplicate submissions and returns verification, measured
cycles, and structural properties for each newly evaluated mapping. The agent
can then refine a tile choice or explore different buffering and store
schedules. Only candidates evaluated within the run enter final selection. PLENA: proposing a region. A 4 search region describes how the controller should generate candidate
intents. Hard assignments remain fixed; preferred assignments guide sampling;
explicitly automatic knobs are left to compiler completion. Other unassigned
knobs remain available for sampling. Each region includes at least one diversity axis , identifying a knob along which alternative plans are
desired, and leaves at least two knobs free of hard assignments. It may also
name an evaluated plan as a center and specify an initial radius in changed
decisions. Diversity guides sampling and selection without adding legality
constraints. The controller constructs a center using preferred values, then the named
plan’s remaining values, or domain midpoints when no plan is named. Explicitly
automatic knobs remain omitted from candidate intents . Without a named
plan, the controller samples up to 256 assignments: preferred knobs take
their requested values with probability 0.75 and otherwise draw uniformly;
other free knobs draw uniformly. With a named plan, sampling changes one to
the radius’s number of knobs, prioritizing diversity axes. Each sampled
assignment becomes a candidate intent whose sampled values are preferences
and whose hard assignments are preserved from the region. The controller removes rejected intents and plans that duplicate either
previous evaluations or other plans in the pool. Deduplication uses the eight
semantic sections. If a neighborhood supplies fewer than two fresh plans, it
expands the radius up to eight; a pool still smaller than two is rejected.
It filters the worst quarter by estimated static cost, preserving the center
and at least two plans. This estimate filters candidates rather than choosing
the measured winner. Two plans enter evaluation . The first is the center when available; otherwise,
it is the plan most distant from previously evaluated plans. The second
prioritizes a new value on the first diversity axis, then maximizes distance
from the first plan and evaluated plans. Distance is normalized Hamming
distance over the eight semantic sections. Both plans obey the hard
assignments, but their realized preferences can differ after completion. Algorithm 1 combines this target-specific proposal path
with the common search loop. Feedback reports each plan’s identity,
verification, measured performance, and realized decisions relative to the
default. A rejected region instead receives a mapping-level explanation,
such as conflicting hard assignments or exhausted alternatives. The agent can
revise its proposal, but only the controller can update the incumbent.
The controller bounds both proposals and evaluations. Rejected regions consume
requests without consuming evaluations, so repeated rejection cannot prolong
search indefinitely. A new batch requires sufficient remaining evaluation
budget; Candidate-0 is outside this search budget. Conventional search policies. Hill climbing, genetic search, and random sampling implement the Propose step in Algorithm 1 over the published
mapping decisions. Hill climbing explores neighboring assignments, genetic
search mutates and recombines typed intents, and random search samples
assignments from the exposed domains. Contour completes these proposals
into legal mappings and generates kernels for verification and measurement.
Measured latency provides the objective value for hill climbing and genetic
selection; random sampling proceeds independently of these values. Across
all policies, the controller retains the fastest verified candidate. Thus,
conventional policies search mapping choices without implementing kernel
generation or legality checks. Stall detection. Search stalls when the incumbent stops improving: the relative
latency improvement over a window of recent evaluations falls below a
threshold, or the policy can reach no unevaluated program. An exploration
round also ends when an LLM search agent produces no new evaluation for a
fixed number of turns, or when the round’s evaluation budget is spent. The
incumbent at the end of the round is the stalled plan , p s p_{s} .
Contour-Ext (Section 3.5 ) starts from p s p_{s} . 3.4. Code Generation and Candidate Validation Gemmini realization. Contour exposes macro tiling, buffering, store scheduling, and batch-region
choices through a legal mapping catalog. Macro-tile dimensions are multiples
of the primitive tile, bounded by workload dimensions and scratchpad and
accumulator capacities. The selected mapping specifies the choices that the
subsequent schedule transformations must realize; choices with only one
applicable value remain fixed. The existing generated backend 5 lowers the HLO computation to a primitive schedule with concrete transfer and matrix-operation addresses
and sizes. Contour then applies schedule transformations to implement
accumulator initialization, the selected buffering strategy, and store order.
The schedule parser checks the transformed schedule before code generation.
This additional transformation stage connects the searchable mapping choices
to their executable realization. PLENA realization. The resolver translates the completed mapping into typed bridge options that Contour passes to code generation, making the resolved computation,
placement, data movement, and execution overlap explicit inputs to lowering.
Instruction selection, physical memory management, and synchronization realize
these decisions as target code . From the same options,
the resolver derives an engine-schedule DAG for symbolic legality checks and
cost estimation. The mapping interface thus gives search control over the
plan realized by the backend.
A schedule layer reads the plan fields and selects operator
decompositions, placement, tensor storage, and loop nests before instruction
selection. Instruction selection maps abstract tile operations to target
instructions by semantic signatures derived from TAIDL. Lowering either
implements every value in a resolved plan or reports that it cannot; it
does not fall back to another value. On request, lowering tags each
instruction with the schedule-layer step that produced it. Independent validation. The evaluator executes each generated program and compares its complete output with an independent numerical oracle under the workload contract.
The acceptance policy remains fixed across mapping and precision choices.
The evaluator returns correctness and performance to the controller,
together with structural counters when available. A candidate replaces the incumbent only when it 6 passes verification and strictly improves the performance objective. Otherwise,
the previous verified candidate remains the result. The agent cannot change
the acceptance criteria or the final selection rule.
The evaluator identifies each program by a hash of its assembly and
does not execute the same program twice. Contour keeps the hashes of
all programs measured in the run. 3.5. On Gemmini and PLENA, we adopt the workload

Each workload–input-shape combination is a workload instance .

an LLM proposes a mapping intent, receives correctness and performance

this configuration Naive + Contour-Explore. Contour-Explore
retains the fastest verified kernel found during the run.

optimizes ISA-level C, and AccelOpt optimizes Trainium NKI kernels using
profiles and optimization memory ( Nie et al., 2026 ; Hong et al., 2025 ; Zhang et al., 2025b ) ; GPU kernel
agents and benchmarks take the same program-level approach ( Sereda et al., 2025 ; Ouyang et al., 2025 ; Liao et al., 2026 ) . In these
workflows, the agent expresses its mapping choices through generated or
modified kernel code, which at the ISA level includes instruction calls,
address calculations, and data-movement schedules. In Contour-Explore, the agent
sets knob values and the compiler generates the kernel; the search policies
of these harnesses can use the same interface, as our AccelOpt integration
shows (Section 5.1 ). AutoTVM tunes the knobs of developer-written schedule templates ( Chen et al., 2018b ) , and Ansor and MetaSchedule generate schedule spaces
from fixed rules ( Zheng et al., 2020 ; Shao et al., 2022 ) . Timeloop
constructs per-layer mapspaces from hand-written architecture descriptions
and scores mappings analytically ( Parashar et al., 2019 ) . In these
systems, the space is fixed before search, and a mapping outside it is
unreachable for any search policy. Contour-Explore derives its mapping surface
from the RTL-lifted machine semantics and measures every mapping as a
generated kernel; when search stalls, Contour-Ext adds knobs and their lowering
to the compiler, extending the surface itself (Section 4.3 ). Concurrent to our work, CAKE ( Ye et al., 2026 ) proposes co-designing a GPU
compiler with kernel agents: agents write a typed, hardware-explicit
schedule IR, and the compiler returns localized diagnostics and evolves its
verifier rules and IR primitives when candidates expose missing
capabilities. Our work differs in three respects. First, CAKE targets NVIDIA
GPUs, for which large libraries of production kernels exist, and its
methodology builds on them: the IR is distilled from production kernels such
as those in FlashInfer and CUTLASS. Emerging accelerators have no such
corpus. Second, CAKE has no formal machine semantics; its primitives come
from production kernels and hardware documentation and are validated by
tests over its kernel corpus. Contour instead derives its knobs from
the formal, RTL-lifted machine semantics of the target, and Contour-Ext adds a
knob only after it passes legality checks against these semantics and the
numerical oracle. Third, CAKE’s candidates are written by LLM agents,
whereas the mapping surface of Contour-Explore can be searched by LLM agents and
by conventional policies such as hill climbing and GA alike. 7. Conclusion We present Contour , a compiler-mediated framework for kernel
generation on emerging accelerators. Contour-Explore connects search policies
to a reusable compiler through a workload-specific mapping surface: the
compiler completes partial mapping intents into legal plans, generates
target code, and returns verified correctness and performance feedback.
Contour-Ext extends this surface when search stalls: an extension agent
implements a new knob and its lowering, and Contour-Ext keeps the knob only if
it passes correctness and effectiveness checks. The naive agent searching through Contour-Explore returns a correct
kernel on every instance, whereas KernelCraft returns one on only
60% of the 20 Gemmini instances and 5 of the 18 PLENA instances. On the
instances where KernelCraft succeeds, the Contour-Explore agent’s
kernels are 2.86 × 2.86\times (Gemmini) and 1.13 × 1.13\times (PLENA) faster than
KernelCraft’s, and Contour-Explore spends 26.3% and 83.4% fewer
tokens per correct kernel. The Contour-Explore agent’s kernels are also 1.17 × 1.17\times faster than Gemmini’s library routine and 1.46 × 1.46\times faster
than those of the PLENA compiler. AccelOpt finds 1.50 × 1.50\times faster
kernels on Gemmini and 1.20 × 1.20\times faster kernels on four PLENA attention instances when it
searches through Contour-Explore instead of editing kernel programs. On 16 VTA instances,
Contour-Ext extends the AutoTVM surface, and AutoTVM’s XGBTuner finds 4.14 × 4.14\times faster kernels on the extended surface; on PLENA, the extended
surface makes the kernels found by hill climbing 1.20 × 1.20\times faster.
These results show that partial mapping specification
with compiler completion lets neural and conventional search share one
verified interface, and that this interface can be extended when search
stalls. A future direction is recursive improvement across data, models, and
harnesses, inspired by MetaRSI ( Tan et al., 2026 ) . The verified kernels,
mapping decisions, and measured performance produced by Contour-Explore,
together with the knobs accepted by Contour-Ext, could serve as post-training
data. A post-trained model could then search more efficiently and propose
further knobs; once these knobs pass the checks of Contour-Ext, they would
expand subsequent searches and produce further training data. References acc (2026) 2026.
