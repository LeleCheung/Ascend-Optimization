# GQA固定源码IR行打包

固定已验收019的Triton源码`2a98e3e0…`，目标原完整调用262.27775μs、0.491653×CANN。研究分支为远端`gqa-goal-20261121/gqa-ir-query-packing`；当前尚无修改IR的设备性能结果。

当前profiling显示输出搬运活跃带宽约72.55GB/s、向量侧读入约103.51GB/s；源绑定模拟器把写出定位到`tl.store`及MTE3搬运，保留各核部分窗口。原IR按128行、每行128个BF16元素读取Q及写出，GM行跨度8192元素。020源码二维打包的reshape在后端失败，提供进入单算子IR的具体编译问题。

候选保持128个program、每program四个querytile、K/V循环外复用及逐行浮点表达式。将每tile行集合改为16个序列位置×8个相邻query头，以16×1024连续元素条带搬运Q及输出，每tile同样16384个元素。预期DMA段由128段256B改为16段2048B；实际指令数和带宽待新二进制核对。65536个query行的唯一所有权与集合覆盖已核对。

003的精确原参数诊断显示最后pass为`InferHIVMDataLayout`。自动降级已把Q缓冲提升到L1／cbuf：16×1024视图作为load目的，同一底层alloc以128×128交给`mmadL1`，随后重写崩溃。该现场定位到Cube侧布局推导；后续采用显式重排时，ND／NZ转换、额外向量工作与UB需求分别检查。

IR原件、模型决策、源码冻结检查、失败IR和CPU编译证据见[分支材料](../gqa-ir-query-packing/status.json)。003／004属于已修改IR的编译修复，固定源码的原始IR仍有完整合格比较起点。达到可编译后继续使用原case1/2/4/7、官方checker与完整调用计时，随后profiling及模拟器重放；收益以超过保留最佳验收。

当前行打包路线保存现场，待出现新的受支持表达方案后继续。IR004调用前的宿主brief中文编码丢失已保留原件并补发完整文本；005仍选择了已知失败的三维折叠，因此按实际结构归档。独立`gqa-ir-loop-unroll`从019原始IR重新开始，研究固定四轮querytile循环的完全展开，保持当前Triton源码及原行所有权，所有成本与性能待实际编译和真机验证。
