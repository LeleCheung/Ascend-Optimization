# HG-KDA 维护约定

## 最高决策：诊断与候选实现分工

自2026-11-10起，本项目后续算子优化必须遵循以下分工；与其他工程说明冲突时，以本节为准。历史实验保留原有贡献记录，不追溯改写。

- **Codex负责分析瓶颈、提出改法，并将诊断能力沉淀到workflow、skill、知识库和分析／调度工具；不得直接编写或修改目标算子的候选实现。**
- **CC／DeepSeek负责生成和修改候选源码。** 该范围包含Triton kernel及候选自身的启动封装、缓存、索引、布局、正确性修复和回退路径；接口或编译错误也须反馈给CC／DeepSeek修改，不能由Codex直接补丁修复候选。
- Codex发现有效方法后，先记录证据、适用条件、机制假设、建议动作和验证方法，再通过已落盘的workflow／知识供CC／DeepSeek使用。禁止通过控制脚本代写候选补丁，或将完整目标实现包装成知识记录直接替换生成结果。Codex可以维护通用分析工具、评测适配和基础设施，但不能借此代做目标算子计算。
- 固定参考、测试合同、精度要求和计时口径。完整评测结果必须返回生成模型，性能未达标时继续修改候选；不能仅以正确性预检通过结束优化，也不能为达标放宽评测要求。
- 保留方法／workflow版本、模型输入输出、生成源码SHA和正式评测证据。Codex新增的诊断与建议属于实质贡献，应如实标注；候选由CC／DeepSeek编写不等于优化方向由其自主发现。历史最佳源码回归与新生成优化分别报告。

## 实现约束

- 候选全部设备计算、复制、归约、扫描、布局转换和回退严格使用 Triton。CANN 原生库及来源明确的 Ascend C 实现仅作为参考。
- Python/C++ 只承担分配、元数据、编译缓存、参数、状态管理及 Triton 启动。原生 DMA、PyTorch 目标计算、CPU 计算不能替代候选路径。
- 静态门禁、绑定源码的逐路径审查、完整 KGS 评测及必要补充检查分别记录，不能互相替代。
- 默认一次完整正式评测；额外复测需说明原因。正式完整调用、独立 profiling 和模拟器耗时分开。
- 分数、来源与实际贡献如实标注。历史 Codex 参与的结果不表述为纯原生 KG 独立效果；历史混合后端成绩不计入严格 Triton 成果。

## 目录与接口

- src/hgkda/：标准库诊断核心；不得导入 KG/KGS 内部实现或硬编码机器路径。
- skills/hgkda/：完整 skill 入口、调用脚本和接口说明。
- examples/：真实证据的精选离线案例，保留来源及哈希。
- tests/：身份、统计、时间范围、适配器及调用验证。
- docs/、manifests/：专业说明、接口合同、迁移与恢复记录。
- 运行环境、日志、缓存和新实验输出放在仓库外，通过参数或配置选择。

## 维护规范

自有文档及注释使用专业中文，字段和命令使用稳定英文标识。删除口语任务记录和个人化表述，保留版权、许可证、正式引用及真实贡献。来源文件和冻结原件不做全文替换。

共享服务器上只操作明确属于本项目的路径与进程；不修改 root 内容、不重启共享服务/容器/镜像。不变更用户 .vscode/，不将其暂存。任何清理前先核验依赖、原件和恢复位置。

网页与模型使用相同 JSON 合同。事实、规则假设和验证结论分字段；缺失证据显式标记，不以指标阈值推断确定因果，不把模拟器指令时间当作真实关键路径。
